# Torikumi Prediction: Empirical Opponent Distributions

## Status

The first descriptive phase specified by this document is implemented in
`src.analysis.torikumi_prediction`. It produces historical observation and
aggregate distributions; it does not yet specify or implement a model that
predicts an exact opponent or a complete daily card.

The existing public **Torikumi** artifact is prospective: it presents
published bouts to someone who has not yet watched them. This analysis is
retrospective and belongs in a separate analysis package. It must not change
the live torikumi acquisition path, the annotated Torikumi artifact, or the
canonical `History` model.

## 1. Motivation

Torikumi are not generated by a published mechanical draw. They are selected
under hard restrictions and apparent policies involving banzuke position,
current record, the stage of the basho, the championship race, absences and
the supply of opponents who have not already been faced.

The practical ability to name an exact future opponent may be low. That does
not imply that opponent selection is statistically unstructured. Before
attempting an exact prediction model, this package should establish what the
historical schedules say about the class of opponent selected for a rikishi
of a given class, on a given day, with a given record.

The primary subject is makuuchi. The implementation will nevertheless process
all banzuke divisions by default. Results for lower divisions may later be
ignored if they are not interesting; lower-division peculiarities must not
drive changes to the questions, definitions or presentation intended for
makuuchi.

## 2. Questions

For a focal rikishi of banzuke class `C` and an opponent of class `C'`, the
first analysis will estimate the observed distributions:

```text
P(C' | C, day)
P(C' | C, day, wins_before)
P(C' | C)
```

The package will also retain losses and prior-bout number so that it can
derive a record-conditioned distribution that remains meaningful below
juryo:

```text
P(C' | C, day, wins_before, losses_before)
```

These are descriptive probabilities among observed scheduled bouts. They are
not yet probabilities conditional on every opponent who was legally or
practically available.

The initial results should help answer:

* how tightly early opponents are grouped by banzuke class;
* how the opponent-class distribution changes across the fifteen days;
* how strongly the distribution changes with the focal rikishi's record;
* when high-ranking classes begin to meet each other;
* how often cross-division opponents appear; and
* whether the same extraction and aggregation are informative outside
  makuuchi without division-specific redesign.

## 3. Source and Population

The source is canonical `History`.

Only completed basho whose `Summary` reaches Day 15 are included. This avoids
allowing a current or otherwise partial basho to bias the all-day aggregates.
The implementation must report the represented date range, included basho
count and excluded incomplete-basho count.

Every pair in each day's `DailyResults.torikumi` is a scheduled bout and is
included. A bout that ultimately produced fusensho/fusenpai remains a real
selection decision and therefore remains in this analysis. Championship
playoffs are outside the regular daily torikumi and are not included.

All divisions represented on the banzuke are processed by default:

```text
Makuuchi
Juryo
Makushita
Sandanme
Jonidan
Jonokuchi
```

The focal rikishi's banzuke chii determines the division of an observation.
A cross-division bout therefore contributes one observation to each ranked
participant's division. For example, an `M16` versus `J2` bout contributes:

* a makuuchi observation with opponent class `J2`; and
* a juryo observation with opponent class `M16`.

The implementation must not assign a cross-division bout wholly to its higher
division for this analysis.

## 4. Banzuke Class

The principal explanatory and response variable is a semantic banzuke class.
It is derived from the structured `Chii` fields, never by parsing or sorting
the display string.

Side and annotation are removed. Yokozuna, ozeki, sekiwake and komusubi are
grouped by level irrespective of their internal number. Maegashira and all
lower-division ranks retain their number:

```text
Y1e, Y1w, Y2e       -> Y
O1e, O1w, O2e       -> O
S1e, S1w, S2e       -> S
K1e, K1w, K2e       -> K
M1e, M1w            -> M1
M17e, M17w          -> M17
J1e, J1w            -> J1
Ms12e, Ms12w        -> Ms12
Sd20e, Sd20w        -> Sd20
Jd35e, Jd35w        -> Jd35
Jk10e, Jk10w        -> Jk10
```

No maximum class number is hard-coded. The observed banzuke determine which
classes exist in each basho and across the selected history.

The class object used in computation should preserve structured level and
optional number fields, with a display label produced separately. Ordering
must follow the semantic chii order rather than lexicographic label order.

## 5. Observation Unit

The unit of analysis is a scheduled-bout endpoint: one scheduled bout
normally produces two directed observations, with each participant taking a
turn as the focal rikishi.

For an `M3e` versus `M7w` bout the observations are:

```text
focal M3, opponent M7
focal M7, opponent M3
```

This directed representation gives an unambiguous denominator for a
conditional opponent distribution. It also permits the two endpoints of a
cross-division bout to belong to different focal divisions.

An aggregate `observations` value is therefore a count of rikishi-bout
endpoints, not necessarily a count of distinct bouts. Any report that also
shows bout counts must label the two measures distinctly.

## 6. Pre-Day Record

For a bout on Day `d`, the focal rikishi's pre-day record is calculated from
recorded results on Days 1 through `d - 1`:

* `W` and `FS` count as wins;
* `L` and `FP` count as losses; and
* there is no draw category.

The row records:

```text
wins_before
losses_before
bouts_before = wins_before + losses_before
bout_number = bouts_before + 1
```

In makuuchi and juryo, `wins_before + losses_before` will normally equal
`d - 1`, subject to absences. Below juryo, rikishi do not compete daily, so
day and bout number are not interchangeable. Retaining both allows the same
base data to be used for all divisions without pretending that their schedules
have the same cadence.

The first distributions use the actual official record entering the scheduled
day. Reconstructing the possibly earlier record known to the torikumi
committee when it compiled the card is a possible later refinement and is not
part of this implementation.

## 7. Base Observation Data

The package will first write a rich row-level CSV. At minimum it contains:

```text
basho
day
focal_id
focal_chii
focal_class
focal_division
opponent_id
opponent_chii
opponent_class
opponent_division
wins_before
losses_before
bouts_before
bout_number
cross_division
fusen
```

The row should additionally retain the two rikishi's positions in that
basho's actually occupied, fully ordered banzuke and their signed difference:

```text
focal_roster_position
opponent_roster_position
roster_position_delta
```

Roster position is secondary explanatory data. It must not replace banzuke
class: the number of occupied sanyaku slots and the lower end of a division
vary between basho, so the roster distance between two named classes is not
fixed.

`fusen` describes the result attached to the scheduled pair. It does not
control whether the observation is included.

## 8. Missing Banzuke Participants

A participant may appear in a daily torikumi without a chii on that basho's
banzuke. Such cases must be audited rather than silently dropped.

For the first implementation:

* a ranked focal participant still contributes an observation;
* an unranked opponent is represented with opponent class `Mz`;
* an unranked participant does not contribute a focal observation because no
  banzuke division or focal class can be assigned; and
* counts and identifying details for all such cases are written as diagnostics.

`Mz` is an analysis label for the missing-banzuke endpoint. It is not treated
as a seventh banzuke division.

## 9. Aggregate Outputs

All aggregate outputs are long-form CSV data. Each probability row must carry
its numerator and denominator; low-support cells must not be hidden behind an
arbitrary threshold.

### 9.1 Class by day

```text
P(C' | C, day)
```

Candidate fields:

```text
focal_division
focal_class
day
opponent_class
observations
focal_total
probability
```

### 9.2 Class by day and wins

```text
P(C' | C, day, wins_before)
```

Candidate fields add `wins_before` to the class-by-day fields.

### 9.3 Class by full pre-day record

```text
P(C' | C, day, wins_before, losses_before)
```

Candidate fields add `wins_before`, `losses_before`, `bouts_before` and
`bout_number`. This output is required even if the first makuuchi presentation
does not use it, because wins and day do not determine a lower-division
rikishi's record.

### 9.4 Overall class distribution

```text
P(C' | C)
```

Candidate fields:

```text
focal_division
focal_class
opponent_class
observations
focal_total
probability
```

### 9.5 Supporting marginals

The output should also make the following inexpensive views derivable, either
as additional aggregates or directly from the base CSV:

```text
P(C' | C, bout_number)
P(opponent_division | focal_division, day)
distribution(roster_position_delta | focal_division, focal_class, day)
```

These are supporting diagnostics rather than replacements for the four
principal class distributions.

## 10. Weighting and Interpretation

Every scheduled endpoint has equal weight. Consequently:

* common matchup types contribute more than rare matchup types;
* a rikishi appearing on many scheduled days contributes more observations
  than one appearing on few days; and
* the overall distribution describes the historical schedule experienced by
  rikishi-bout endpoints, not an equally weighted average of basho, rikishi or
  class-pair estimates.

This weighting is intentional for the first descriptive account. Alternative
per-basho or per-rikishi weighting can be considered later if the initial
results show that a small number of eras or rikishi dominate a finding.

The probabilities do not by themselves measure a committee preference for a
class. The observed share of opponents from `O`, for example, depends partly
on how many active ozeki existed and were available in the represented basho.
The first report must describe its results as observed selection frequencies,
not opportunity-adjusted selection rates.

## 11. Validation and Diagnostics

The implementation must validate or report at least:

* included and excluded basho counts and date ranges;
* scheduled bout count and directed observation count;
* counts by focal division;
* cross-division bout and observation counts;
* fusen bout and observation counts;
* missing-banzuke participants and affected bouts;
* duplicate participation by one rikishi on the same day, if any;
* a repeated regular opponent within one basho, if any;
* result pairs whose participants disagree with the scheduled pair, if any;
* aggregate numerators summing to their stated denominators; and
* probabilities within each conditioning group summing to one, subject only
  to output rounding.

Unexpected cases should be surfaced in diagnostics before the package adopts
special-case behaviour for them.

## 12. Division Policy

The extractor and aggregators operate on every division by default and write
division-identifiable outputs. They must not contain a makuuchi-only branch in
their core logic.

Makuuchi nevertheless governs the purpose of the work:

* the initial interpretation and narrative focus on makuuchi;
* code should not acquire lower-division-specific scheduling rules merely to
  make lower-division findings look cleaner;
* juryo and lower-division outputs are evaluated after the common analysis
  runs; and
* an uninteresting or peculiar result confined to a lower division may be
  omitted from publication without changing the implementation.

Retaining `day`, `bout_number`, wins and losses is sufficient to let the common
analysis reveal whether lower divisions remain meaningful under the same
questions.

## 13. Package Boundary

The proposed package is:

```text
src.analysis.torikumi_prediction
```

It will consume `History` and write analysis artifacts under a dedicated
output root. It may reuse general CSV/JSON output helpers, but it must not:

* modify `History`;
* modify `src.infra.torikumi` or its persisted `Future`;
* modify the rating-annotated public Torikumi producer;
* calculate bout-winning probabilities;
* publish files directly to the website; or
* treat result outcomes as evidence about which opponent was selected, except
  to reconstruct the focal rikishi's pre-day record and identify fusen.

The command-line entry point is:

```text
python -m src.analysis.torikumi_prediction
```

It writes immutable timestamped runs beneath:

```text
files/output/analysis/torikumi_prediction
```

An alternative History zip, date range and output root can be supplied with
`--history-zip`, `--start`, `--end` and `--output-root`.

## 14. Deferred Work

The first implementation will not:

* reconstruct historically eligible opponent sets;
* reconstruct dated heya membership or family relationships;
* calculate opportunity-adjusted selection rates;
* infer the record available at the time the card was compiled;
* learn or hand-code opponent-selection rules;
* predict an exact opponent;
* solve a complete daily card as a constrained matching problem;
* evaluate top-k opponent predictions, entropy, log loss or calibration;
* decide which lower-division results merit a public presentation; or
* integrate the results into the public site.

Those questions should be informed by the empirical distributions rather than
prejudged in the first implementation.

## 15. Completion Criteria

The first implementation is complete when it can, from a supplied `History`:

1. select completed basho and report the selected historical scope;
2. derive semantic classes for every ranked participant;
3. emit the directed base observations for every division;
4. reconstruct wins and losses before every scheduled bout;
5. retain fusen schedules and audit missing-banzuke endpoints;
6. emit the four principal aggregate distributions with counts and
   probabilities;
7. retain roster-position displacement as supporting data;
8. demonstrate aggregate reconciliation and probability-sum validation in
   automated tests; and
9. run all divisions through the same core extraction and aggregation path.

Only after these outputs have been inspected should a second proposal decide
whether exact torikumi prediction is worthwhile and, if so, how candidate
availability and whole-card constraints should be modelled.
