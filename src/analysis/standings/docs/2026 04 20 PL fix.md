# Position Statement: Standings Metrics Model Revision

## 1. Executive Summary

The project has successfully progressed from a computational standings engine to a functioning browser-based standings application.

We now have:

* a standings engine operating over canonical historical data
* multi-basho rolling-window publication
* generated CSV datasets
* JSON sidecars
* bootstrap configuration
* static HTML/CSS presentation
* JavaScript loading, filtering, and sorting
* successful deployment to a live local Apache host

This is a substantial achievement.

During live use of the browser presentation, however, an important conceptual gap has become visible in the metrics model.

The existing model distinguishes:

1. **wins type** (`real` vs `all`)
2. **basho basis** (`window` vs `presence`)

but does **not** distinguish:

3. **bout-count basis** (`expected` vs `as_available`)

This omission affects the meaning of displayed counts, averages, and comparisons.

The project therefore now requires a controlled extension of the standings model.

---

## 2. What Has Been Achieved

## 2.1 Engine Capability

The standings engine can already compute standings over selected windows of basho using canonical historical data.

It supports:

* single basho standings
* rolling multi-basho standings
* selectable win definitions
* ranked outputs
* derived statistics
* publication artefacts

This engine remains architecturally sound.

---

## 2.2 Publication Layer

An offline publisher now generates:

* one dataset per supported retrospective basho window
* metadata sidecars for each dataset
* bootstrap site configuration

This cleanly separates:

* calculation
* publication
* browser presentation

---

## 2.3 Browser Application

A static browser application now exists with:

* window selector
* division selector
* sortable table
* dynamic loading of published data
* dynamic range display

The project has therefore already crossed the threshold from prototype to usable product.

## 3. What Has Been Learned Through Live Use

When examining the published table, the meaning of the **Count** column became questionable.

Example expectation:

For a 6-basho view, a rikishi present in 4 basho and expected to fight 15 times each basho would naturally be thought of as having:

```text
4 × 15 = 60 expected bouts
```

Yet current displayed counts derive from actual recorded bouts fought, e.g.:

```text
59
```

if one bout was missed.

This exposed a distinction not previously modelled explicitly.

---

## 4. Existing Metric Dimensions

The current system already contains two genuine dimensions.

---

## 4.1 Wins Type

* `real` wins only
* `all` wins including fusen etc.

---

## 4.2 Basho Basis

### Window

All basho in the selected window count.

Example:

6-basho view always uses denominator 6.

### Presence

Only basho in which the rikishi was present count.

Example:

Absent in 2 of 6 basho means denominator 4.

---

## 5. Newly Discovered Dimension

## 5.1 Bout-Count Basis

This is independent of the above two dimensions.

### Expected

Count the bouts a rikishi would normally be expected to have had in basho where he was present.

Examples:

* sekitori: 15 per basho
* lower divisions: 7 per basho

Thus:

```text
present in 4 basho => expected count 60
```

### As Available

Count only actual recorded bouts available in the data.

Thus:

```text
present in 4 basho, missed one day => 59
```

---

## 6. Why This Matters

Without this distinction, numbers can appear misleading.

A rikishi who won every bout fought may display as:

```text
59 / 59
```

under actual-bouts counting,

but another reasonable interpretation is:

```text
59 / 60
```

under expected counting.

Likewise, on a full-window basis:

```text
59 / 90
```

may also be meaningful.

These are not errors.

They are different analytical bases.

The system currently exposes some of these implicitly and others not at all.

---

## 7. Revised Conceptual Model

The standings metrics model now has three binary dimensions:

## 7.1 Wins Type

* real
* all

## 7.2 Basho Basis

* window
* presence

## 7.3 Bout Basis

* expected
* as_available

This yields:

```text
2 × 2 × 2 = 8
```

possible metric families.

---

## 8. What Should Change

## 8.1 Immediate Conclusion

The current browser table is not wrong.

It is displaying metrics from a partially expressed model.

The remedy is not patching labels alone.

The remedy is to extend the publication model so the third dimension is explicit.

---

## 8.2 Engine Outputs

The engine / publisher should compute and export additional count fields such as:

* `window_expected_bout_count`
* `window_available_bout_count`
* `presence_expected_bout_count`
* `presence_available_bout_count`

or equivalent clearer names.

---

## 8.3 Derived Metrics

Averages and rates should then be definable explicitly against those bases.

---

## 8.4 Browser UI

Initially, no new control need be exposed.

The page can simply adopt one chosen default basis.

Later, an advanced selector can allow users to switch basis.

---

## 9. Recommended Default Interpretation

For public standings use, a strong candidate default is:

* wins type = `real`
* basho basis = `presence`
* bout basis = `expected`

This corresponds to:

> How successful was this rikishi in basho where he actually participated, judged against normal opportunity?

This is intuitive and fair.

---

## 10. Action Plan

## Phase 1 — Data Model Revision

1. Add explicit expected / available count calculations in Python.
2. Add exported CSV columns.
3. Preserve backward compatibility where possible.

---

## Phase 2 — Publication Refresh

1. Regenerate all published datasets.
2. Verify counts manually against sample rikishi.

---

## Phase 3 — Browser Adjustment

1. Rename ambiguous **Count** column.
2. Display chosen default count basis.
3. Ensure Mean column basis matches Count basis.

---

## Phase 4 — Optional UI Enhancement

Add selector:

```text
Count Basis:
Expected / Actual
```

and possibly later:

```text
Basho Basis:
Window / Presence
```

---

## 11. Final Position

The current project is successful and fundamentally sound.

What has happened is not failure, but refinement through real use.

The browser page has exposed an analytical dimension that remained latent in the engine.

This is exactly the kind of discovery healthy prototypes are supposed to produce.

The correct next move is therefore:

> preserve the current architecture, extend the metrics model, regenerate the published data, and then expose the richer semantics cleanly in the UI.
