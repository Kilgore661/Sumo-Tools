# Proposal: contribution of normalisation to Elo-89 rating changes

## Purpose and decision context

The author accepts Elo-89 as a useful operational rating system. This
investigation supplies evidence for a personal judgement about the practical
importance of normalisation. It is not a pass/fail condition for publishing
the ratings. Even an arguably material but non-disastrous contribution may be
acceptable, provided the account explains it honestly and remains open to
well-supported alternatives.

The expectation to examine is:

> Population normalisation usually contributes little to reported rating
> changes compared with changes generated by competition over the same period.
> Its contribution is unlikely to materially alter readers' interpretation,
> including in Makuuchi, which deserves separate inspection.

The analysis must expose exceptions as well as typical values. It must not
encode an arbitrary significance threshold, label the model as passing or
failing, or infer reader reactions from numbers alone. Implementation can
proceed without a numerical definition of "material": interpretation belongs
to the author after seeing the results.

## Scope

Implement a separate, read-only consumer of production artifacts under
`src.analysis.elo89_normalisation`. The primary deliverable is an accounting
of changes over the same observation intervals as the site's rating-change
tables, with historical rolling windows added to avoid judging the effect
only at the latest basho.

The package must not change Elo-89, its entrant map, its handling of returning
rikishi, the production bundle or the published website. Missing bouts while
remaining represented retains the existing rating. Leaving the represented
population and returning triggers P1 reinitialisation; that policy is accepted
and must be handled explicitly in the accounting.

Two related questions remain outside this first implementation:

- cumulative contributions to a wrestler's rating since initialisation,
  including an enriched current-rating table and adjacent-rikishi gap table;
- how present ratings or pairwise gaps would differ in a counterfactual replay
  with pre-basho normalisation disabled.

These are possible later extensions, not prerequisites for resolving the
appraisal's original TBD. In particular, the accounting below does not measure
the full causal effect of normalisation on subsequent probabilities and bout
updates.

## Existing observations

Inspection of the saved production bundle covering January 1989–July 2026
found 224 basho adjustments. End-of-basho shifts had mean absolute magnitude
0.0395 points and maximum absolute magnitude 0.1534. Start-of-basho shifts had
median absolute magnitude 2.2310, mean absolute magnitude 3.9477, and range
−8.6405 to +30.4014. The largest positive shift was May 1992, when the recorded
population grew from 721 to 850, with 147 initialisations and 18 departures.
Initialisations include returns, not necessarily only career debutants.

These observations motivate separate treatment of the two operations. They
are not significance findings or golden values that future runs must match.
The implementation must calculate its statistics from the supplied run and
record that run's provenance. Earlier illustrative two- and four-point examples
are not evidence about particular wrestlers.

The saved Elo-89 run is still a separate required input, with the standard
site-bundle location as its default. Live History validates that run and supplies

Use the manifest, `basho_adjustments.csv`, `basho_start_ratings.json`,
`basho_end_ratings.json` and `bout_ledger.csv` from one production run. Read
the matching History for chii, divisions and names; use only the dates
represented in that run. Daily snapshots are not needed for this experiment.

Validate model identity, chronological coverage, IDs, active snapshot sets and
adjustment counts. Every ledger participant must be active in the relevant
snapshot. Reject mismatches rather than silently combining runs. Record input
paths and SHA-256 hashes, the model manifest, dates, window sizes and package
configuration in the diagnostic manifest. Stream the large bout ledger into
per-rikishi/per-basho aggregates.

The output directory must be distinct from and must not contain or be inside
an input directory. Write only this package's declared artifacts; do not
recursively clear an arbitrary user-supplied directory. No production run,
prior fitting, network access or deployment is invoked.

## Accounting definitions

For each basho t, let S(t) be the pre-basho common adjustment and E(t) the
post-basho common adjustment. Let B(i,t) be the sum of both-sided ledger deltas
belonging to wrestler i in that basho. Sum actual rating-point deltas, not
delta/K: the site's existing fields named `normalised_delta...` describe a
different normalisation and must not be used for this purpose.

For a wrestler present continuously between two processed basho-end snapshots
a and b:

```text
displayed_change = end_rating(i,b) - end_rating(i,a)
bout_contribution = sum B(i,t), for a < t <= b
pre_contribution = sum S(t), for a < t <= b
post_contribution = sum E(t), for a < t <= b
normalisation_contribution = pre_contribution + post_contribution
displayed_change = bout_contribution + normalisation_contribution
```

The start endpoint's adjustments and bouts are already included in its rating
and must not be counted again. A window of n basho means n successive
represented observations, matching the site, not n fixed calendar intervals.
No-bout basho still count and receive the applicable adjustments.

For returners, infer initialisation episodes from active snapshot membership.
The raw initial rating at a return is its start snapshot value minus S(t).
Define the reset contribution as that raw initial rating minus the last
represented end rating before the gap. Include only adjustments and bouts
received while represented. Then an endpoint-comparable window obeys:

```text
displayed_change = bout_contribution + pre_contribution
                   + post_contribution + reset_contribution
```

Sum reset terms if there is more than one return. Report such rows in a
separate category: a reset is not normalisation. Do not discard these rows
from the latest-site reconciliation, but keep them out of the main continuous
rating summaries. A debutant without the required start endpoint has no
comparable endpoint change and is counted as excluded, not assigned zero.

The remainder after this decomposition is a numerical reconciliation residual,
not another substantive component. Require absolute residual <= 1e-6 rating
points using full-precision sources. When comparing site CSV values rounded
to three decimals, allow the corresponding rounding tolerance (0.001 points).

Subtracting accumulated adjustments holds the observed bout updates fixed.
It does not reconstruct an alternative Elo history. Also, applying one common
shift to simultaneously active X and Y contributes exactly zero to their
instantaneous rating gap; these outputs must not describe it as an actual
movement of positions in the rating order.

## Populations and intervals

Use windows of 1, 2, 3, 4, 5, 6 and 12 represented basho, matching production.
Produce the latest endpoint tables and all available historical rolling
endpoint tables. Match the site's eligibility rule of presence at both
endpoints, while distinguishing continuous and reset-containing windows.

Report all wrestlers and Makuuchi separately. For comparability with the site,
the primary Makuuchi group is membership at the end endpoint. Include start
division, end division and whether the wrestler remained in Makuuchi throughout
the window, so promotions and demotions can be inspected. Missing chii stays
explicitly unclassified. Report counts for all categories and exclusions.

Use one observation per basho for common-adjustment distributions. For
individual change summaries, use one wrestler-window observation and state
that weighting. Historical rolling windows overlap; the result is descriptive,
not a collection of independent observations for a significance test. Provide
per-endpoint summaries so large historical populations do not hide differences
between periods.

## Proposed outputs

Write machine-readable CSVs alongside a human-readable report and local HTML
charts. Label units as rating points and define all denominators.

| Artifact | Contents |
|---|---|
| `manifest.json` | Input provenance, dates, configuration and output inventory |
| `basho_adjustments.csv` | Pre/post shifts, their sum, active counts, entrants and departures |
| `window_changes.csv` | IDs, names, dates, window, divisions, episode status, endpoint ratings, bouts, four accounting contributions and residual |
| `latest_changes.csv` | Latest endpoint subset for all seven windows, suitable for comparison with site tables |
| `summaries.csv` | Overall and per-endpoint distribution summaries, by window and population |
| `exceptions.csv` | Largest contributions, largest residuals and reset-containing windows, with enough context to inspect each case |
| `report.md` | Definitions, provenance, observed results and limitations; no automated verdict on materiality |
| `charts.html` | Local diagnostic views described below |

Distribution summaries include counts, signed mean, mean absolute value,
population standard deviation, minimum, maximum and linearly interpolated
1st, 5th, 10th, 25th, 50th, 75th, 90th, 95th and 99th percentiles. Summarise
bout, pre-, post- and combined normalisation contributions independently,
including absolute magnitudes and the displayed total change.

For each population/window, show mean absolute normalisation divided by mean
absolute bout contribution, and median absolute normalisation divided by
median absolute bout contribution. Display the numerator and denominator as
well as the ratio. If a denominator is zero, report unavailable. These are
descriptive comparisons, not significance thresholds. Do not calculate an
individual percentage by dividing by a near-zero net change.

Show counts of sign reversals between bout contribution and displayed change
for continuous windows, with exact zero treated separately. Include their
actual magnitudes; a sign reversal alone does not establish practical
importance. Inspect the 20 largest absolute normalisation contributions per
population/window, retaining ties, plus the five largest positive and negative
pre-basho shifts. Avoid selecting examples only because they support the
expectation.

The HTML views should provide window and population selection and include:

1. Time series and distributions of pre- and post-basho shifts, visibly
   separated so the small post-basho values remain readable.
2. Comparable distributions of bout-derived and normalisation contributions.
3. A scatterplot of bout contribution against displayed change with an identity
   line; hover identifies wrestler, dates and both adjustment components.
4. A sortable enriched change table and an exceptions view, with reset rows
   visibly identified and excluded from continuous summaries.

This is an enriched **change** table. A lifetime rating-origin decomposition
or pairwise differences table is deferred as described in Scope.

## Implementation structure

Suggested modules are `__main__.py` for arguments, `inputs.py` for validated
artifact loading, `accounting.py` for episode and window reconstruction,
`summary.py` for descriptive statistics, and `report.py` for output generation.
Reuse stable History and production-artifact readers where suitable, but do
not import a producer that reruns or modifies Elo-89. Keep numerical accounting
independent of chart generation.

## Verification and completion

Use small hand-calculated fixtures to establish:

- exact endpoint accounting with unequal pre/post shifts and nonzero bouts;
- correct endpoint inclusion for one- and multi-basho windows;
- no-bout periods retaining their common adjustments;
- departure and return, including correct reset terms and no adjustments
  attributed during absence;
- endpoint membership exclusions, division transitions and missing chii;
- zero denominators, signs, percentiles and the specified weighting;
- unchanged pairwise gaps under a common shift.

On the supplied production run, require reconciliation of every eligible
window within tolerance and compare the latest seven windows with the existing
site tables. Generate and inspect charts and tables for readable labels,
correct filters and agreement with the underlying CSVs. Input hashes must be
unchanged after execution.

The implementation is complete when the outputs are reproducible, accounting
checks pass, and the author can inspect typical effects and exceptions for
Makuuchi and the full population. A judgement that the effect is negligible is
not a completion criterion. Record the author's eventual interpretation in a
separate findings document and use it to resolve the appraisal's TBD; do not
prewrite that conclusion here.
