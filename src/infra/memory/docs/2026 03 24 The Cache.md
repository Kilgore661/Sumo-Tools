# Cache/Shared Memory Loader for Annotated Sumo History

## Purpose

This folder contains a small Python utility for **loading a large annotated sumo-history dataset once**, storing it in **OS shared memory**, and allowing other Python processes to **attach to the same named memory block** instead of repeatedly loading the dataset from disk.

The intended outcome is faster startup for downstream programs that need access to the same historical `History` object.

---

## Files

### `version.py`
Defines the shared-memory version identifier:

```python
VERSION = 4
```

This value is used to construct the shared memory segment name:

```python
history{VERSION}  # -> history4
```

The version number acts as a simple compatibility boundary. If the serialized payload format, source data, or expectations change, incrementing `VERSION` prevents clients from attaching to an older incompatible memory segment.

---

### `shared_memory_start.py`
Bootstraps the shared-memory segment.

#### Responsibilities
- Loads annotated history from disk using `load_history_with_annotations(...)`
- Serializes the resulting Python object with `pickle.dumps(...)`
- Creates a named shared memory block large enough to hold the serialized bytes
- Writes the serialized bytes into shared memory
- Keeps the process alive so the shared memory remains available
- Cleans up the segment on exit

#### Current execution flow
1. Import `load_history_with_annotations` from `infra.persistence.annotated_serialiser`
2. Read the history dataset from:
   ```python
   ../files/output/fsm/Historys/1958_01 to 2025_11
   ```
3. Convert the loaded object to a pickled byte stream
4. Validate the byte stream with a test `pickle.loads(...)`
5. Create a shared memory segment named `history4`
6. Copy the serialized bytes into `shm.buf`
7. Print basic metadata such as name and size
8. Wait for user input before releasing the segment
9. On shutdown, call:
   - `shm.close()`
   - `shm.unlink()`

#### Run command
From `src`:

```bash
py -m infra.memory.shared_memory_start
```

#### Notes
- The process must remain alive; otherwise the shared memory will be cleaned up in the `finally` block.
- The file is written as an interactive foreground utility rather than a background service.

---

### `shared_memory_connect.py`
Connects to an already-created shared-memory segment and reconstructs the history object.

#### Responsibilities
- Open the named shared memory segment `history{VERSION}`
- Read the full byte payload from the segment
- Deserialize it back into a Python object using `pickle.loads(...)`
- Return that object to the caller

#### Public API
```python
connect() -> history | None
```

#### Current execution flow
1. Attempt to attach to shared memory named `history4`
2. Read all bytes from `shm.buf`
3. Unpickle the bytes into `history`
4. Return the reconstructed object
5. If the segment does not exist, print a message telling the user to run:
   ```bash
   py -m infra.memory.shared_memory_start
   ```

#### CLI behavior
If run directly, it calls `connect()` and prints the number of loaded basho objects:

```bash
py -m infra.memory.shared_memory_connect
```

## Dependency on the Serialisation Layer

This folder depends on a separate persistence module described in the project notes as the **Sumo Serialisation Module**.

That module provides APIs such as:

```python
save_history_with_annotations(history, filename)
load_history_with_annotations(filename)
```

Its role is to convert rich domain objects such as `History`, `BashoState`, `Banzuke`, and `Summary` into JSON-compatible structures, store them in compressed `.zip` files, and reconstruct them later.

This shared-memory utility sits **after** that persistence layer in the pipeline:

1. Serialized annotated history exists on disk
2. `shared_memory_start.py` loads it into a Python object
3. The object is pickled into bytes
4. Those bytes are placed into named shared memory
5. Other processes attach and unpickle the object locally

## How It Works in Practice

### Startup side
A single process loads the full dataset once and publishes it into shared memory.

### Consumer side
Any number of Python processes can attach to the same named segment and reconstruct the same history object without reloading the dataset from the original `.zip` source.

This is useful when:
- the underlying dataset is large
- disk deserialization is slow
- multiple short-lived analysis/test processes need the same data

---

## Design Characteristics

### Benefits
- **Reduces repeated disk I/O** for consumers
- **Avoids repeated domain reconstruction from the annotated archive**
- **Simple API surface** with one writer and one reader
- **Versioned shared-memory name** provides a basic compatibility mechanism

### Limitations
- The shared memory contains a **pickled blob**, not a structured zero-copy layout
- Every consumer still performs a full `pickle.loads(...)`
- The entire object must fit in available RAM and shared-memory limits
- The writer process must remain alive to keep the segment available
- `pickle` payloads are Python-specific and unsafe to load from untrusted sources

### Operational implications
This approach improves load behavior mainly by skipping repeated reads from the history archive on disk. It does **not** provide fine-grained shared object access between processes; each consumer reconstructs a private Python object from the shared byte buffer.

## Expected Usage Pattern

### 1. Start the publisher
```bash
py -m infra.memory.shared_memory_start
```

Expected console output includes:
- loading message
- shared memory creation message
- segment name
- approximate memory size

### 2. Connect from another process
```python
from infra.memory.shared_memory_connect import connect

history = connect()
if history is None:
    raise RuntimeError("Shared history is not available")
```

### 3. Shut down the publisher when no longer needed
Press Enter in the startup process. This triggers cleanup and removes the named shared memory segment.

---

## Error Handling

### Missing shared memory segment
If `shared_memory_connect.py` cannot find the segment, it catches `FileNotFoundError` and tells the user to run the startup module first.

### General exceptions
Both scripts print the exception and traceback for easier debugging.

### Resource cleanup
`shared_memory_start.py` ensures cleanup in a `finally` block:
- `close()` detaches the process handle
- `unlink()` removes the named segment

---

## Security and Reliability Notes

### `pickle` safety
`pickle.loads(...)` must only be used with trusted data. In this design the bytes originate from a local trusted process, so that assumption appears to hold, but it should be called out explicitly in production documentation.

### Memory pressure
The code allocates enough shared memory to store the full serialized history. Depending on dataset growth, this may become a significant memory footprint.

### Cross-version compatibility
A client and publisher must agree on:
- the `VERSION` constant
- the Python object model
- the pickled payload expectations

Changing the history schema or the object graph without updating `VERSION` could lead to subtle runtime issues.

---

## Suggested Improvements

### 1. Close the shared memory handle in the reader on success
`shared_memory_connect.py` returns `history` but does not explicitly close the shared memory handle after deserialization succeeds. Since the byte payload is copied into `bytes(shm.buf)` before unpickling, it would be cleaner to close the handle before returning.

Possible pattern:

```python
shm = shared_memory.SharedMemory(name=f'history{VERSION}')
try:
    history = pickle.loads(bytes(shm.buf))
    return history
finally:
    shm.close()
```

### 2. Store payload length explicitly
The reader currently deserializes `bytes(shm.buf)` for the entire segment. That works because the segment size exactly matches the serialized payload size. Storing a small header with payload length would make the protocol more explicit and easier to evolve.

### 3. Replace interactive lifetime management with a service model
Instead of blocking on `input(...)`, the publisher could run as:
- a daemon/service
- a context-managed test fixture
- a process supervised by a task runner

### 4. Add health and compatibility checks
Examples:
- schema/version metadata in the payload
- checksum validation
- dataset source path in metadata
- creation timestamp

### 5. Consider alternatives to pickle for long-term robustness
If cross-version stability or safety becomes a concern, alternatives might include:
- memory-mapped files
- Apache Arrow / Plasma-like object formats
- custom binary layouts
- explicit JSON/ZIP caching with process-local memoization

---

## Summary

This folder provides a lightweight shared-memory bridge for annotated sumo history data. One process loads the canonical history archive from disk, pickles it, and publishes it as a named shared memory segment. Other processes attach to that segment and reconstruct the same Python `History` object locally, reducing repeated startup cost for tools that need large historical datasets.
