# The Tracker: Conceptual Model and Responsibilities

## 1. Purpose

The tracker exists to **maintain a current, authoritative sumo data store**.

It is not fundamentally:

* a scheduler
* a background service
* a cache
* a website generator

Those may exist around it, but they do not define it.

---

## 2. The Maintained Data Store

The tracker maintains a **single logical data store**.

This store is:

* **canonical** — the source of truth
* **complete** — contains all required historical data
* **internally consistent** — never partially updated

At present, the canonical content is:

* `History`

---

## 3. Representations of the Data Store

The data store may exist in multiple **representations**.

These are not separate stores.
They are different forms of the same underlying content.

### Current representations

* **Durable representation**

  * zip file containing serialized `History`

* **Runtime representation**

  * in-memory `History` (plus auxiliaries)

These must always correspond to the same logical state.

---

## 4. Auxiliaries

Auxiliaries are **derived data structures maintained alongside `History`**.

They exist to support efficient access or common operations.

### Properties of auxiliaries

* fully derivable from `History`
* not independent sources of truth
* maintained as part of the system
* optional but first-class once included

### Examples

* per-rikishi timelines
* indices
* cached aggregates

---

## 5. What the Tracker Actually Does

The tracker’s job is to:

### 5.1 Detect when an update is required

Using:

* current date
* basho schedule
* configuration parameters 

### 5.2 Perform a full update cycle

This consists of:

1. **Load current state**

   * from durable representation (if present)

2. **Determine missing or incomplete basho**

3. **Parse and construct new data**

   * using the parsing pipeline (e.g. `parse_bashostate`) 

4. **Update `History`**

5. **Recompute auxiliaries (if any)**

6. **Publish the new state atomically**

   * write new zip
   * replace old version

7. **Record success**

   * e.g. via ledger 

---

## 6. System Components (Operational, Not Defining)

The tracker may include supporting components, but these are **implementation details**, not defining features.

### Time sources

* real-time clock
* simulated clock (for testing) 

### Scheduler loop

* periodic polling based on configuration 

### State reflection

* tray or console output 

### Alerting

* fatal condition notification 

These support the system but are not its purpose.

---

## 7. What the Tracker Does *Not* Do

The tracker does **not**:

* generate websites
* produce reports
* run forecasts
* serve APIs
* act as a general-purpose data service

Those are **tools**, and they sit outside the tracker.

---

## 8. Tools and Consumers

External tools:

* read the durable representation (zip)
* or attach to runtime state (if exposed)

They may:

* transform data
* present data
* analyze data

But they do not participate in maintaining the store.

---

## 9. Correctness Guarantees

The tracker must ensure:

### 9.1 Atomic updates

A run either:

* fully succeeds and publishes a new valid state
* or fails and leaves the previous state untouched

### 9.2 No partial visibility

At no point should consumers see:

* partially written zip files
* inconsistent auxiliaries
* mismatched representations

### 9.3 Idempotent daily operation

If a run has already succeeded for a given date:

* it must not repeat unnecessarily
* ledger enforces this 

---

## 10. Design Principles

### 10.1 The primary responsibility is to maintain the sumo data store

Everything else is secondary.

---

### 10.2 Canonical state is distinct from its representations

Zip file and in-memory state are representations, not separate stores.

---

### 10.3 History is canonical; auxiliaries are derived

All auxiliary data must come from `History`.

---

### 10.4 Only broadly reusable derived data belongs in the store

If it’s tool-specific, it doesn’t belong here.

---

### 10.5 Tools are separate from store maintenance

They consume the store but do not define or maintain it.

---

### 10.6 Avoid misleading architectural terms

Do not imply:

* cache
* service
* daemon

unless those are intentional design commitments.

---

### 10.7 Responsibilities must remain cleanly separated

* Store maintenance = tracker
* Data usage = tools

---

### 10.8 Valid states only

The system moves only between fully valid states.

---

### 10.9 Growth happens by promotion, not leakage

New derived data starts outside the system and is promoted only if justified.

---

### 10.10 Conceptual model over implementation

The architecture should remain stable even if the code changes.

---

## 11. Summary

The tracker is best understood as:

> A system that maintains a canonical, complete, and correct sumo data store,
> publishes it in stable representations, and optionally maintains derived auxiliaries —
> while remaining strictly separate from the tools that consume that data.

# Codebase Mapping: Concept → Implementation

This ties each part of the model to the files you uploaded.

---

## 1. Canonical Data Store → `History` pipeline

### Concept

The system maintains a single canonical store: **`History`**

### Implementation

* Entry point:

  * `parse_and_save_history()` 

* Core flow:

  * `parse_range(...)` builds a `History`
  * `parse_bashostate(date)` produces one `BashoState`
  * `tidy_up(...)` assembles final objects

👉 This is the **heart of the system**:

* everything else exists to support this pipeline

---

## 2. Parsing Pipeline → Data Construction

### Concept

Build new canonical data from raw inputs.

### Implementation layers

#### Margin (expected structure)

* `get_margin_data()` 
  → produces sorted `(RikId, Chii)`

#### Body (HTML → structured tables)

* `parse_body()` 
  → returns `BanzukeTables`

* `BanzukeTables`, `BodyTable`, `TableType` 

#### Adapter (critical boundary)

* `adapt_body_data_for_fsm()` 

👉 This is a **key architectural seam**:

* converts legacy flat structures → structured FSM input

#### FSM validation layer

* `parse_and_validate_body(...)` 

👉 This is where:

* correctness is enforced
* inconsistencies are resolved

---

## 3. Daily Results Integration

### Concept

Augment canonical state with per-day results.

### Implementation

* `_parse_daily_results(...)` 

* Bridging adapter:

  * `adapt_banzuke_for_daily_parser()` 

👉 Important insight:

* this is an intentional **compatibility layer**
* preserves trusted legacy logic without rewriting it

---

## 4. Final Assembly → Canonical Object

### Concept

Produce a fully valid `BashoState`.

### Implementation

* `tidy_up(...)` 

Key properties:

* preserves `Chii` objects (no downgrade)
* constructs:

  * `Banzuke`
  * `Summary`
  * `BashoState`

👉 This is the **“commit point” for a single basho**

---

## 5. Durable Representation (Publishing)

### Concept

Persist the canonical store safely.

### Implementation

* `save_history_with_annotations(...)` (called from `parse_and_save_history`) 

* Output:

  * zip file under `files/output/Historys`

👉 This corresponds exactly to:

> “publish the maintained data store”

---

## 6. Update Cycle (Tracker Layer)

### Concept

Decide *when* to run the pipeline.

### Implementation pieces

#### Configuration

* `TrackerConfig` 

Defines:

* trigger hour
* polling interval
* basho window

#### Clock abstraction

* `RealClock`, `ScaledClock` 

👉 Clean separation:

* real time vs simulated time

#### Ledger (idempotency)

* `InMemoryLedger` 

Tracks:

* which dates already succeeded

---

## 7. Runtime Feedback (Non-essential)

These **do not define the system**, but support it.

### Tray / state display

* `set_tray_state(...)` 

### Alerts

* `alert_fatal(...)` 

### Logging

* `WarningLogger`

## 8. Key Architectural Boundaries

This is the most important part of the mapping.

### 8.1 Parsing vs Validation

* parsing = extract structure
* FSM = enforce correctness

👉 Clean separation already exists

---

### 8.2 Canonical vs Legacy Compatibility

Adapters:

* `adapt_body_data_for_fsm` 
* `adapt_banzuke_for_daily_parser` 

👉 These isolate:

* legacy assumptions
* modern model

This is **excellent architecture** — keep this boundary.

---

### 8.3 Construction vs Publication

* build in memory (`History`)
* then publish (zip)

👉 This enables:

* atomic updates
* correctness guarantees

---

### 8.4 Core vs Operational Concerns

Core:

* parser
* FSM
* History

Operational:

* clocks
* scheduling
* tray
* alerts

👉 Already mostly separated — good.
