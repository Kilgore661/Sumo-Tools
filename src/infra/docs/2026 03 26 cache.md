## Cache lifecycle mini-spec

### Purpose

The cache lifecycle stage is responsible for ensuring that a usable cache is running for the current canonical history.

Its job is not to decide whether source data is complete, not to rebuild canonical history, and not to perform analysis. Its job is:

> given the current update-cycle branch and the current canonical history, ensure that a running cache exists in the correct lifecycle state for downstream analysis.

In the present design, the important question is not “is there some daemon?” but simply whether the cache process that publishes shared memory is running when needed, and whether it has been restarted when the source dataset changed. That follows from the current cache design and the known stale-cache issue already identified in the tracker material. 

---

### Role in the system

The cache lifecycle stage sits after canonical publication and before analysis.

Its position depends on the retrieval outcome:

* after `SUCCESS_CHANGED`, cache must be refreshed
* after `SUCCESS_UNCHANGED`, cache need only be present

So cache lifecycle is a **runtime publication** stage, not a persistence stage and not an analysis stage.

---

### Inputs

Cache lifecycle requires:

#### 1. Retrieval change signal

It must know whether the managed source dataset changed this cycle.

Conceptually this is:

* `dataset_changed = True` after retrieval success changed
* `dataset_changed = False` after retrieval success unchanged

#### 2. Current canonical history artifact

It must know which canonical published history to start the cache from.

In current terms, this is the canonical zip artifact.

#### 3. Ability to observe cache liveness

It must be able to determine whether a cache publisher is already running.

#### 4. Ability to stop and start cache

It must be able to stop an existing cache publisher and start a new one.

---

### Core rule

The central rule is:

> cache lifecycle is driven by source-dataset change, not by zip comparison.

So cache policy is:

* if source dataset changed, restart cache from current canonical history
* if source dataset did not change and no cache is running, start cache
* if source dataset did not change and cache is already running, leave it alone

That is the rule you settled earlier, and it is the simplest one that solves the stale-cache problem without introducing unnecessary inference.

---

### Success condition

Cache lifecycle succeeds if, after it completes:

* a cache publisher is running
* it is the correct cache instance for the current cycle’s policy

In the present design, that means:

* after `dataset_changed = True`, the running cache must be the freshly started one
* after `dataset_changed = False`, any already-running cache may be reused, otherwise one must be started

The stage fails if it cannot establish that postcondition.

---

### Operational behaviour

#### Case 1: dataset changed

If the source dataset changed this cycle, then previously running cache must not be reused.

Operationally:

1. observe whether a cache publisher is currently running
2. if one is running, stop it
3. start a new cache publisher from the current canonical history
4. confirm that the new cache publisher is running

If any mandatory step fails, return failure.

This branch exists specifically to avoid analysis attaching to stale cache after a source change.

---

#### Case 2: dataset unchanged

If the source dataset did not change this cycle, then cache restart is not required.

Operationally:

1. observe whether a cache publisher is currently running
2. if one is already running, do nothing further
3. if none is running, start a cache publisher from the current canonical history
4. confirm that the cache publisher is now running

If startup is needed and fails, return failure.

---

### What “running” means

For the present system, “running” should be interpreted narrowly and pragmatically:

> the cache publisher process that owns the shared-memory publication is alive.

You explicitly said daemons/services are far downstream, and the current cache design is a foreground publisher process rather than a service. So the lifecycle contract should stay simple and tied to the present implementation model.

It does **not** need to solve future concerns such as deep health checks, stale version metadata, or long-lived service supervision.

---

### What cache lifecycle does **not** decide

Cache lifecycle does not decide:

* whether retrieval succeeded
* whether canonical history should be rebuilt
* whether canonical publication is required
* whether analysis should run
* whether derived artifacts are satisfactory

Those are upstream or downstream concerns.

Its only question is:

> given this cycle’s branch, what cache action is required to satisfy the cache precondition for analysis?

---

### Failure semantics

Cache lifecycle returns failure if it cannot establish the required postcondition.

Examples include:

* an existing cache publisher was supposed to stop but did not
* a new cache publisher could not be started
* startup returned but the cache process is not actually alive
* the stage cannot determine whether cache is running

The key point is that failure is judged by the postcondition:

> after the lifecycle step, is there a running cache in the required state?

If not, the stage fails.

---

### Idempotence

The unchanged branch should be idempotent.

If the source dataset is unchanged and a cache publisher is already running, repeated calls should perform no additional lifecycle action and still succeed.

The changed branch is intentionally not reuse-idempotent in the same way, because its contract is to force refresh. Repeating it may stop and restart cache again, which is acceptable for that branch.

---

### Relationship to analysis

Analysis requires cache, but cache lifecycle does not know what analysis does.

Its only responsibility to analysis is to establish the precondition:

> before analysis runs, there is a running cache corresponding to the current cycle’s canonical history policy.

That is enough separation of concerns.

---

### Non-responsibilities

Cache lifecycle does not:

* compare canonical zip versions
* inspect source records
* verify derived artifact existence
* validate analysis outputs
* act as a general service manager
* enforce future daemon/health-check semantics

Those may come later, but they are outside the present design.

---

### Recommended result shape

Conceptually, cache lifecycle can return a simple success/failure result.

If you want richer detail for logging or debugging, useful secondary information might be:

* whether cache was already running
* whether cache was stopped
* whether cache was started
* whether this cycle performed a refresh or only an ensure-running action

But the essential contract is still binary:

* **success**
* **failure**

because the update-cycle policy already knows which branch it is in.

---

### Invariants after return

After successful cache lifecycle:

* a cache publisher is running

Additionally:

* if the source dataset changed this cycle, the running cache is the freshly started one for the current canonical history
* if the source dataset did not change this cycle, the running cache is either the existing reused one or a newly started one

Those are the postconditions downstream analysis relies on.

---

### Short operational summary

Cache lifecycle should behave like this:

* if source data changed:

  * stop any running cache
  * start a new cache from the current canonical history
  * confirm it is running
* if source data did not change:

  * if cache is already running, leave it alone
  * otherwise start it
  * confirm it is running

That is the exact contract `update_cycle` needs.

The next natural one is the **analysis stage contract**, because that is where “mandatory derived artifacts” becomes concrete.
