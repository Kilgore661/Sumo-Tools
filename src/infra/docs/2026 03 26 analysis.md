Here is a **clean, minimal, and final-form analysis mini-spec**, aligned with everything we’ve now settled — especially:

* artifacts are **mandatory**
* validation is **existence-only**
* analysis is **generation**, not validation
* control logic lives in `update_cycle`, not here

---

# Analysis stage mini-spec

## 1. Purpose

The analysis stage is responsible for generating the required derived artifacts from the current published history.

Its role is:

> given a running cache and a set of required derived artifacts, produce those artifacts.

It does not verify them, and it does not decide whether they are needed. It simply attempts to generate them.

---

## 2. Role in the system

The analysis stage sits after cache lifecycle and before derived-artifact validation.

It assumes:

* required source data is complete
* canonical history is current
* cache is running

It guarantees only that:

* generation of required artifacts has been attempted

The tracker determines whether analysis should run; analysis does not decide this itself.

---

## 3. Inputs

The analysis stage requires:

### 3.1 Running cache

Analysis reads from the cache, which represents the current canonical history.

It does not read raw HTML or interact with the parser directly.

### 3.2 Required derived-artifact set

A complete set of artifacts that must exist after the cycle.

Each artifact must define:

* a unique identifier
* its expected managed output path

Optional parameters (e.g. basho identifier such as `2026/03`) are part of the artifact definition.

---

## 4. Outputs

The analysis stage returns a binary result:

* **success**
* **failure**

This result reflects whether the stage completed its generation attempts without error.

It does **not** guarantee that all required artifacts exist. That is the responsibility of validation.

---

## 5. Core rule

The defining rule of analysis is:

> analysis attempts to generate required artifacts; it does not prove that they exist or are valid.

---

## 6. Operational behaviour

Conceptually, analysis performs:

1. connect to the running cache
2. iterate over the required derived-artifact set
3. for each artifact:

   * execute the corresponding generation logic
   * write the artifact to its expected managed path
4. return success if all generation steps complete without error
5. return failure if any generation step fails

The internal structure (single function, multiple jobs, subprocesses, etc.) is not part of the contract.

---

## 7. When analysis runs

Analysis is invoked by `update_cycle` under two conditions:

### 7.1 Source dataset changed

Analysis must run.

Reason:

* canonical history has been rebuilt
* cache has been refreshed
* derived artifacts must be regenerated

### 7.2 Source dataset unchanged

Analysis runs only if required derived artifacts are missing.

Reason:

* artifacts are mandatory
* absence must be repaired even if source data did not change

---

## 8. Success semantics

Analysis returns **success** if:

* all required generation steps completed without error

Analysis returns **failure** if:

* any required generation step fails

Note:

* success does not imply artifact completeness
* failure does not specify which artifact failed (though implementations may log this)

---

## 9. Failure semantics

Analysis fails if it cannot complete its generation work.

Examples:

* cannot connect to cache
* generation logic raises an error
* output cannot be written
* required job cannot run

Failure is judged by inability to complete generation, not by artifact inspection.

---

## 10. Relationship to validation

Analysis and validation are separate stages.

* **analysis**: attempts to create artifacts
* **validation**: checks that required artifacts exist

Tracker success requires both:

* analysis succeeds
* validation confirms artifact existence

---

## 11. Idempotence

Analysis should be safe to rerun for the same input state.

That is:

> running analysis multiple times for the same canonical history should not corrupt or invalidate the managed artifact set.

Artifacts may be overwritten.

---

## 12. Non-responsibilities

Analysis does not:

* determine whether it should run
* validate artifact existence
* inspect source files
* rebuild canonical history
* manage cache lifecycle
* enforce tracker policy

It is a pure generation stage.

---

## 13. Invariants after return

After analysis returns:

* generation has been attempted for all required artifacts

No stronger guarantee is made.

Artifact existence is established only by the validation stage.

---

## 14. Short summary

Analysis does this:

* read from cache
* generate required artifacts
* write them to their expected locations
* report success or failure

It does not decide policy and does not validate results.

---

This is intentionally tight and minimal. It gives you:

* a stable interface
* no premature complexity
* full alignment with your “existence = validity” rule
