# **Sumo Tools — System Design (Draft v0)**

## **1. Vision**

The long-term goal is to build a **library of tools for analysing sumo data**, structured in layers:

```text
raw data → canonical model → shared memory → tools
```

Where:

* **Raw data** = scraped HTML and related files
* **Canonical model** = validated, structured representation of sumo history
* **Shared memory** = fast access layer for tools
* **Tools** = analysis, reporting, visualisation, etc.

At present, only parts of this exist:

* a working **shared memory layer**
* a developing **canonical model (`sumo_core`)**
* an **old scraper/parser pipeline**
* and a **tracker** that orchestrates execution

The immediate task is to **redefine the tracker and parser so they correctly feed the canonical model layer**.

---

## **2. Current Repository Context**

Relevant structure:

```text
src/
    infra/
        memory/        # working shared memory system
        parser/        # early parsing infrastructure
        persistence/   # serialisation (zip writing)
    sumo_core/         # canonical model (target)
files/output/...       # canonical zip(s)
```

The only currently “live” pipeline is:

```text
shared_memory_start → loads canonical zip
shared_memory_connect → tools read from memory
```

So the missing piece is:

> **how the canonical zip is created and kept up to date**

That is the responsibility of the **tracker + parser**.

---

## **3. High-Level Architecture**

### **3.1 Data Flow**

```text
[Tracker]
    ↓
[Scraper] → raw HTML files
    ↓
[Parser / Canonical Builder]
    ↓
[Timestamped canonical zip]
    ↓
[Shared Memory Loader] (separate tool)
    ↓
[Tools]
```

### **Key principle**

The tracker is responsible for producing:

> **a valid, canonical, timestamped snapshot of sumo history**

It is **not responsible** for:

* shared memory
* analysis tools
* downstream consumers

---

## **4. Design Principles**

### **4.1 Monotone canonical data**

* Accepted (parsed) data only moves forward
* Invalid or provisional raw data may be discarded

### **4.2 Time-driven orchestration**

* The system is driven by **when data should exist**
* Not by inspecting the filesystem during normal operation

### **4.3 Separation of concerns**

| Component   | Responsibility                   |
| ----------- | -------------------------------- |
| Tracker     | when to run                      |
| Scraper     | fetch raw data                   |
| Parser      | validate + build canonical model |
| Persistence | write canonical zip              |
| Memory      | load into shared memory          |
| Tools       | consume                          |

### **4.4 Fail fast on logic errors**

* Parser or model errors are **fatal**
* Scraping failures are **recoverable**

---

## **5. The Tracker (v1 Target)**

## **5.1 Purpose**

A long-running tray application that:

* monitors time/date
* determines when new data may exist
* triggers scraping and parsing
* ensures a canonical zip is produced when possible

---

## **5.2 Non-goals (explicitly deferred)**

* Not a Windows service
* No auto-start on boot
* No repo integrity audit
* No recovery from silent crashes
* No management of shared memory
* No analysis pipeline

These are future concerns.

---

## **5.3 State Model**

The tracker is always in one of:

* **DORMANT** — outside basho window
* **READY** — within window, waiting
* **ACTIVE** — running pipeline

This matches the existing, proven tracker model.

---

## **5.4 Scheduling**

* Uses basho calendar logic (unchanged)

* Trigger condition:

  * within basho/pre-basho window
  * past trigger hour
  * not yet executed today

* Polling interval: ~60 seconds

---

## **5.5 Execution Pipeline**

```text
scrape → parse → write canonical zip
```

---

## **5.6 Step 1 — Scrape**

### Responsibility

* Download relevant files only

### Characteristics

* No historical reasoning
* No gap detection
* No parsing

### Failure behavior

* log failure
* return to READY
* retry on next cycle

---

## **5.7 Step 2 — Parse / Build Canonical Model**

### Responsibility

* Validate raw files
* Construct canonical model (`sumo_core`)
* Write timestamped zip

### Output

* A new file such as:

```text
files/output/.../YYYY_MM_DD_HHMMSS.zip
```

### Parser outcomes

| Outcome                     | Action                         |
| --------------------------- | ------------------------------ |
| Valid data                  | write new zip                  |
| Provisional (e.g. torikumi) | delete offending files, no zip |
| Internal failure            | alert + terminate              |

### Notes

* Parsing is **incremental**
* Parser may support CLI options (start/end/date) for development
* Tracker invokes parser in default “update” mode

---

## **5.8 Canonical Output Policy**

* Each successful run produces a **timestamped zip**
* Previous zips are retained (traceability)
* Tools currently consume **latest zip**

---

## **5.9 Step 3 — Publish**

Publishing is simply:

> **successfully writing the canonical zip**

No further action is taken by the tracker.

---

## **5.10 Failure Policy (Critical)**

| Stage                    | Behavior    |
| ------------------------ | ----------- |
| Scrape fails             | retry later |
| Parse provisional        | clean exit  |
| Parse fails (real error) | terminate   |
| Zip write fails          | terminate   |

This replaces the current tracker’s “continue after error” behavior.

---

## **5.11 Execution Loop**

```text
loop:
    update state

    if not ready:
        sleep
        continue

    run scrape
    if fail:
        continue

    run parser
    if provisional:
        continue
    if fail:
        terminate

    ensure zip written

    return to READY
```

---

## **5.12 Known Issue to Fix**

* Tracker must **not rerun the same day after restart**

Current behavior loses this memory; new tracker must persist it.

---

## **6. Shared Memory Layer (Context Only)**

Separate tools:

```text
shared_memory_start
shared_memory_connect
```

* Load canonical zip into memory
* Provide fast access for tools

**Tracker does not interact with this layer.**

---

## **7. Tools (Future Layer)**

Examples:

* analysis scripts
* reporting tools
* website generators

These will:

* consume shared memory
* not interact with tracker directly

This layer is not yet designed.

---

## **8. Open Questions (Deferred)**

* How tools detect new data
* Whether shared memory auto-refreshes
* Repo-wide integrity auditing
* Incremental vs full rebuild tradeoffs
* Retention policy for old zips

---

## **9. Summary**

This design:

* preserves the **working tracker model**
* removes inappropriate responsibilities (analysis)
* promotes parser to **canonical data builder**
* cleanly separates system layers
* prioritises correctness over completeness

It is intentionally **minimal but solid**, forming the foundation for:

> a reproducible, traceable, and extensible sumo data platform
