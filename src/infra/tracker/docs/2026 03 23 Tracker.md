# Tracker (Draft 1.3)

## Purpose

The tracker is responsible for maintaining a canonical `History` that is complete from the epoch (1958/01) through the **last day**.

It determines when updates should occur and orchestrates the update cycle.

The tracker does **not** interpret data, assess correctness of results, or reason about historical completeness beyond time-based expectations.

---

## Core Concept: Last Day

During a basho, results for each day are published at **10:00 UK time**.

Define:

> **Last day (of results)** = the latest day of the current basho for which results should have been published as of the current UK time.

This determines how far the canonical `History` is expected to extend.

---

## Responsibilities

The tracker is responsible for:

* Determining when new results should be available
* Determining the ordered list of requested `BashoDayRef`s - aka `BashoDayRef`s - needed to extend `History` to the last day
* Initiating update cycles
* Coordinating scraper and parser execution
* Maintaining update state
* Retrying failed updates

The tracker is **not** responsible for:

* Parsing or interpreting data
* Validating correctness of results
* Determining which raw artifacts are needed for a requested `BashoDayRef`
* Constructing the canonical model

---

## Update Model

An update cycle attempts to extend the canonical `History` to the current **last day**.

Each cycle consists of:

1. Determine the current last day
2. Determine the ordered list of requested `BashoDayRef`s needed to extend `History` from its last known complete state to the last day
3. Request raw data for those `BashoDayRef`s (scraper)
4. Attempt to construct canonical `History` (parser)
5. If successful, publish the updated canonical state

This model naturally supports:

* normal daily updates
* catch-up after downtime
* recovery of isolated missing days

---

## Contracts

### Tracker Contract

Maintain a canonical `History` that is complete through the last day.

An update cycle succeeds iff:

* a canonical `History` exists, and
* it is total through the last day

---

### Scraper Contract (as used by tracker)

Given an ordered list of requested `BashoDayRef`s:

* obtain the daily results file for each requested `BashoDayRef`
* obtain the current standings file for each `Date` represented in the list

A scrape succeeds iff:

* all requested daily results were obtained, and
* the corresponding current standings files were obtained

Failures are:

* expected
* recoverable
* non-fatal

---

### Parser Contract (as used by tracker)

Given the scraped artifacts:

* construct and validate a canonical `History`

A parse succeeds iff:

* the resulting `History` is valid, and
* it is total through the last day

Otherwise, the update is rejected.

---

## State Model

The tracker operates as a simple state machine:

* **IDLE / READY** — waiting for next update opportunity
* **RUNNING** — performing an update cycle
* **FAILED** — last attempt failed; will retry

Transitions:

* READY → RUNNING when an update is due
* RUNNING → READY on success
* RUNNING → FAILED on failure
* FAILED → READY on retry

---

## Scheduling

The tracker determines when updates should occur based on time.

Key rules:

* Results are expected daily at **10:00 UK time** during a basho
* Updates should occur shortly after this time
* Outside basho periods, updates may be infrequent or unnecessary

The tracker does not inspect data to determine completeness; it relies solely on time.

---

## Failure Handling

Failures may occur due to:

* network issues during scraping
* incomplete or inconsistent raw data
* parser validation failures

Behaviour:

* failures do not corrupt canonical state
* failures are logged
* retries are attempted in subsequent cycles

---

## Invariants

At all times:

* The canonical `History` is valid
* The canonical `History` is total through the last successful last day
* No invalid or partial canonical state is published

---

## Design Principles

* **Time-driven, not data-driven**
  The tracker schedules updates based on expected publication times.

* **Tracker plans, scraper fetches**
  The tracker determines the requested `BashoDayRef`s; the scraper obtains data for those requests.

* **Strict separation of concerns**
  Scraper fetches, parser validates, tracker orchestrates.

* **All-or-nothing updates**
  Partial updates are not accepted.

* **Monotonic progression**
  History advances forward in time; it is not rewritten.

---

## Summary

The tracker ensures that the system maintains a canonical `History` that is:

* valid
* structured
* complete through the last day

It does this by:

* determining when updates should occur
* determining which `BashoDayRef`s must be covered
* invoking scraper and parser
* accepting only fully valid, complete results

The tracker is the orchestrator of the system, not a participant in data interpretation.
