# 04.4 Published Artifact Model

## Status

Draft design document for the `make_site2` Published Artifact Model.

This document defines the semantic model of the deliberately published
analytical object placed in the `PA` position of a `PAPanel`. It refines
`04 Model Design.md` and meets the Public UI Model at the boundary defined by:

```text
PAPanel -> PA . Notes

PA -> <table> | <indexed table> | <chart> | <sectioned table> |
      <prose> | <custom artifact>
```

`PA` always means **Published Artifact**.

This document names semantic concepts. It does not require that every named
concept become a distinct Python class or prescribe concrete HTML/CSS/JavaScript
implementation.

---

## 1. Purpose

The Published Artifact Model states **what analytical object is deliberately
shown to the reader** within a `PAPanel`.

It answers questions including:

- What PA occupies this public Page's PAPanel?
- Which PA terminal form does it use?
- What site-facing analytical inputs does it consume?
- What visible analytical features does it own?
- What labels, columns, groups, traces, sections, links or views have public
  meaning within it?
- Which Notes, caveats or provenance pertain to it or its visible features?
- Which Filter state affects its visible presentation?
- Does it require standard or specialised PA-terminal rendering?

It does not answer where the Page sits in Navigation, how the PublicUI shell is
laid out, where the FilterSection sits relative to the PAPanel, or how static
output is deployed.

---

## 2. Position and Boundary

The Published Artifact Model is resolved alongside the Public UI Model from
planned publication material and producer site-facing inputs.

```text
PublicationPlan + resolved site-facing inputs
  -> PublicUIModel + PublishedArtifactModel
  -> Rendering
```

The boundary is:

```text
Public UI Model:
  represents PublicUI, ContentPanel, FilterSection, PAPanel, PA placement and
  Notes ownership within PG.

Published Artifact Model:
  represents the analytical object occupying PA and the PA-specific visible
  meanings needed to present it.

Rendering Design:
  defines how modelled PA terminal forms and their features become visible
  browser output.
```

A PA may require a specialised renderer for genuine analytical structure. That
specialisation remains within the `PA` position and shall not redefine the
surrounding `PG` structure.

---

## 3. PublishedArtifact

`PublishedArtifact` is the root semantic representation of one deliberately
published analytical object.

Conceptually:

```text
PublishedArtifact
  pa_id
  terminal_form
  public_framing?
  input_references
  filter_relationships?
  visible_feature_model
  note_references_or_definitions?
  provenance?
  consistency_requirements?
  renderer_kind?
```

The Public UI Model places the PA in its PAPanel. The Published Artifact Model
specifies what that PA is and what its visible analytical content means.

A PA is not merely:

- a data file;
- a dataframe dump;
- a chart-library object;
- an HTML fragment;
- an old standalone report;
- a renderer function.

It is the public analytical object those implementation materials may be used to
realise.

---

## 4. PA Terminal Forms

At page-grammar level, a PA occupies one of the following terminal forms:

```text
<table>
<indexed table>
<chart>
<sectioned table>
<prose>
<custom artifact>
```

These terminal forms classify the public analytical presentation sufficiently
for `PG`. The Published Artifact Model may define internal semantic structure
beneath each terminal form where public meaning or auditable rendering requires
it.

A new PA terminal form should be introduced only when a public analytical object
cannot honestly be represented by an existing form and the distinction matters
for public modelling or rendering.

---

## 5. Producer Site-Facing Inputs

A PA shall be constructed from deliberate site-facing analytical material.

Producer modules own analysis-specific computation and meaning. They may supply
site-facing material as, for example:

- Python objects;
- JSON or JSON-like structures;
- CSV or other tabular data;
- chart data/configuration inputs;
- structured prose;
- generated public-facing data files;
- other explicit producer outputs suitable for public modelling.

The important design requirement is not the serialization form. The important
requirement is that promoted PAs receive intentional site-facing inputs rather
than requiring `make_site2` to recover public meaning by parsing legacy rendered
HTML.

Where a producer input contains public facts such as column meaning, visible
feature labels, permitted Filter relationships, Notes, caveats or provenance,
the Published Artifact Model shall preserve those facts for public presentation.

---

## 6. PA Identity and Framing

Each PA shall have a stable `pa_id` within the public-site product or other
scope specified by later implementation design.

A PA may have public framing distinct from the selected Page Heading. For
example, a Page may frame the reader's question while a PA title identifies the
specific view or selected data instance currently displayed.

The model shall distinguish:

```text
Page Heading
  page-level title and summary in ContentPanel

PA framing
  optional title/subtitle or label accompanying the analytical object in
  PAPanel

PA-internal labels
  table headings, section headings, chart axes, trace labels and other labels
  within the terminal form
```

Whether a PA needs visible framing, and how it is rendered, belongs to the PA
model and Rendering Design rather than being inferred from browser headings.

---

## 7. Filter Relationships

Filters are modelled as part of the Public UI Model's `FilterSection`, not as
children of the PA. A PA may nevertheless declare which Filter state it consumes
and what public effect that state has on its visible presentation.

A PA's Filter relationships may express matters including:

- selecting a data instance;
- selecting a division or cohort;
- restricting visible rows;
- selecting a measure;
- exposing or hiding a declared column group;
- selecting a declared representation or view;
- exposing or hiding a visible feature whose Notes relevance changes with it.

The Published Artifact Model shall not treat arbitrary artefact-local
interaction as a Filter. An interaction becomes a Filter relationship when it
is reader-visible state in the public page contract, not merely because an
interactive renderer can change something.

Examples of normally artefact-local interaction include hover behaviour or
ordinary chart zoom. Examples of public Filter relationships include selecting
`Division` or displaying an optional declared `Delta` column group.

---

## 8. Notes, Caveats and Provenance

The Public UI Model represents `Notes` within the `PAPanel`. The Published
Artifact Model supplies the PA-specific explanatory meaning needed to determine
which Notes exist and when they are relevant.

A Note may pertain to:

- the PA as a whole;
- a visible table column or column group;
- a visible chart trace or source;
- a declared PA representation/view;
- a visible feature of a custom artifact;
- a data interpretation caveat;
- public provenance material.

A Note does not belong to a Filter. A Filter may affect Note relevance because
it changes the visible PA or one of its visible features.

A PA may carry provenance such as:

- source data identity or description;
- generation or data-as-of information;
- method or model family information;
- model/version information where publicly meaningful;
- sample/support limitations;
- known limitations;
- producer-owned explanatory information.

Internal diagnostics, filesystem paths and experimental labels shall not become
public provenance merely because they exist in producer output.

The PA model should represent only as much Note targeting and provenance
structure as required by real public cases. A large abstract taxonomy should not
be invented in advance of need.

---

## 9. Table PA

A `<table>` PA is a deliberately published analytical table.

It is not merely a CSV file, a dataframe dump or an HTML `<table>` element.

A table PA may represent, where applicable:

```text
TablePA
  data_source
  public_framing?
  row_identity?
  row_ordering?
  column_model
  column_group_model?
  link_model?
  declared_filter_relationships?
  notes/provenance?
  consistency_requirements?
  renderer_kind?
```

### 9.1 Column Meaning

A table column may have public meaning including:

- identity/name;
- rank or position;
- metric;
- result/record;
- rating;
- status;
- movement/delta;
- orientation/side;
- external link destination.

A column model may specify:

- stable column identity;
- reader-facing heading;
- semantic role;
- value source or value derivation;
- default visibility;
- optional visibility governed by a Filter;
- grouping relationship;
- formatting or link meaning where public interpretation requires it;
- Note/provenance association.

Implementation field names shall not leak into visible headings unless adopted
deliberately as public wording.

### 9.2 Shared Table Treatment versus Table Meaning

The PA model owns table-specific visible meaning: for example, that a column is
movement direction or that a numeric column is optional under a Filter.

Shared visual treatments such as cell padding, row striping, alignment defaults
or density policy belong in Rendering Design for the `<table>` PA terminal,
unless a particular visible treatment itself conveys PA-specific meaning.

### 9.3 Table Sorting Semantics

Ordinary table sorting is expected table PA behaviour. A row-number column is a
reference column, not a data column: it is not sortable and is renumbered
`1..n` after filtering and sorting.

Every other ordinary table data column is sortable by default unless the column
model explicitly declares it unsortable. A sortable column has:

- a display value;
- a sort value;
- a sort kind; and
- a default sort direction.

Column-specific sort configuration takes precedence over sort-kind defaults.
Where no column-specific direction is declared, default directions are:

```text
numeric/count/rate/performance values
  descending

text values
  ascending

Chii/rank ordinal values
  ascending by ordinal, where lower ordinal means higher Chii
```

Chii sorting uses emitted integer ordinals only. Runtime code shall not parse or
infer ordinals from display strings such as `Y1e`. A producer that emits a
sortable Chii display value must also emit the corresponding ordinal sort value;
missing ordinal data is an input validation failure.

Result or record strings such as `11-4 JS` sort by the integer wins value before
the first hyphen. Producers may emit an explicit result/wins sort value, but the
runtime may also parse this compact display form because the rule is simple and
stable. Missing or unparsable result values sort last.

Clicking a sortable column heading sorts by that column. Clicking the active
sort heading toggles direction. The active sort heading shall display a trailing
up/down indicator and expose the equivalent sort state accessibly.

## 10. Indexed Table PA

An `<indexed table>` PA is a table presentation whose visible data is selected
from a declared indexed set of data instances.

It is appropriate where the public analytical object is a table browser over a
partitioned or indexed universe, such as per-basho or per-division results.

Conceptually:

```text
IndexedTablePA
  index_source
  selected_instance_relationship
  payload_source_relationship
  default_instance?
  table_column_model
  declared_filter_relationships?
  notes/provenance?
  consistency_requirements?
  renderer_kind?
```

The PA model owns how a selected public data-instance value identifies the
visible table payload. The Public UI Model owns the FilterItem through which a
reader selects that value where it is a public Filter.

---

## 11. Chart PA

A `<chart>` PA is a deliberately published analytical chart.

It is not merely a Plotly specification, an image or a generated HTML fragment.
A plotting library is a rendering mechanism, not the semantic model.

Conceptually:

```text
ChartPA
  data_sources
  series_or_trace_model
  axis_semantics
  category/order_semantics?
  declared_filter_relationships?
  default_visible_series_or_view?
  annotation/uncertainty/support_meaning?
  notes/provenance?
  consistency_requirements?
  renderer_kind?
```

Chart PA meaning may include:

- series/trace labels;
- axis meanings and public labels;
- comparison categories;
- uncertainty or support interpretation;
- source selection;
- expected public default view;
- Note relevance associated with a visible series/source.

Chart presentation decisions such as typography, colour palettes, sizing or
legend layout belong to Rendering Design except where a presentation feature
has declared analytical meaning.

---

## 12. Sectioned Table PA

A `<sectioned table>` PA is a table-like analytical presentation naturally
composed of named sections or related subtables.

Conceptually:

```text
SectionedTablePA
  section_model+
  shared_column_model?
  local_column_models?
  declared_filter_relationships?
  notes/provenance?
  consistency_requirements?
  renderer_kind?

Section
  section_id
  public_label
  data_source_or_selection
  local_notes?
```

A section label is PA-internal framing unless deliberately elevated into Page or
PA framing. The surrounding `PAPanel` remains owned by the Public UI Model.

Shared visual table treatment should normally apply across table and sectioned
-table PA terminals unless a documented semantic difference requires an
exception.

---

## 13. Prose PA

A `<prose>` PA is deliberately published explanatory or narrative analytical
material occupying the PA position.

It may contain:

- methodology;
- glossary or explanatory material;
- research narrative;
- interpretive caveats;
- public-facing supporting argument;
- inline structured material where deliberately part of the prose PA.

A prose PA is not a general escape hatch for arbitrary copied HTML or for a
page-specific shell. Page Heading, FilterSection, PAPanel and Notes ownership
remain governed by `PG` and the Public UI Model.

---

## 14. Custom Artifact PA

A `<custom artifact>` PA represents a genuine analytical presentation whose
internal public meaning cannot honestly be represented by table, indexed table,
chart, sectioned table or prose terminal forms.

Custom artifact PAs are allowed where justified by real domain structure. They
shall not be used merely to avoid modelling ordinary public-page or table/chart
structure.

Conceptually:

```text
CustomArtifactPA
  pa_id
  custom_kind
  declared_visible_feature_model
  data/input_relationships
  declared_filter_relationships?
  notes/provenance?
  consistency_requirements?
  renderer_kind
```

A custom PA renderer may own specialised PA internals. It shall not own:

- PublicUI shell structure;
- NavigationBar or Navigation;
- ContentPanel or Heading;
- FilterSection/PAPanel relationship;
- Notes placement outside the PA's PAPanel;
- public selection/deep-link conventions.

### 14.1 Banzuke Changes Example

Banzuke Changes is a reasonable custom-artifact pressure case because its
banzuke-shaped display has genuine domain structure rather than being an
ordinary generic table alone.

A Banzuke Changes PA may own facts such as:

- East/West banzuke-style presentation;
- scan-style alternative representation where declared as Filter state;
- rank-position display;
- movement-direction display distinct from numeric movement magnitude;
- declared optional context, delta or rating features;
- Notes associated with visible movement/result features.

For example, the fact that movement direction is visible separately from an
optional numeric movement magnitude is PA-specific visible meaning. Its exact
layout and styling are rendered within the custom PA terminal under Rendering
Design; it is not a page-shell decision.

---

## 15. Links and Domain Behaviour

A PA may contain links with public analytical or domain meaning, such as links
from a rikishi name to a public external rikishi record or links to related
public pages.

The PA model should represent link meaning where consistency or public
interpretation depends on it. Shared domain-link behaviour should not be
reimplemented inconsistently across unrelated PA renderers.

The model need not represent incidental browser link styling unless that styling
carries intended public meaning; such treatment generally belongs to Rendering
Design.

---

## 16. PA-Local Interaction

Some interactivity belongs within a PA without becoming a page-level Filter.

Examples may include:

- ordinary table sorting;
- chart hover behaviour;
- chart zoom or pan;
- legend interaction not promoted to public state;
- row disclosure local to an artefact;
- local explanatory affordances.

A PA-local interaction becomes a Filter relationship only when it is a
deliberate reader-visible control over material public analytical presentation
within the page contract.

Material public state should be identifiable for stable link restoration where
required. Transient PA-local interaction need not be serializable merely because
it exists in the browser.

---

## 17. Renderer Kind and Runtime Requirements

A PA may identify the renderer kind required to realise its terminal form and
visible features.

Examples may include:

```text
basic_table
indexed_table
plotly_chart
sectioned_table
prose_renderer
banzuke_changes
```

Renderer kind identifies PA-internal realisation requirements. It does not
assign page-shell ownership to the PA.

A PA may imply runtime support requirements. Those requirements shall be known
through publication planning before rendering/output writing completes; a PA
renderer shall not create undisclosed runtime dependencies as a side effect of
rendering.

---

## 18. Consistency and Validation

A valid Published Artifact Model shall be internally coherent and compatible
with its planned public Page and Public UI placement.

Expected consistency rules include, as applicable:

1. The PA has a stable identity and an approved terminal form.
2. Required site-facing input/data references are present and resolve under the
   Publication Plan.
3. Visible feature declarations refer to features available in the PA model.
4. Table Notes referring to columns or groups refer to declared visible
   features.
5. Chart Notes referring to traces, sources or representations refer to
   declared visible features.
6. Filter relationships refer to supported Filters in the associated public UI
   or to deliberately specified PA-local public state.
7. Default-visible and optional feature relationships are consistent.
8. A renderer kind capable of realising the PA terminal form is available.
9. A custom PA does not require redefinition of surrounding `PG` structure.
10. Public labels and provenance are deliberate rather than accidental leaks of
    producer implementation detail.

An incoherent Published Artifact Model is a modelling or input-resolution error.
It shall not be repaired by the renderer through guesses or silent omissions.

---

## 19. What the Published Artifact Model Does Not Own

The Published Artifact Model does not own:

- site identity;
- Navigation hierarchy or visible numbering;
- selected Page Heading;
- NavigationBar/Hider behaviour;
- the Contents relationship between FilterSection and PAPanel;
- Notes placement outside the PAPanel relationship;
- public Page inclusion decisions or status policy;
- final public-selection/deep-link syntax;
- shared shell layout;
- generic colour, spacing or typography policy;
- static output writing;
- deployment.

If a PA implementation needs to make those decisions privately, either the PA
boundary has been crossed or the public/model/rendering design is incomplete.

---

## 20. Relationship to Rendering Design

Rendering Design shall define how PA terminal forms and declared PA features are
made visible.

The model provides ownership and meaning; Rendering Design supplies chosen
shared or PA-specific presentation rules where those are not uniquely implied by
meaning.

Examples:

| Modelled fact | Rendering Design concern |
| --- | --- |
| This PA is a table with declared columns. | Shared table container, typography, alignment, padding and row treatment. |
| This column is a shikona link column. | Link/column alignment and interaction presentation. |
| Movement direction is a distinct visible Banzuke Changes feature. | Direction-column placement and glyph rendering. |
| Notes pertain to the displayed PA/features. | Notes display treatment within PAPanel. |
| A Chart PA contains declared series and axes. | Chart library realisation, size, palette and label treatment. |

This separation permits informed visual decisions without treating implementation
convenience as analytical meaning.

---

## 21. Relationship to Legacy Evidence

Legacy pages, older code and archived documentation may provide evidence about:

- PA types already required by real public material;
- meaningful visible features that should not be lost during migration;
- Notes and provenance needs;
- domain-link behaviour;
- specialised artefact pressures;
- rendering regressions that reveal missing PA meaning.

Such evidence must be evaluated against current Requirements, Specification and
Model Design. It does not become a PA contract merely because it appeared in a
former implementation.

---

## 22. Deferred Questions

The following matters are deliberately deferred until real implementation or
promotion pressure requires them:

- exact Python or serialized representation of PA models;
- exact site-facing input interchange formats;
- complete table column/group metadata vocabulary;
- complete chart series/axis metadata vocabulary;
- precise Note-target and Note-relevance representation;
- whether every PA renderer kind must be registered explicitly;
- how public provenance is displayed across PA forms;
- whether new PA terminal forms are required beyond the initial set;
- which PA-local interactions become declared public state.

Deferred questions shall not be resolved implicitly by local renderer code where
they affect public meaning or model boundaries.

---

## 23. Summary

The Published Artifact Model represents the deliberately published analytical
object placed in the `PA` position of a `PAPanel`.

It says:

```text
what PA is being published
which PA terminal form it uses
what public analytical inputs and features it owns
what Filter relationships affect its visible presentation
what Notes, caveats and provenance pertain to it
what specialised internal rendering it may require
```

It does not say:

```text
how the public page shell is structured
where NavigationBar or ContentPanel appear
where Filters sit relative to PAPanel
how shared rendering styles the public site
how output is written or deployed
```

This boundary allows rich analytical presentation, including specialised public
artefacts, while preserving one coherent modelled public page structure governed
by `PG`.
