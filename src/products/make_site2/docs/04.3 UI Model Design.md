# 04.3 UI Model Design

## Status

Initial design document for the `make_site2` UI Model.

This document describes the semantic model of the public interface before it is
rendered. It defines the interface structures that sit between the resolved
Publication Plan and the Rendering layer.

This is a design document, not an implementation inventory. Naming a concept
does not imply that the concept must become a Python class.

Rendering details belong to:

```text
05 Rendering Design.md
```

Artifact internals belong to:

```text
04.4 Artifact Model Design.md
```

---

# 1. Purpose

The UI Model defines what the generated public interface is.

It exists because `make_site2` generates a non-trivial public UI. The package
therefore needs an explicit model of that UI before it renders HTML, CSS, or
JavaScript.

The UI Model answers questions such as:

```text
What interface regions exist?
What page is selected?
What is the ContentPanel structure?
What filters are visible?
Is this page a single visible artefact or a selected alternative?
What PA slot is visible?
Where do notes belong?
What owns page heading, branch selection, filters, PA framing, and artifact
placement?
```

The UI Model does not answer:

```text
What HTML tags are emitted?
What CSS classes are used?
What JavaScript modules are loaded?
How table rows are rendered internally?
How Plotly traces are constructed?
How files are written to disk?
How the completed site is deployed?
```

Those are later design concerns.

---

# 2. Position in the Pipeline

The UI Model is the third model layer in the `make_site2` pipeline.

```text
SiteDefinition
  -> PublicationPlan
  -> UIModel
  -> RenderedSite
  -> WrittenOutput
```

The Publication Plan says what this build will publish and at which routes.

The UI Model says what interface structure will be rendered for the planned
site.

The renderer consumes the UI Model.

---

# 3. Core Responsibility

The UI Model owns semantic interface structure.

It owns:

```text
PublicSiteUI
Sidebar
ContentPanel
Heading
Contents
G1 Single Visible Artefact structure
FilterSection
FilterItem
BooleanChoice
SingleFiniteChoice
PA slot
Note ownership
```

It does not own:

```text
producer computation
route derivation
file copying
deployment
HTML tag selection
CSS implementation
JavaScript implementation
table row rendering internals
chart trace construction
artifact-specific layout internals
```

A useful rule:

```text
If the concept describes the structure of the interface before rendering, it
belongs in the UI Model.

If the concept describes artifact internals, it belongs in the Artifact Model.

If the concept describes HTML/CSS/JS realization, it belongs in Rendering.
```

---

# 4. UIModelResolver

The `UIModelResolver` consumes a Publication Plan and produces the UI Model.

Conceptually:

```python
def make_ui_model(
    publication_plan: PublicationPlan,
) -> UIModel:
    ...
```

The resolver converts planned pages into interface structures.

For each included planned page, it determines:

```text
Heading
Contents grammar
FilterSection, if any
visible PA slot structure
Note ownership
artifact reference or artifact model handoff
```

The resolver does not render.

It does not write HTML.

It does not decide route paths; those are already known from the Publication
Plan.

---

# 5. Overall UI Shape

The generated public UI has the conceptual shape:

```text
PublicSiteUI
  Sidebar
  PageUIModel*
```

Each page UI model has:

```text
PageUIModel
  Route
  Status
  ContentPanel
```

The standard visible public UI is:

```text
PublicUI
  Sidebar
  ContentPanel
```

The Sidebar provides site-shell structure.

The ContentPanel provides selected-page structure.

---

# 6. Sidebar

The Sidebar is part of the UI Model because it is part of the generated public
interface.

Conceptually:

```text
Sidebar
  Caption
  Navigation
  Hider
```

The Sidebar owns:

```text
site identity display
navigation display structure
sidebar visibility control
```

The Sidebar does not own:

```text
page filters
page contents
PA notes
artifact rendering
```

The Hider is shell state. It is not a Filter.

Filters affect the visible analytical content. The Hider affects the shell.

---

# 7. Navigation in the UI Model

The UI Model consumes planned navigation.

The Publication Plan has already resolved which pages are included and what
routes they have.

The UI Model represents navigation as an interface structure:

```text
Navigation
  navigation nodes
  active page state
  clickable page links
  non-clickable grouping nodes
  quick links, if present
```

The UI Model does not derive routes.

The UI Model does not decide which pages are included.

It renders planned navigation semantics into interface structure for the
renderer to realize later.

---

# 8. ContentPanel

The ContentPanel is the semantic region where the selected page is presented.

Conceptually:

```text
ContentPanel
  Heading
  Contents
```

The ContentPanel owns:

```text
page-level heading/framing
the selected page's contents
filter placement at content level
branch-selection placement where applicable
PA slot placement
note ownership and placement in the interface model
```

The ContentPanel does not own:

```text
site identity
global navigation
artifact internals
producer computation
route derivation
```

A ContentPanel should not be treated as an undifferentiated container of visual
widgets.

It expresses the page's analytical organization.

---

# 9. Heading

The Heading provides page-level framing.

Conceptually:

```text
Heading
  Head
  SubHead, if present
```

The Heading owns page identity and immediate reader context.

It is distinct from:

```text
site caption
navigation label
PA title/framing
artifact-internal labels
table column headings
chart axis labels
chart trace labels
```

Example distinction:

```text
Navigation label:
  Basho Results

Heading:
  Basho Results Browser

Artifact-internal labels:
  Day, East, West, Kimarite, Record, etc.
```

---

# 10. Contents

`Contents` is the structured public content displayed inside the ContentPanel.

`make_site2` currently supports one implemented content grammar shape:

```text
G1: Single Visible Artefact
```

This name is a design label.

It describes the current structural case used by promoted pages in the public
site.

Richer grammars are possible, especially for nested controls or selected
artifact views, but they are deferred to Appendix A until a real promoted page
requires them.

---

# 11. G1: Single Visible Artefact

G1 describes ordinary pages whose contents expose one visible published artefact,
optionally controlled by filters and accompanied by notes.

Conceptually:

```text
G1Contents
  FilterSection?
  PA
  Note*
```

G1 is the default promoted-page shape.

It covers pages such as:

```text
one table page
one indexed-table page
one chart page
one sectioned-table page
one prose page
one custom-artifact page
```

A G1 page may have no filters.

A G1 page may have notes.

G1 does not mean the artefact is simple. It means the page structure has one
visible PA slot.

The artifact inside that slot may be rich.

---

# 12. Deferred Richer Grammars

G1 is not the only possible content-panel model.

The current model deliberately does not implement nested or hierarchical
filters, choices, or options. This keeps the promoted pages in a flat,
auditable grammar while the real pressure cases remain small.

Known deferred pressures include:

```text
artifact views
view-local controls
controls whose applicability depends on another control
mixed chart/table artifacts
```

For example, Win Probability by Standing has a flat `Source`, `Division`, and
`Error bars` control set. Semantically, `Error bars` applies only to the
observed source, but the current implementation keeps it as a peer control
rather than introducing conditional or nested controls.

Career Length is another pressure case because it contains chart-like and
table-like views.

See:

```text
A Appendix - Better Models.md
```

---

# 13. Filter

`make_site2` uses **Filter**, not **Option**, as the public UI-model term.

A Filter is reader-visible state that restricts, selects, projects, or otherwise
narrows what part of the available analytical view is shown.

A Filter may internally correspond to:

```text
row filtering
column projection
source selection
measure selection
representation selection
branch selection
PA selection
visibility preset selection
```

The public meaning remains:

```text
show this slice or view of the available analytical content
```

A Filter may have:

```text
stable id
label
allowed values
default value
URL-state participation
help text
presentation hint
```

Every Filter has a label.

If a real pressure case needs an intentionally unlabelled Filter, that absence
should be represented explicitly, for example by allowing the label to be null
or empty.

A Filter is not a specific browser widget.

For the current flat G1 grammar, each Filter is one of:

```text
BooleanChoice
SingleFiniteChoice
```

`BooleanChoice` means true/false state and is rendered as a checkbox.

`SingleFiniteChoice` means choosing one value from a finite set. It may be
rendered as a radio button group or dropdown according to rendering policy.

The implementation may continue to use compact names such as `checkbox` and
`select`, provided they are read semantically:

```text
checkbox = BooleanChoice
select = SingleFiniteChoice
```

---

# 14. FilterSection

A FilterSection groups Filters that affect the same contents or branch.

Conceptually:

```text
FilterSection
  FilterItem*

FilterItem
  BooleanChoice | SingleFiniteChoice
```

The UI Model may later allow nested groups if real pages need them:

```text
FilterSection
  Filter
  FilterGroup
```

But the basic model is:

```text
a page or branch has a section of reader-visible filters
```

A FilterSection belongs to the smallest semantic scope that owns the state.

Examples:

```text
G1 page:
  FilterSection affects the visible PA.

Deferred richer grammar:
  branches, view-local controls, or conditional controls may own their own
  FilterSection or equivalent structure.
```

Filters do not own Notes.

Filters may have help text.

---

# 15. Deferred Branch and View Structures

The active UI Model does not define branches or selected-alternative content
structures.

Branch-like or view-like structures remain possible future model elements for
pages where a selected representation changes the visible PA, local controls, or
payload kind.

Those ideas are deferred to Appendix A.

---

# 16. PA Slot in the UI Model

The UI Model treats PA as a visible analytical slot inside Contents or Branch.

At UI Model level, a PA records enough structure to place and frame the visible
analytical object.

Conceptually:

```text
PA
  PAId
  PATitle, if present
  Artifact reference or Artifact model handoff
  Note*
```

The UI Model owns PA placement and PA-level note ownership.

The Artifact Model owns concrete artifact internals.

Thus:

```text
UI Model:
  there is a PA here, with this framing and note ownership

Artifact Model:
  the PA contains an indexed table / chart / sectioned table / prose / custom
  artifact with these artifact-specific contracts
```

---

# 18. Artifact Slot

An Artifact is the concrete analytical object displayed by a PA.

At UI Model level, the artifact is a slot or handoff point.

The UI Model distinguishes artifact placement from artifact internals.

Initial artifact kinds include:

```text
table
indexed_table
chart
sectioned_table
prose
custom_artifact
```

The UI Model does not define:

```text
table rows
table column layout
chart traces
chart axes
prose markup details
custom artifact internals
```

Those belong to `04.4 Artifact Model Design.md`.

---

# 18a. Model-To-Render Invariant

The visual and structural shape of the rendered page must follow the logical
shape of the model.

The renderer must not invent public structure while rendering.

If the UI Model says a FilterSection contains five peer Filters, the rendered
structure should not imply that one filter is a child, subtype, explanation, or
secondary control of another unless the model says so.

The same principle applies to lower-level rendering details:

```text
control grouping
control layout
notes placement
table alignment
spacing
muted or emphasized text
responsive behavior
artifact-local chrome
```

If an unstyled/default rendering looks wrong, the remedy is to add or refine the
model or rendering grammar at the highest appropriate level, not to patch the
local HTML or CSS with an unmodelled exception.

For now, a plain browser default is preferable to bespoke styling that cannot be
traced back to the model.

---

# 19. Notes

Notes are semantic explanatory annotations.

Notes are not table-only.

Notes may explain or qualify any visible analytical content.

A Note may pertain to:

```text
the PA as a whole
a table column
a column group
a table visibility preset
a chart trace
a chart source
a data source
a prose section
a visible artifact feature
a public caveat
a provenance fact
```

Notes belong to PAs or visible artifact features.

Notes do not belong to Filters.

A Filter may affect which Notes are relevant by changing visible content. That
does not make the Note a Filter note.

Examples:

```text
A note about a table column appears when that column is visible.
A note about a chart trace appears when that trace/source is visible.
A note about a PA-level caveat appears whenever that PA is visible.
```

The UI Model records note ownership and relevance.

The renderer decides how relevant notes are visually realized.

---

# 20. URL-State Ownership

The UI Model identifies meaningful public state.

Meaningful state may include:

```text
selected filters
selected branch
selected representation
selected data instance
visible artifact preset
```

The UI Model does not define final URL syntax.

Detailed route/query/hash behavior belongs to rendering/runtime design.

However, the UI Model should make clear which pieces of state are semantically
meaningful and therefore candidates for URL serialization.

---

# 21. Page Status in the UI Model

The Publication Plan carries page status forward.

The UI Model may include page status so that rendering can later display or
apply status-specific treatment.

Examples:

```text
promoted
candidate
research
diagnostic
legacy
superseded
excluded
```

The UI Model does not decide status.

The UI Model carries the planned status into interface structure.

---

# 22. Relationship to Artifact Model

The UI Model and Artifact Model meet at the PA/Artifact boundary.

The UI Model owns:

```text
where the PA appears
what the PA is called
which filters select or modify visible content
which branch is selected
where notes belong
what artifact slot is present
```

The Artifact Model owns:

```text
what artifact kind is displayed
what data it consumes
what renderer kind it requires
what artifact-specific labels, columns, traces, sections, or interactions exist
```

This separation allows custom artifact rendering without custom page rendering.

---

# 23. Relationship to Rendering

The renderer consumes the UI Model.

The renderer owns:

```text
HTML structure
CSS classes
control widgets
responsive layout
runtime initialization
note placement
navigation display
ContentPanel visual realization
```

The renderer does not invent the UI Model.

It realizes the UI Model.

If the renderer needs to know something structural that is absent from the UI
Model, the model is incomplete.

# 26. Deferred Questions

The following questions are deferred:

```text
Whether FilterGroup is needed in the first implementation.
Exact URL-state representation for filters and branch selection.
Exact note relevance representation.
Whether notes need their own target taxonomy immediately.
Exact page-status rendering rules.
Exact UI Model storage format.
Whether UI Model objects are produced as Python objects, JSON-like structures,
or both.
Whether Sidebar hider state is persisted.
```

These should be resolved when they become implementation pressure points.

The UI Model is the semantic model of the public interface before rendering.

It says:

```text
what interface regions exist
what content grammar a page uses
what filters are visible
what branch is selected
what PA slot is present
where notes belong
where artifact rendering begins
```

It does not say:

```text
which HTML tags are used
which CSS classes are used
how table rows render
how chart traces are built
how files are written
how deployment happens
```

The central invariant remains:

```text
No promoted page is rendered until it has first been represented in the UI Model.
