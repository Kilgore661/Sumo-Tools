# 04.2 Publication Plan Model Design

## Status

Initial design document for the `make_site2` Publication Plan Model.

This document describes the resolved build/publication plan. It sits between the
declared Site Model and the UI Model.

This is a design document, not an implementation inventory. Naming a concept
does not imply that the concept must become a Python class.

---

# 1. Purpose

The Publication Plan describes what a particular build will publish.

It answers questions such as:

```text
Which declared pages are included in this build?
Which declared pages are excluded from this build?
What canonical public route does each included page have?
What artifact input, data, asset, and runtime references does each included page need?
What quick links are available, and what canonical routes do they target?
What page status does each planned page carry forward?
```

The Publication Plan is resolved build intent.

It is not the Site Model, not the UI Model, not rendered output, and not a
deployment action.

---

# 2. Position in the Pipeline

The Publication Plan is the second model layer in the `make_site2` pipeline.

```text
SiteDefinition
  -> PublicationPlan
  -> UIModel
  -> RenderedSite
  -> WrittenOutput
```

The Site Model declares public intent.

The Publication Plan resolves that intent for a particular build.

The UI Model later resolves each planned page into a semantic interface
structure.

---

# 3. Core Responsibility

The Publication Plan owns resolved publication structure.

It owns:

```text
included pages
excluded pages, if recorded
canonical page routes
navigation-derived route table
home route
quick-link route targets
status propagation
artifact input references
data references
asset references
runtime requirements
```

It does not own:

```text
ContentPanel structure
G1/G2 grammar selection
FilterSection structure
BranchSelector structure
PA internals
artifact internals
rendered HTML
CSS implementation
JavaScript implementation
filesystem output paths
local or remote deployment execution
```

A useful rule:

```text
If the concept says what this build will publish and where, it belongs in the
Publication Plan.

If the concept says what the page interface structurally is, it belongs in the
UI Model.

If the concept says how files are written, it belongs in the output/build design.

If the concept says where the completed site is copied or uploaded, it belongs
in deployment design.
```

---

# 4. Inputs

The Publication Plan is derived from:

```text
SiteDefinition
BuildConfig
```

Conceptually:

```python
def make_publication_plan(
    site_definition: SiteDefinition,
    build_config: BuildConfig,
) -> PublicationPlan:
    ...
```

The `SiteDefinition` provides declared public intent.

The `BuildConfig` provides operational choices for this build.

---

# 5. BuildConfig

`BuildConfig` represents operational build choices.

It may include:

```text
build mode
included status policy
development versus production mode
output root
cache/version policy
source-data policy, if needed
```

Deployment configuration is related but distinct.

Deployment is a first-class package requirement, but deployment does not belong
inside the Publication Plan itself.

A successful builder is not enough if there is no ordinary way to view the result
locally or publish it remotely. Therefore deployment must be designed and
implemented as part of the package. However:

```text
PublicationPlan:
  what pages/routes/dependencies this build includes

DeploymentConfig / DeploymentPlan:
  where the completed static output is copied or uploaded
```

The distinction is about ownership, not importance.

---

# 6. Included Pages

The Publication Plan determines which pages are included in a particular build.

The decision is based on:

```text
page status
build mode
site definition
explicit build policy
```

For example, a public build may include only promoted pages, while a development
build may include candidate, research, diagnostic, or legacy pages.

The exact status-inclusion policy can evolve, but inclusion must be explicit and
deterministic.

Non-promoted content must not leak into a build merely because it exists.

---

# 7. Excluded Pages

The Publication Plan may record excluded pages.

This is useful when the build needs to know that a page exists but is not part of
the current publication plan.

Examples:

```text
candidate page excluded from public build
diagnostic page excluded from public build
legacy page excluded unless compatibility mode is requested
superseded page excluded by default
```

Excluded pages are not rendered as normal pages.

If an included quick link, route, or promoted page depends on an excluded page,
that is an internal contradiction and should fail immediately.

---

# 8. PlannedPage

A `PlannedPage` is a page after site-definition resolution but before UI-model
resolution.

Conceptually, a PlannedPage contains:

```text
PageId
PageDefinition
Status
CanonicalRoute
NavigationPath
ContentSource
ArtifactInputReferences
DataReferences
AssetReferences
RuntimeRequirements
```

A PlannedPage is not:

```text
a ContentPanel
a G1 or G2 structure
a PA
an Artifact
rendered HTML
an output file
```

The PlannedPage is the bridge between public declaration and UI-model
resolution.

---

# 9. Route Derivation

Routes are derived from the navigation tree.

This is a design rule:

```text
canonical navigation placement -> canonical public route
```

The Publication Plan does not allow arbitrary page-level route invention.

A page's canonical route is derived from its canonical navigation path.

A promoted page therefore needs a canonical navigation placement.

If a page is not placed in the navigation tree, it has no canonical public route.

---

# 10. Route Table

The Publication Plan owns the resolved route table.

The route table records:

```text
PageId -> CanonicalRoute
CanonicalRoute -> PlannedPage
NavigationPath -> CanonicalRoute
```

Routes must be unique within the planned build.

The exact slug policy belongs to route design, but route derivation belongs to
the Publication Plan.

Examples of possible route derivation:

```text
Navigation path:
  Current Sumo / Basho Results

Canonical route:
  /current-sumo/basho-results/
```

or, if the navigation slug policy uses shorter subject slugs:

```text
/current/basho-results/
```

The important point is not the exact spelling here. The important point is that
the route is derived from the canonical navigation path.

---

# 11. Home Route

The Publication Plan resolves the home page.

It records:

```text
home page id
home page canonical route
root entry behavior
```

The declared home page must be included in the build.

If the home page is not included, the build is internally contradictory and
should fail immediately.

---

# 12. Quick Links

Quick links are shortcut entry points into the canonical navigation structure.

They are not a second navigation tree.

They are not alternate canonical placements.

They point to canonical routes derived from the navigation tree.

Examples:

```text
Basho Results
Standings
Banzuke Changes
Rikishi Lookup
Ratings Explanation
```

The Site Model may declare quick links.

The Publication Plan resolves quick links to canonical routes.

If a quick link points to a missing or excluded page, the plan is internally
contradictory and should fail immediately.

---

# 13. Status Propagation

The Publication Plan carries page status forward.

A page's declared status may affect:

```text
whether it is included
how it is marked
whether it must satisfy promoted-page rules
whether it appears in public or development builds
```

The Publication Plan does not erase status once a page is included.

The UI Model and renderer may later use page status for public markers,
development markers, or legacy/research framing.

---

# 14. Dependency References

The Publication Plan resolves references to the inputs required by each planned
page.

This means it records which ingredients are needed.

It does not necessarily interpret those ingredients.

Examples:

```text
Basho Results planned page requires:
  BRB artifact input reference
  indexed basho data references
  table/runtime assets
```

The Publication Plan answers:

```text
What does this page depend on?
```

It does not answer:

```text
What G1/G2 structure does the page resolve to?
What filters does the artifact input define?
What rows does the table contain?
How is the artifact rendered?
```

Those belong to the UI Model and Artifact Model stages.

---

# 15. Artifact Input, Data, and Asset References

A planned page may reference:

```text
artifact input references
data references
asset references
runtime references
```

A reference identifies a required input.

A reference is not the same thing as loaded content.

For example:

```text
ArtifactInputRef:
  the BRB artifact input required by the planned page

Loaded Artifact Input:
  the actual object or parsed data used later to construct UI Model / Artifact
  Model objects
```

The Publication Plan resolves references.

Later stages consume those references.

---

# 16. Reference Resolution versus Content Loading

The Publication Plan resolves required references.

It does not need to parse or interpret all referenced content.

Example:

```text
PublicationPlan:
  PlannedPage "Basho Results" requires ArtifactInputRef("brb") and data refs.

UIModelResolver:
  uses the BRB artifact input to construct G1 contents, filters, PA, artifact, and
  notes.
```

This keeps the planning stage distinct from UI-model resolution.

If the implementation later uses in-memory artifact input objects rather than file
references, the same conceptual boundary still applies:

```text
Publication Plan:
  knows what source is required

UI Model:
  interprets that source as interface structure
```

---

# 17. Runtime Requirements

The Publication Plan records the complete runtime requirements of the planned
site.

It will always know the runtime requirements for the build.

In the initial design, this may simply mean:

```text
all builds include the standard make_site2 runtime bundle
```

If later builds use split runtime bundles, the selection of those bundles still
belongs to planning, not to ad hoc renderer discovery.

The renderer should not be surprised by a page's runtime requirements.

---

# 18. Build Modes

The Publication Plan may vary by build mode.

Possible build modes include:

```text
public
development
local preview
stress test
```

Build mode may affect:

```text
which statuses are included
whether development-only navigation nodes appear
whether diagnostic or legacy pages are built
whether extra build metadata is emitted
whether cache policy is development or production oriented
```

Build modes are operational choices.

They do not change the meaning of a PageDefinition.

---

# 19. Route and Status Consequences

The Publication Plan makes page status operational.

Examples:

```text
promoted:
  included in ordinary public builds

candidate:
  included in development or preview builds if requested

research:
  included when research pages are part of the public structure or explicitly
  requested

diagnostic:
  development-only unless explicitly requested

legacy:
  compatibility-only unless explicitly requested

superseded:
  excluded by default

excluded:
  excluded
```

The exact policy may change, but it must be explicit.

---

# 20. Global and Page Assets

The Site Model declares global assets.

PageDefinitions may declare page assets.

The Publication Plan determines which declared assets are required by this build.

It records:

```text
global assets required by the site
page assets required by included pages
runtime assets required by the planned site
```

It does not copy the assets.

Copying belongs to the OutputWriter.

---

# 21. Publication Plan and Deployment

Deployment is a first-class requirement of the package.

However, deployment is downstream of planning.

The Publication Plan produces a resolved site that is suitable for rendering and
output.

Deployment design later determines how the completed static output is copied or
uploaded to:

```text
local browser-visible target
remote public target
```

The Publication Plan should not contain remote host behavior, upload commands,
or deployment retry policy.

---

# 22. What the Publication Plan Does Not Own

The Publication Plan does not own:

```text
UI grammar selection
ContentPanel structure
FilterSection structure
BranchSelector structure
PA internals
Artifact internals
table rows
chart traces
HTML rendering
CSS classes
JavaScript implementation
filesystem output paths
deployment execution
```

If those concepts appear in the Publication Plan, the design boundary has likely
been crossed.

---

# 23. Transformation to UIModel

The next stage consumes the Publication Plan and produces the UI Model.

Conceptually:

```python
def make_ui_model(
    publication_plan: PublicationPlan,
) -> UIModel:
    ...
```

This transformation resolves planned pages into interface structures.

Example:

```text
PlannedPage:
  PageId = basho_results_browser
  Route = /current-sumo/basho-results/
  ArtifactInputRef = brb

UIModel:
  G1 page with Heading, FilterSection, indexed-table PA, and relevant notes
```

The Publication Plan prepares this transformation by resolving what the planned
page is and where it will live.

---

# 24. Relationship to make_site and ui_model Evidence

Existing `make_site` and `ui_model` material may inform the Publication Plan.

Useful evidence includes:

```text
current page ids
current navigation-derived routes
known build modes
known deployment needs
known data and artifact input locations
known runtime asset requirements
quick-link candidates
legacy inclusion pressures
```

That evidence is not authoritative.

The Publication Plan for `make_site2` is defined by the new requirements,
specification, and design.

---

# 25. Deferred Questions

The following questions are deferred:

```text
Exact build mode vocabulary.
Exact status inclusion policy for each build mode.
Exact route slug normalization rules.
Whether excluded pages are recorded in the plan or simply absent.
Whether research pages are part of ordinary public builds.
Whether diagnostic/legacy pages have any public build mode.
Exact representation of artifact-input/data/asset references.
Exact quick-link placement in rendered UI.
Exact cache/version policy.
```

These should be resolved when they become implementation pressure points.

---

# 26. Summary

The Publication Plan is the resolved publication model for a build.

It says:

```text
which pages are included
which routes they get
which dependencies they require
which runtime bundle is required
which quick links resolve to which canonical routes
which statuses carry forward
```

It does not say:

```text
how each page's UI is structured
how artifacts render internally
what HTML/CSS/JS is emitted
where the final site is deployed
```

The Publication Plan is the bridge between declared public intent and UI-model
resolution.

It is the stage where the site stops being merely declared and becomes a concrete
plan for a buildable public publication.
