# 05.1 Rendering Grammar Audit How To

## Status

Working audit guide for `make_site2` rendering.

This document is a companion procedure to `05 Rendering Design`.

`05 Rendering Design` defines the rendering contract.

This document describes how to inspect rendered HTML, CSS, and browser behavior
for compliance with that contract.

It is not a styling specification.

It is not a list of desired visual improvements.

It does not redefine the rendering model.

It is a method for deciding whether a visible fact is justified.

---

# 1. Purpose

The audit exists to prevent accidental bespoke rendering.

The central audit question is:

```text
Which semantic owner justifies this visible token, spacing, alignment, ordering,
or behavior?
```

Do not ask first:

```text
What HTML or CSS would make this look right?
```

Ask first:

```text
Where does this visible fact live in the underlying semantic tree?
```

If the visible fact has no owner, either:

```text
identify the missing model concept
declare a rendering-grammar rule
accept the browser default for now
remove the bespoke implementation
```

---

# 2. Audit Vocabulary

The following terms are audit vocabulary.

They help classify evidence during inspection.

They do not create new product model entities by themselves.

## Concrete Owner

A concrete owner is a named model or rendering entity represented directly in
the code or design.

Examples:

```text
NavigationBar
ContentPanel
FilterSection
FilterControl
PASlot
Notes
```

Concrete owners are preferred when the concept is stable and important enough
to be part of the implementation vocabulary.

## Virtual Owner

A virtual owner is a documented rendering-grammar concept that may not yet have
its own model class or data structure.

Examples:

```text
heading hierarchy
table-like artifact
table-like column alignment
browser-default spacing
```

Virtual owners are allowed.

They must be named, documented, and used consistently.

If a virtual owner accumulates enough rules or exceptions, consider promoting it
to a concrete model or rendering entity.

## Browser Default

A browser default is visible behavior supplied by the user-agent stylesheet or
standard HTML layout behavior.

Examples:

```text
default heading margins
default heading font sizes
default list indentation
default table column sizing
default link underlining
```

Browser defaults are allowed when no declared rule overrides them.

They should be recorded as defaults, not mistaken for authored design rules.

## Bespoke Implementation

A bespoke implementation is an emitted token, layout behavior, style, or runtime
behavior that has no concrete owner, no documented virtual owner, and is not an
accepted browser default.

Bespoke implementation should be removed, or the missing owner/rule should be
declared at the highest sensible level.

---

# 3. Audit Shape

Use a top-down structural walk.

Start at the rendered public shell.

At each level:

```text
identify the current semantic path
list the visible facts introduced at that level
identify the owner of each visible fact
classify the owner
compare the implementation to the rule
record the verdict
```

Repeated structures should be audited as patterns.

Do not list every navigation item, table row, or filter instance unless a
specific instance has a special rule.

Examples of repeated patterns:

```text
NavigationItem*
FilterControl*
TableRow*
TableColumn*
```

Examples of constrained special cases:

```text
TableColumn[shikona]
current active page link
disabled unavailable filter option
```

---

# 4. Audit Table

Use this table shape:

| Path | Visible Fact | Semantic Owner | Owner Kind | Rule Source | Implementation | Verdict |
|---|---|---|---|---|---|---|
| `...` | ... | `...` | concrete / virtual / browser default / bespoke | ... | ... | OK / Allowed default / Missing rule / Bespoke / Model gap |

## Path

The structural path in the semantic/rendering tree.

Use concrete names when they exist.

Use virtual names only when the concept has been documented as rendering
grammar.

## Visible Fact

The thing a user can observe.

Examples:

```text
text exists
text is bold
items are indented
column is left-aligned
regions scroll independently
label and control stay together
```

## Semantic Owner

The entity that justifies the visible fact.

The semantic owner is not the CSS selector.

The semantic owner is not the DOM node by itself.

The selector or DOM node belongs in the Implementation column.

## Owner Kind

Use one of:

```text
concrete
virtual
browser default
bespoke
```

Use `concrete/virtual edge` when a real data concept is being governed by a
virtual rendering category.

## Rule Source

Name the design rule, model rule, or accepted default.

If there is no source, the row should not be `OK`.

## Implementation

Describe the relevant emitted HTML, CSS, or runtime behavior.

Keep this column factual.

## Verdict

Use:

```text
OK
Allowed default
Missing rule
Bespoke
Model gap
```

---

# 5. Verdicts

## OK

The visible fact has an owner, a rule, and an implementation that matches the
rule.

## Allowed Default

The visible fact comes from browser behavior and no declared rule overrides it.

Allowed defaults are acceptable, but they should remain visible in the audit so
future work does not mistake them for deliberate authored design.

## Missing Rule

The visible fact is wanted, but no model or rendering-grammar rule yet explains
it.

Add a rule before adding implementation.

## Bespoke

The implementation creates a visible fact without a concrete owner, documented
virtual owner, or accepted browser default.

Remove it or define the missing owner/rule.

## Model Gap

The visible fact appears to be a real semantic distinction, but the current model
has no place for it.

This is stronger than a missing rendering rule.

It suggests the model may need to grow.

# 7. Promotion Rule

Virtual owners are acceptable when they are light, documented, and consistent.

Promote a virtual owner to a concrete model or rendering entity when:

```text
it accumulates several independent rules
it needs named state
it has repeated exceptions
it is needed by more than one renderer
it becomes hard to audit using prose alone
```

Promotion should be deliberate.

Do not promote every virtual owner immediately.

The audit should make the pressure visible before the model grows.

---

# 8. Audit Discipline

When changing rendering:

```text
1. Name the visible fact being changed.
2. Identify its semantic owner.
3. Check whether the owner is concrete, virtual, or only a browser default.
4. Add or update the rule before changing implementation.
5. Keep the implementation at the highest sensible shared level.
6. Record any new virtual owner or accepted browser default.
```

The goal is not to avoid CSS or HTML.

The goal is to ensure that CSS and HTML realize the semantic tree rather than
quietly inventing one.
