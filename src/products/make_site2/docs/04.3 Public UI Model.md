# 04.3 Public UI Model

## Status

Draft design document for the `make_site2` Public UI Model.

This document defines the semantic model of the visible public interface before
rendering. It refines `04 Model Design.md` for the model that represents the
public page grammar `PG` specified in `02 Specification.md`.

It names semantic concepts. It does not require that every named concept become
a distinct Python class, nor does it specify HTML, CSS or JavaScript
realisation.

---

## 1. Purpose

The Public UI Model states **what visible public interface shall be rendered**.

It consumes resolved planned publication material and represents a visible
public page conforming to `PG`:

```text
PublicUI -> NavigationBar . ContentPanel
NavigationBar -> <hider> . NavigationContent
NavigationContent -> <site caption> . QuickLinks? . Navigation
ContentPanel -> Heading . Contents
Contents -> FilterSection? . PAPanel
PAPanel -> PA . Notes
Notes -> <hider> . NotesContent
NotesContent -> Note*
```

It answers questions including:

- What visible top-level public regions exist?
- What NavigationBar and Navigation are present?
- What Page is selected in the ContentPanel?
- What page-level Heading is visible?
- Is there a FilterSection, and what Filters does it contain?
- What PAPanel is visible?
- What PA occupies that PAPanel?
- What Notes belong to that PA or its visible features?
- What public state is material to the visible presentation?

The Public UI Model is the model against which shared page rendering is
designed and audited.

---

## 2. Position and Boundary

The Public UI Model is resolved after publication planning and before rendering.

```text
PublicationPlan + resolved site-facing inputs
  -> PublicUIModel + PublishedArtifactModel
  -> Rendering
```

The boundary is:

```text
Publication Plan Model:
  determines what the build includes and what inputs it requires.

Public UI Model:
  represents the semantic visible public interface conforming to PG.

Published Artifact Model:
  represents analytical material and PA-specific visible meaning.

Rendering Design:
  defines how those modelled entities become visible browser output.
```

The Public UI Model shall not be bypassed for promoted Pages by page-specific
HTML, copied reports or bespoke renderer-owned page structures.

---

## 3. PublicUIModel

`PublicUIModel` is the root semantic representation of a selected visible
public page.

Conceptually:

```text
PublicUIModel
  NavigationBar
  ContentPanel
  selected_public_state
  carried_public_status?
```

It represents the top-level production:

```text
PublicUI -> NavigationBar . ContentPanel
```

This is a material modelling decision. The NavigationBar is part of the visible
public model and is not merely rendering infrastructure outside the page grammar.
Its layout and behaviour are therefore subject to the same model-to-render
discipline as the ContentPanel.

A static site may serialize or reconstruct this model in different ways. The
conceptual ownership is unchanged: the renderer shall be able to render a
selected visible public page from the resolved model.

---

## 4. NavigationBar

`NavigationBar` represents the site-level public region alongside the selected
ContentPanel.

It conforms to:

```text
NavigationBar -> <hider> . NavigationContent
NavigationContent -> <site caption> . QuickLinks? . Navigation
```

Conceptually:

```text
NavigationBar
  Hider
  NavigationContent
    site_caption
    QuickLinks?
    Navigation
```

### 4.1 Site Caption

The site caption is the public site identity displayed in the NavigationBar. It
is resolved from the Site Definition's public site identity.

It is distinct from:

- the selected Page Heading;
- a Navigation label;
- a PA title or framing;
- a Notes heading;
- a browser/deployment-context label unless separately specified.

### 4.2 Hider

`Hider` represents the reader-visible control by which the NavigationBar's
content region may be hidden or restored.

Hider state affects the public shell presentation only. It is not a `Filter`,
because it does not restrict, select or otherwise change the visible analytical
content in the PAPanel.

The Hider is a first-class structural part of the NavigationBar, not an overlay
owned by the page shell. When NavigationContent is hidden, the Hider remains
visible so the reader can restore the NavigationBar content.

The model need only represent the meaning and relevant state of the Hider.
Whether its state is persisted across browser visits belongs to runtime/rendering
design unless later made part of public-state requirements.

---

## 5. QuickLinks

`QuickLinks` represents a small curated set of direct links to important public
Pages inside the visible NavigationBar.

It realises the terminal requirement in `PG`:

```text
QuickLinks -> <curated public page links>
```

Conceptually:

```text
QuickLinks
  QuickLink+

QuickLink
  page_id
  label
  href
```

QuickLinks are not the canonical public-navigation hierarchy. They are a
NavigationBar convenience layer over selected renderable Pages. A QuickLink
shall resolve to a Page that is also present as a renderable public Page.

The initial curated QuickLinks are, in order:

1. Banzuke Changes
2. Basho Results

---

## 6. Navigation

`Navigation` represents the resolved subject-led public navigation available in
the visible NavigationBar.

It realises the terminal requirement in `PG`:

```text
Navigation -> <hierarchical numbered navigation items>
```

Conceptually:

```text
Navigation
  NavigationItem+
  selected_page_id?

NavigationItem
  node_id
  label
  children*
  public_selection_reference?
  selection_state?
  availability/status_state?
```

A NavigationItem may be a grouping item with children and no selectable Page.
It may be a selectable item corresponding to a PlannedPage. Where deliberate
policy permits unavailable or non-promoted items to be represented, that state
shall be explicit.

The Public UI Model shall preserve:

- hierarchy;
- reader-facing labels;
- selectable versus non-selectable meaning;
- selected Page indication where applicable;
- any explicitly public availability/status meaning.

Numbering is part of the specified visible Navigation form. The model need not
store literal prefixed number strings where hierarchy is sufficient for the
renderer to produce them consistently.

Navigation label capitalisation follows the Site Definition policy: grouping
items with children are title-style labels, while leaf items are sentence-style
labels using capitals only for proper nouns and the first word.

---

## 7. ContentPanel

`ContentPanel` represents the selected Page as visible public content.

It conforms to:

```text
ContentPanel -> Heading . Contents
```

Conceptually:

```text
ContentPanel
  page_id
  public_status?
  Heading
  Contents
```

The ContentPanel owns the selected Page's public framing and analytical content
structure. It is distinct from the NavigationBar, and it does not own site
identity or public Navigation.

A ContentPanel is not an arbitrary container of widgets. Its structure must be
representable through an approved public grammar.

---

## 8. Heading

`Heading` represents page-level reader framing for the selected Page.

It conforms to:

```text
Heading -> <main heading> . <sub heading>?
```

Conceptually:

```text
Heading
  main_heading
  sub_heading?
```

The Heading is distinct from:

- the NavigationBar site caption;
- Navigation labels;
- PA title/framing;
- table headings and chart labels;
- Notes headings or Note content.

The model records these distinct roles even if current rendering uses a simple
visual hierarchy. Decisions about typographic styling or HTML heading elements
belong to Rendering Design.

The sub heading may carry trusted inline markup declared by the Site Definition
where that markup is part of the intended public caption, for example an inline
link. This does not make producer data or copied HTML part of the Public UI
Model boundary.

---

## 9. Contents

`Contents` represents the selected Page's analytical public presentation.

It conforms to:

```text
Contents -> FilterSection? . PAPanel
```

Conceptually:

```text
Contents
  FilterSection?
  PAPanel
```

The structural relationship is important:

- a FilterSection, where present, is a sibling of PAPanel;
- a PAPanel contains the visible PA and its Notes;
- Notes do not belong to or extend the FilterSection.

The Public UI Model shall preserve that relationship. A renderer shall not
place Notes in a way that visually implies they span or belong to both the
FilterSection and the PA unless the public model is deliberately amended.

The initial supported public shape has one visible PAPanel and one visible PA.
A Page requiring multiple simultaneous PAPanels, nested Filter scope or other
additional visible structure requires an approved extension rather than a local
renderer invention.

---

## 10. FilterSection and FilterItems

`FilterSection` represents reader-visible controls that affect the visible PA or
its selected public presentation.

It conforms to:

```text
FilterSection -> FilterItem*
FilterItem -> BooleanChoice | SingleFiniteChoice
```

Conceptually:

```text
FilterSection
  FilterItem*

FilterItem
  filter_id
  label
  default_value
  public_state_participation
  help_text?
  presentation_hint?
```

A FilterSection may be absent. A represented FilterSection may contain the
Filters applicable to the PA/view under the initial flat-filter public model.

### 10.1 Filter Meaning

A `Filter` is semantic reader-visible state that changes what analytical
material or representation is shown. It may correspond to:

- restricting rows;
- selecting a data instance;
- choosing a source;
- selecting a measure;
- controlling visible columns or groups;
- choosing a declared representation/view.

A Filter is not defined by the browser control used to display it.

### 10.2 BooleanChoice

`BooleanChoice` represents a labelled true/false Filter with a declared default
value.

Conceptually:

```text
BooleanChoice
  filter_id
  label
  default_value: boolean
  public_state_participation
  help_text?
  presentation_hint?
```

### 10.3 SingleFiniteChoice

`SingleFiniteChoice` represents a labelled Filter that selects exactly one
value from a finite declared value set.

Conceptually:

```text
SingleFiniteChoice
  filter_id
  label
  Values
  default_value
  public_state_participation
  help_text?
  presentation_hint?

Values
  Value+

Value
  value_id
  label
```

The model does not determine whether a BooleanChoice appears as a checkbox or
whether a SingleFiniteChoice appears as radio buttons or a select control.
Those are Rendering Design decisions.

### 10.4 Filter Scope and Limits

Under the initial `PG`, Filters in the FilterSection govern the displayed
PAPanel/PA presentation as flat peer controls.

The initial Public UI Model does not represent:

- nested Filters;
- conditional Filter groups;
- multiple PAPanel-local FilterSections;
- Filter structure that changes with alternative visible PA branches.

Where a real promoted Page requires such structure, the public model shall be
extended explicitly.

### 10.5 Filters and Notes

Filters do not own Notes. A Filter change may cause different Notes to be
relevant only because it changes the visible PA or a visible PA feature.

---

## 11. PAPanel

`PAPanel` represents the region containing the Published Artifact and the Notes
that accompany it.

It conforms to:

```text
PAPanel -> PA . Notes
```

Conceptually:

```text
PAPanel
  PA
  Notes
```

PAPanel is a semantic entity, not merely a convenient layout wrapper. It makes
explicit that the visible Published Artifact and its Notes constitute one
public analytical presentation, separate from the sibling FilterSection that
controls or selects it.

The Public UI Model owns the placement relationship:

```text
FilterSection? beside/before PAPanel at Contents level
PA and Notes together inside PAPanel
```

The precise visible arrangement within those relationships belongs to Rendering
Design. For example, Rendering Design may specify a Notes panel beneath a PA
with bounded height, but the model establishes that such Notes are in the
PAPanel rather than underneath the FilterSection.

---

## 12. PA Position and Handoff

`PA` means **Published Artifact**.

At Public UI Model level, `PA` identifies the deliberately published analytical
object occupying the PA position in a PAPanel and provides the handoff to the
Published Artifact Model.

It conforms at public-page level to one terminal form:

```text
PA -> <table> | <indexed table> | <chart> | <sectioned table> |
      <prose> | <custom artifact>
```

Conceptually:

```text
PAReference
  pa_id
  terminal_form
  public_framing?
  published_artifact_model_reference
```

The Public UI Model owns:

- that a PA is present in the PAPanel;
- which PA is being presented;
- PA framing at public page placement level where declared;
- the relationship between the PA, its Filters and its Notes.

The Published Artifact Model owns terminal-form-specific analytical structure,
such as table columns, chart traces, sectioned-table sections or specialised
custom artefact semantics.

---

## 13. Notes and Note Relevance

`Notes` represents explanatory material accompanying the PA within a PAPanel.

It conforms to:

```text
Notes -> <hider> . NotesContent
NotesContent -> Note*
```

Conceptually:

```text
Notes
  Hider
  NotesContent
    Note*

Note
  note_id
  applies_to
  text_or_content_reference
  relevance_condition?
```

A Note may pertain to:

- the PA as a whole;
- a visible table column or column group;
- a visible chart trace or data source;
- a visible representation/view;
- an artefact-specific visible feature;
- a caveat or provenance fact relevant to the displayed analytical content.

The model shall record Note ownership and the semantic conditions under which a
Note is relevant where those conditions exist.

The renderer decides the visible Notes treatment and how currently relevant
Notes are displayed; it shall not relocate them outside their PAPanel ownership.

The Notes Hider is a first-class structural part of the Notes region. It may
hide or restore NotesContent without removing the Notes region from PAPanel
ownership. When NotesContent is hidden, the Hider remains visible so the reader
can restore it.

`Notes` may be present in PAPanel even when it contains zero currently visible
Notes. The rendering need not display an empty Notes container or Hider when no
Note is relevant.

---

## 14. Public State in the UI Model

The Public UI Model shall identify public state that materially determines the
visible interface or PA presentation.

Material public state may include:

- selected Page;
- selected Filter values;
- selected data instance;
- selected declared PA representation or view;
- selected visible groups or measures where represented as Filters.

The Publication Plan establishes available Page selections and the basis for
public selection references. The Public UI Model identifies the state belonging
to the selected interface and PA presentation. Runtime/Rendering Design defines
serialization and restoration behaviour consistent with the public state
contract.

The Public UI Model need not treat incidental interaction as public state.
Examples normally outside the model include temporary hover, scroll position,
open transient tooltips and non-material chart zoom.

NavigationBar Hider state and Notes Hider state are shell/UI state and are not
Filters. Their persistence may be a runtime policy without making either part
of material analytical public state.

---

## 15. PublicStatus in the Visible Model

The Publication Plan carries declared PublicStatus for included Pages.

The Public UI Model may carry that status where the renderer needs it to
represent public status, limitations or context visibly.

The Public UI Model does not decide whether a Page is promoted, candidate,
research, diagnostic, legacy, superseded or excluded. It preserves planning
meaning where visible representation requires it.

A promoted Page is expected to conform to `PG` in the initial supported public
shape. A non-promoted Page exposed under deliberate policy shall not silently
redefine normal promoted-page structure.

---

## 16. Model-to-Render Invariant

The Public UI Model is the direct semantic owner of visible public-page
structure. Rendering shall realise it, not reconstruct or replace it ad hoc.

The following are consequences of this invariant:

1. The top-level visible relationship between NavigationBar and ContentPanel
   shall be a rendering of `PublicUI -> NavigationBar . ContentPanel`.
2. NavigationBar identity, NavigationContent and Hider presentation shall be a
   rendering of the modelled NavigationBar rather than an unowned shell
   convenience.
3. The selected Page's Heading shall be distinct from site caption, PA framing
   and artefact-internal labels.
4. A FilterSection shall render as a sibling of PAPanel, not as the owner of PA
   Notes.
5. Notes shall be rendered within the PAPanel relationship established by the
   model.
6. A PA renderer may render PA internals but shall not redefine surrounding
   `PG` structure.
7. Where the model establishes an owner but not a unique visual treatment,
   Rendering Design shall own the chosen shared treatment.

This invariant does not mean that font sizes, spacing or colours must be stored
in the Public UI Model. It means that visible decisions must have an accountable
modelled owner or declared rendering/design status.

---

## 17. What the Public UI Model Does Not Own

The Public UI Model does not own:

- analytical computation;
- inclusion or exclusion decisions for a build;
- final public-link syntax;
- loaded PA-specific rows, columns or traces except through PA model handoff;
- table or chart internal rendering mechanics;
- HTML element selection;
- CSS selector names or styling values;
- JavaScript implementation detail;
- static output file writing;
- deployment operations.

It also does not own richer public structures that have not been specified. A
renderer requirement for unrepresented structure is evidence that the public
model or specification needs deliberate extension.

---

## 18. Transformation to Rendering

The renderer consumes the Public UI Model together with resolved Published
Artifact Models and runtime/public-state material.

Conceptually:

```text
PublicUIModel + PublishedArtifactModel + applicable public state
  -> Rendered PublicUI
```

For a selected promoted Page, the renderer shall be able to identify from the
model:

- the NavigationBar and its Navigation/Hider;
- the selected ContentPanel;
- the Heading;
- any FilterSection and FilterItems;
- the PAPanel;
- the PA terminal form/model to render;
- the relevant Notes to present.

If a renderer requires additional page-level semantic knowledge that is absent
from the Public UI Model, it shall not hide that gap with page-local markup or
CSS. The model/design shall be corrected or extended.

---

## 19. Relationship to Legacy Evidence

Archived documentation and legacy `make_site` behaviour may reveal useful
public-interface evidence, including:

- expected Navigation stress cases;
- previously visible PA features;
- Filter behaviour worth retaining;
- Note ownership/placement regressions;
- specialised PA behaviours such as Banzuke Changes presentation.

Such evidence informs evaluation against current requirements and `PG`. It does
not determine the Public UI Model merely because it existed before.

---

## 20. Invariants

A valid Public UI Model for an initial supported promoted Page shall satisfy:

1. It represents one `PublicUI` with one NavigationBar and one selected
   ContentPanel.
2. NavigationBar contains site caption, Navigation and Hider meaning.
3. ContentPanel contains one Heading and one Contents.
4. Contents contains zero or one FilterSection and one PAPanel.
5. PAPanel contains one PA and one Notes entity; Notes may contain zero Notes.
6. Every represented FilterItem is a supported Filter form or the specification
   has been extended deliberately.
7. Every visible Note belongs to the visible PA or a visible PA feature and is
   relevant to the current public state.
8. The PA position hands off to a valid Published Artifact Model of an approved
   terminal form.
9. No page-specific renderer-owned public structure is required to make the
   represented Page intelligible.

---

## 21. Summary

The Public UI Model is the semantic representation of the visible public page
specified by `PG`.

It says:

```text
what NavigationBar and ContentPanel are visible
what Navigation and Hider meaning exist
what selected Page Heading is shown
what Filters are available
what PAPanel contains the Published Artifact and Notes
what public state matters to the visible presentation
where PA-specific modelling begins
```

It does not say:

```text
how HTML/CSS/JavaScript realise those relationships
how PA terminal internals are computed or drawn
how static files are written
how completed output is deployed
```

The central model commitment is that the entire visible promoted public page,
not only its inner artefact area, is represented before it is rendered.
