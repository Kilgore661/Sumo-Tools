# 04.1 Site Definition Model

## Status

Draft design document for the `make_site2` Site Definition Model.

This document defines the model of declared public-site intent. It refines
`04 Model Design.md` for the first stage of the model pipeline:

```text
Site Definition
  -> Publication Plan
  -> Public UI Model and Published Artifact Model
  -> Rendering
```

It names semantic concepts. It does not require that every named concept become
a distinct Python class.

---

## 1. Purpose

The Site Definition Model states **what public site is intended**.

It answers questions including:

- What is the public site called?
- What subject-led public navigation is intended?
- What Pages are known to the site?
- Which Page is associated with which Navigation position?
- What is the declared public status of each Page?
- What public material is each Page intended to publish?
- What site-level public assets or semantic defaults are declared?

It does not resolve a particular build, construct the visible `PublicUI`, render
HTML/CSS/JavaScript, or determine deployment destinations.

---

## 2. Position and Boundary

The Site Definition Model is upstream of the Publication Plan and Public UI
Model.

```text
Public requirement and specification
  -> Site Definition Model
  -> Publication Plan Model
  -> Public UI Model / Published Artifact Model
  -> Rendered static site
```

The boundary is:

```text
Site Definition Model:
  declares the intended public site.

Publication Plan Model:
  resolves what this build will publish and what it requires.

Public UI Model:
  represents the selected visible interface conforming to PG.
```

The Site Definition Model is not itself a `PG` instance. It supplies declared
public identity, Navigation and Page material from which a conforming visible
`PublicUI` can later be resolved.

The specification mandates common public structure such as the existence of the
NavigationBar hider. That common structure need not be redundantly declared in
every Site Definition unless a later requirement introduces site-specific
variation.

---

## 3. SiteDefinition

`SiteDefinition` is the root declaration of a public site.

Conceptually:

```text
SiteDefinition
  SiteIdentity
  NavigationTree
  PageRegistry
  PublicAssets?
  SiteDefaults?
```

Where required, it may also name a home Page or other deliberate public entry
points.

The SiteDefinition is authoritative for intended public organisation. Producer
file paths, generated output directories, legacy HTML layout and deployment
locations do not define the site's public structure.

### 3.1 SiteIdentity

`SiteIdentity` shall contain the stable identity and public caption/title of the
site.

Conceptually:

```text
SiteIdentity
  site_id
  site_caption
```

The public site caption is the material from which the `<site caption>` terminal
of `PG` is resolved.

Site identity is distinct from:

- package name;
- deployment directory or host name;
- Page title;
- Navigation item label;
- PA framing or title.

These values may resemble one another, but they do not have the same meaning or
owner.

---

## 4. NavigationTree

`NavigationTree` declares the intended subject-led organisation of public
material.

Conceptually:

```text
NavigationTree
  NavigationNode+

NavigationNode
  node_id
  label
  children*
  page_id?
  public_selection_hint?
  status/readiness_hint?
```

A Navigation node may be:

- a grouping node with children but no Page destination;
- a Page node associated with a known Page;
- a declared but unavailable/future node where that is deliberate and its
  treatment is resolved later.

A Navigation node is not automatically a Page. A Page is not automatically
included in Navigation merely because it exists in the PageRegistry.

The tree declares hierarchy and reader-facing labels. The public specification
requires rendered Navigation to appear as hierarchical numbered navigation
items; numbering and detailed visible treatment are resolved by the Public UI
Model and Rendering Design rather than stored as ad hoc text in labels.

Navigation labels use role-based capitalisation:

- a node with child items is a title and uses ordinary title capitalisation;
- a node without child items is a sentence-style label and uses capitals only
  for proper nouns and the first word; and
- sumo terms such as rikishi, banzuke, basho, chii and makuuchi are treated as
  ordinary words, not proper nouns, unless they begin the label.

### 4.1 Canonical Placement and Additional Entry Points

A promoted Page should ordinarily have one canonical Navigation placement.
Additional public entry points may point to the same Page, but they do not
create competing canonical subject structures.

If quick entry points are later supported, they shall be declarations referring
to known public Pages or public selections, not a second independent site
hierarchy.

---

## 5. PageRegistry and PageDefinition

`PageRegistry` declares Pages known to the public-site product.

Conceptually:

```text
PageRegistry
  PageDefinition*

PageDefinition
  page_id
  title
  summary?
  public_status
  publication_source
  page_assets?
  declared_defaults?
```

A `PageDefinition` identifies an intended public or candidate publication unit.
It shall be capable of directing later planning to the material needed to
construct the Page's public presentation.

A PageDefinition is not:

- an HTML page;
- a deep-link encoding;
- a `ContentPanel` instance;
- a fully resolved `PAPanel`;
- a data payload;
- a copied legacy report.

### 5.1 Page Identity and Public Wording

The model shall preserve the distinction between:

```text
page_id
  stable identity of the Page declaration

Navigation label
  concise wording for a Navigation item

Page title
  main reader-facing title of the selected Page

Page summary
  optional immediate framing for that Page

public selection representation
  resolved public link/state expression, owned downstream
```

They may have related text but shall not be collapsed merely for convenience.

### 5.2 Page Publication Source

A PageDefinition shall refer to the deliberate public material from which its
presentation can be planned and modelled.

This reference may lead downstream to a PA declaration, producer site-facing
input or another approved public source. It shall not rely on inspecting
arbitrary producer output directories or reverse-engineering legacy rendered
HTML as the normal publication mechanism.

The Site Definition declares the intended source relationship. The Publication
Plan resolves concrete required inputs for a build, and the PA/Public UI model
layers represent the published analytical and interface structure.

---

## 6. PublicStatus

Every declared Page shall have an explicit `PublicStatus` or be deliberately
excluded from the PageRegistry.

Initial status vocabulary is:

```text
promoted
candidate
research
diagnostic
legacy
superseded
excluded
```

At Site Definition level, status is a statement of public intent:

```text
This is how the project currently regards this Page.
```

It does not by itself decide build inclusion, visual marking or conformance
handling. The Publication Plan resolves those consequences under the
specification and build policy.

A `promoted` Page is intended for the normal public site and must be capable of
resolution into approved public structure and Published Artifact material.

Non-promoted status exists to prevent interesting, provisional, diagnostic or
legacy material from accidentally becoming normal public-site authority.

---

## 7. Public Assets and Semantic Defaults

The Site Definition may declare site-level public assets and semantic defaults
needed by the intended public site.

### 7.1 Public Assets

Public assets may include references to resources required across the public
site, such as shared runtime assets or a public site image.

A PageDefinition may also declare an asset or input specific to that Page where
it is part of the intended public material.

Asset declaration does not imply ownership of copying, output path selection or
browser loading implementation. Those are resolved downstream.

Page-specific assets shall not be used to smuggle an independently designed
page shell around the specified public model.

### 7.2 Semantic Defaults

A site declaration may include semantic defaults such as:

- a home or initial selected Page;
- an intended initial public entry point;
- defaults intrinsic to declared public content where these belong at site/page
  declaration level.

The Site Definition shall not contain operational build/deployment settings
merely because they are convenient to store nearby. Output directories, build
timestamps, cache tokens, local/remote destinations and development deployment
choices belong to build or deployment configuration.

---

## 8. Invariants

A valid Site Definition shall satisfy the following invariants:

1. `site_id` is stable within the public-site product.
2. Every Navigation node has a stable node identity within its tree.
3. Every declared Page has a stable `page_id` within the site.
4. Every Navigation node that refers to a Page refers to a Page in the
   PageRegistry.
5. A declared default/home Page, where present, refers to a known Page.
6. Any declared additional public entry point refers to a known Page or a
   resolvable public selection declared under later policy.
7. Every Page has an explicit PublicStatus.
8. A promoted Page has sufficient declared publication source information for a
   Publication Plan to attempt normal public publication.
9. The Navigation tree and PageRegistry express public intent, not incidental
   producer or filesystem arrangement.

An incoherent Site Definition is a declaration error. It is not a condition the
renderer should repair by guessing.

---

## 9. What the Site Definition Model Does Not Own

The Site Definition Model does not own:

- concrete inclusion decisions for a particular build;
- resolved public URLs or serialized public state;
- resolved data/asset file dependencies;
- build output paths;
- runtime manifests;
- `PublicUI`, `NavigationBar`, `ContentPanel`, `PAPanel` or other rendered-page
  model instances;
- Filter rendering or current runtime Filter state;
- PA internals such as table columns or chart traces;
- Notes visibility for a selected visible PA state;
- HTML, CSS or JavaScript;
- deployment destinations or operations.

This boundary is intentional. Site Definition states what public site is
intended; later layers resolve, model, render and publish it.

---

## 10. Transformation to Publication Plan

The Publication Plan consumes a Site Definition together with build context and
build policy.

Conceptually:

```text
SiteDefinition + BuildContext + BuildPolicy
  -> PublicationPlan
```

That transformation resolves matters such as:

- which Pages are included in the build;
- how public statuses affect publication;
- stable public page-selection/deep-link references;
- required public assets and site-facing inputs;
- build-specific instances or defaults;
- invalid or missing dependencies that prevent publication.

It does not render `PG` and does not determine PA internals beyond what is
necessary to resolve required declared inputs.

---

## 11. Relationship to Legacy Evidence

Archived documentation and legacy `make_site` behaviour may provide evidence
about possible site identity, Navigation structure, public Page candidates,
status decisions or material readers expect to find.

Such evidence is not authoritative. The active Site Definition Model is governed
by current Requirements, Specification and agreed design decisions.

Where a legacy item is retained, it shall be retained because it fits the
current intended public site, not because a former output path or page happened
to exist.

---

## 12. Summary

The Site Definition Model is the declaration of public intent at the start of
the `make_site2` model pipeline.

It declares:

```text
what the site is called
how public subject navigation is intended to be organised
which Pages are known
how those Pages are publicly regarded
what deliberate public material they point toward
what site-level public assets or semantic defaults are required
```

It does not determine how a particular build is resolved, how `PG` is
instantiated as a visible page, how a Published Artifact is internally modelled,
how HTML/CSS/JavaScript renders the result, or how the static output is
deployed.

That separation allows public intent to remain explicit while later layers do
the work required to publish a coherent and auditable public site.
