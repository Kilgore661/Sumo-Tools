# 04.2 Publication Plan Model

## Status

Draft design document for the `make_site2` Publication Plan Model.

This document defines the resolved publication plan for a build. It refines
`04 Model Design.md` for the stage between declared public intent and the
semantic public interface:

```text
Site Definition
  -> Publication Plan
  -> Public UI Model and Published Artifact Model
  -> Rendering
```

It names semantic concepts. It does not require that every named concept become
a distinct Python class.

---

## 1. Purpose

The Publication Plan Model states **what a particular build will publish**.

It resolves a Site Definition under a build context and policy. It answers
questions including:

- Which declared Pages are included in this build?
- Which known Pages are excluded, omitted or unavailable in this build?
- What public selection reference identifies each included Page?
- What Navigation destinations are available in this build?
- What public assets, site-facing inputs and runtime support are required?
- What declared PublicStatus is carried forward for each planned Page?
- What failures prevent a valid publication from being constructed?

The Publication Plan is resolved build intent. It is not the visible public UI,
a Published Artifact model, rendered output or a deployment operation.

---

## 2. Position and Boundary

The Publication Plan consumes declared site intent and prepares material for
semantic UI and PA resolution.

```text
SiteDefinition + BuildContext + BuildPolicy
  -> PublicationPlan
  -> PublicUIModel / PublishedArtifactModel
```

The boundary is:

```text
Site Definition Model:
  declares what public site is intended.

Publication Plan Model:
  resolves what this build will publish and what it requires.

Public UI Model:
  represents the visible PublicUI conforming to PG.

Published Artifact Model:
  represents deliberately published analytical material in PA positions.
```

The Publication Plan shall not construct browser-visible layout or privately
invent public structure. It supplies the resolved publication units and inputs
from which downstream models instantiate the specified public page.

---

## 3. Inputs to Planning

Conceptually:

```text
PublicationPlan = plan(SiteDefinition, BuildContext, BuildPolicy)
```

### 3.1 SiteDefinition

The Site Definition supplies declared public intent, including:

- site identity;
- intended Navigation tree;
- Page definitions and PublicStatuses;
- declared publication sources;
- declared public assets and semantic defaults.

### 3.2 BuildContext

`BuildContext` supplies operational facts of the particular build, such as:

- build mode;
- repository/product/output roots;
- development, preview or public-build context;
- selected data availability or build-time instance information where needed;
- cache/version information where required for output.

BuildContext does not redefine Page meaning, Navigation meaning or `PG`.

### 3.3 BuildPolicy

`BuildPolicy` supplies deliberate rules for resolving the build, such as:

- which PublicStatuses may be included in a public or development build;
- whether unavailable/candidate material is omitted, exposed with status, or
  treated as an error;
- whether optional additional entry points are included;
- consistency checks required before publication proceeds.

BuildPolicy may vary publication inclusion; it shall not silently change the
specified structure of promoted public Pages.

---

## 4. PublicationPlan

`PublicationPlan` is the root resolved model for one build.

Conceptually:

```text
PublicationPlan
  ResolvedSiteIdentity
  PlannedNavigation
  PlannedPage*
  ExcludedOrUnavailablePage*
  PublicSelectionTable
  RequiredPublicAssets
  RequiredRuntimeSupport
  ValidationResults
```

Where applicable, it may also contain a resolved home/default public selection
or additional deliberate public entry points.

The Publication Plan is complete enough for downstream model resolution and
rendering to know what public material exists in the build and where its inputs
come from.

---

## 5. PlannedPage

A `PlannedPage` is a PageDefinition resolved for inclusion in a particular
build.

Conceptually:

```text
PlannedPage
  page_id
  public_status
  title
  summary?
  public_selection_reference
  navigation_placement?
  publication_source_reference
  required_site_facing_inputs
  required_data_references
  required_asset_references
  required_runtime_support
```

A PlannedPage is not:

- a `ContentPanel`;
- a `PG` parse/tree instance;
- a `PAPanel`;
- a PA;
- loaded table rows or chart traces;
- rendered HTML;
- a written output file.

A PlannedPage is the resolved hand-off from site declaration to UI and PA model
resolution.

---

## 6. Inclusion and PublicStatus Resolution

The Publication Plan shall decide inclusion explicitly and deterministically.
It shall not include material merely because supporting output exists.

A Page's declared PublicStatus shall be carried into planning and may determine
whether that Page is included under the applicable BuildPolicy.

Typical intended treatment is:

| PublicStatus | Ordinary public-build treatment |
| --- | --- |
| `promoted` | included where required inputs are valid |
| `candidate` | not ordinarily included; may be included in an explicit preview/development build |
| `research` | included only under declared public or preview policy |
| `diagnostic` | not ordinary public material |
| `legacy` | not ordinary public material unless deliberately exposed under status |
| `superseded` | omitted by default |
| `excluded` | omitted |

This table describes the intended planning distinction; exact build-mode policy
may be refined without changing the meaning of PublicStatus itself.

A planned promoted Page shall be capable of downstream representation under the
approved public specification. A Page that requires an unapproved public
structure shall not become promoted merely because it can be rendered somehow.

---

## 7. Planned Navigation

The Site Definition declares intended Navigation. The Publication Plan resolves
Navigation availability for the particular build.

`PlannedNavigation` shall identify, as applicable:

- the included hierarchical Navigation structure;
- nodes that resolve to included Pages;
- grouping nodes retained in the build;
- unavailable or omitted destinations under the relevant policy;
- the relationship between available Navigation destinations and public
  selection references.

The plan shall preserve Navigation as public subject structure. It shall not
derive Navigation from resolved files, PA data sources or output directories.

The fact that `PG` requires Navigation to render as hierarchical numbered
navigation items is not a reason to store visible numbering text in the plan.
Numbered visible presentation belongs downstream to the Public UI Model and
Rendering Design.

---

## 8. Public Selection References

Each included selectable Page shall have a stable public selection reference in
the plan.

A `PublicSelectionReference` identifies the Page in the generated public site
and provides the basis for stable deep links and selected-page restoration.

The concrete representation may use a path, query state, hash state or an
approved combination. Whatever representation is selected shall satisfy these
rules:

- it is deliberate and stable for public purposes;
- it is unique within the planned site where it identifies a Page;
- it is not derived accidentally from producer filenames or legacy output
  layout;
- it can be related back to a known planned Page;
- it permits predictable handling of unavailable or invalid selections.

Conceptually, the plan records relationships such as:

```text
page_id -> public_selection_reference
public_selection_reference -> planned_page
navigation_destination -> public_selection_reference
```

### 8.1 Material Page State

The Publication Plan may establish the mechanisms and declarations needed to
represent material public state beyond Page selection. The Public UI and PA
models later determine which declared Filters and PA views supply such state for
a particular planned Page.

The plan shall not confuse transient browser interaction with stable public
selection merely because both may be expressed in JavaScript at runtime.

---

## 9. Home and Additional Public Entry Points

Where the Site Definition declares a home/default Page, the Publication Plan
shall resolve it to an included public selection reference.

A declared home/default Page that is not includable under the plan is an
inconsistency that shall be reported rather than silently replaced.

Where additional entry points or quick links are supported, planning shall
resolve them to included Pages or approved public selections. They shall not
become a second independent Navigation hierarchy or create accidental alternate
public identities.

---

## 10. Dependency and Input References

A PlannedPage shall record the dependencies required for downstream UI/PA model
resolution and publication.

These may include:

- producer site-facing input references;
- PA declaration or configuration references;
- data references;
- page-specific public asset references;
- shared runtime/asset requirements;
- any declared consistency metadata needed before rendering.

The Publication Plan owns the resolution of **which inputs are required**. It
does not necessarily own the interpretation of their analytical content.

For example:

```text
Publication Plan:
  Banzuke Changes requires its declared site-facing configuration and data.

Published Artifact Model resolution:
  interprets that material as the public PA features, such as table structure,
  Filter relationships and relevant Notes.
```

If implementation passes in-memory objects rather than file references, the
same ownership boundary remains: planning identifies required published inputs;
downstream modelling interprets them as interface and PA meaning.

---

## 11. Required Public Assets and Runtime Support

The Publication Plan shall collect required public assets and runtime support
for the included site.

It may record:

- shared site CSS and browser runtime assets;
- assets required by included Pages or PAs;
- serialized runtime/model/data material required in static output;
- asset identity/version requirements where needed for a valid build.

The plan identifies requirements. It does not itself write files or define CSS,
HTML or JavaScript behaviour.

Runtime support must arise from the planned public site, not be discovered only
when an unplanned renderer path happens to require an extra script or asset.

---

## 12. Validation and Blocking Failures

The Publication Plan shall validate that the declared public site can be
resolved into a buildable publication before normal rendering proceeds.

Blocking failures include, where applicable:

- a Navigation destination referring to an unknown Page;
- a declared home/default Page that is absent or excluded from the build;
- duplicate or contradictory public selection references;
- a promoted Page missing its declared publication source;
- missing required site-facing inputs or public assets;
- a status/inclusion contradiction;
- an intended promoted Page known not to be representable under approved public
  structure.

The renderer shall not be expected to guess around planning contradictions or
repair missing required public meaning.

Some conditions may be represented as planned non-public or unavailable
material in development/preview contexts under explicit policy. They shall not
silently leak into normal promoted publication.

---

## 13. What the Publication Plan Does Not Own

The Publication Plan does not own:

- the semantic instantiation of `PublicUI`, `Sidebar`, `ContentPanel`,
  `FilterSection`, `PAPanel` or `Notes`;
- the resolved contents of a PA;
- table-column, chart-trace or specialised PA internals;
- visible layout, colours, typography or spacing;
- HTML elements, CSS selectors or browser event handling;
- output-file writing mechanics;
- local or remote deployment actions.

If such matters are being decided in planning, the layer boundary has been
crossed.

---

## 14. Transformation to Public UI and Published Artifact Models

The downstream transformation is conceptually:

```text
PublicationPlan + resolved site-facing inputs
  -> PublicUIModel + PublishedArtifactModel
```

For each included promoted Page, downstream model resolution shall produce a
semantic public interface conforming to the approved public specification and
shall populate its PA position using deliberate Published Artifact material.

For example:

```text
PlannedPage:
  page_id = banzuke_changes
  public selection reference resolved
  required site-facing input/data references resolved
  public_status = promoted

Downstream models:
  ContentPanel and Contents conforming to PG
  PAPanel containing the Banzuke Changes PA and relevant Notes
```

The Publication Plan makes this resolution possible and deterministic. It does
not substitute for it.

---

## 15. Relationship to Output and Deployment

The Publication Plan contributes the resolved publication dependencies needed by
rendering and output writing, but it is not a written output manifest unless a
later implementation deliberately uses it to generate one.

Output design owns creation of the static output tree. Deployment design owns
copying or publishing completed output to local or remote targets.

Deployment settings shall not determine public Navigation, Page identity, PA
meaning or `PG` structure. Environment/context may affect permitted publication
policy or visible status treatment only where explicitly designed.

---

## 16. Relationship to Legacy Evidence

Archived documents, legacy code and legacy output may reveal:

- Pages previously made available;
- public view state worth preserving;
- public-facing data dependencies;
- specialised PA behaviours that may have been lost;
- legacy inclusion or migration pressures.

This material may inform planning declarations and validation. It does not
define what a new build must publish or how public selection is resolved unless
adopted deliberately under the active requirements and specification.

---

## 17. Invariants

A valid Publication Plan shall satisfy the following invariants:

1. Every included PlannedPage originates in a declared PageDefinition.
2. Every included selectable PlannedPage has one valid public selection
   reference.
3. Every planned Navigation destination resolves to an included PlannedPage or
   is represented under an explicit unavailable/non-page policy.
4. A resolved home/default public selection, where declared, identifies an
   included PlannedPage.
5. Every included PlannedPage carries its declared PublicStatus and the policy
   consequence of that status is explicit.
6. Every promoted PlannedPage has all required references needed for downstream
   modelling or reports a blocking failure.
7. Required shared and Page/PA-specific public assets are collected explicitly.
8. No planned public Page identity is derived accidentally from producer output
   paths or legacy file layout.
9. The plan does not claim that a Page is promoted if it cannot be represented
   under an approved public specification and model path.

---

## 18. Summary

The Publication Plan Model is the resolved public publication model for one
build.

It states:

```text
which declared Pages this build publishes
how included Pages are publicly selected
which Navigation destinations are available
which PublicStatuses carry forward
which site-facing inputs, data, assets and runtime support are required
which contradictions block valid publication
```

It does not state:

```text
how PG is instantiated as visible interface structure
how a PA is internally modelled
how rendering makes the model visible
how files are written or deployed
```

This layer is the bridge between declared public intent and the semantic public
interface. It prevents inclusion, state selection and dependency resolution from
being improvised later inside page-specific rendering code.
