# 10.1 Selected History Coherence Audit

## Status

Current audit of the relationship between an explicitly selected `History` input
and the data published by currently promoted `make_site2` Pages.

This document records the evidence and initial PA-by-PA assessment for the
active Selected-History coherence P0. The governing rule exposed by this audit
has now been incorporated into:

```text
02 Specification.md
04.2 Publication Plan Model.md
07 Build, Output and Runtime Design.md
08 Producer Integration and Migration.md
```

The implementation policy and producer integration required to make the current
code conform remain outstanding. Once those changes are implemented and
verified, this audit may be reduced to a completed-conformance record or moved
to archive.

---

## 1. Trigger for the Audit

A local build was run using a deliberately restricted history source:

```text
--history-zip '.\files\output\Historys\1978_01 to 1980_11.zip'
```

The resulting public site showed two different apparent data instances:

```text
Basho Results
  correctly reflected the latest basho in the selected History: 1980_11.

Banzuke Changes
  displayed current/full-history change material from 2026 rather than
  changes into the final basho of the selected History.
```

This exposed a build/data-coherence problem, not a public-link problem. The
canonical Banzuke Changes link correctly identifies the Page's latest-basho
view; the data copied into that built site was inconsistent with the selected
History used elsewhere in the same site.

---

## 2. Agreed Rule

The accepted build rule is:

```text
An explicit History input selects the History/data instance for the whole
published site build.

Every included promoted PA whose meaning depends on History must be derived
from, or validated against, that selected History.
```

Consequences:

- a build from a History ending in `1980_11` shall not silently combine a
  `1980_11` Basho Results view with a `2026` Banzuke Changes view;
- a PA whose semantic meaning is "latest" means latest within the selected
  History/data instance used for that build;
- a public link does not freeze published data across later deployments, but a
  single completed build must be internally coherent;
- pre-existing copied producer output is acceptable only where it is known or
  validated to correspond to the selected build data instance, or where the PA
  is demonstrably independent of that History.

**Incorporation status:** This rule is now part of the active specification and
design documents. It is no longer merely a proposed conclusion of this audit.
The outstanding question is how the implementation enforces it incrementally.

---

## 3. Current Build Mechanism

`build_site(...)` resolves a `History` from either an explicit object, an
explicit `history_zip`, or the live store:

```python
resolved_history = (
    history
    if history is not None
    else load_history_from_zip(history_zip)
    if history_zip is not None
    else get_history()
)
```

However, only Basho Results is currently built using that resolved object:

```python
build_basho_results_data_output(
    history=resolved_history,
    output_root=output_root,
    payload_mode=basho_results_payload_mode,
)
```

The remaining included PA outputs are staged through copying functions that do
not receive `resolved_history`:

```python
copy_banzuke_changes_data_output(output_root=output_root)
copy_standings_by_wins_data_output(output_root=output_root)
copy_finish_by_chii_data_output(output_root=output_root)
copy_banzuke_division_by_era_data_output(output_root=output_root)
copy_makuuchi_rank_by_era_data_output(output_root=output_root)
copy_division_stability_data_output(output_root=output_root)
copy_first_chii_appearance_data_output(output_root=output_root)
copy_rank_at_retirement_data_output(output_root=output_root)
copy_career_length_data_output(output_root=output_root)
copy_typical_equelo_values_data_output(output_root=output_root)
copy_win_probability_by_standing_data_output(output_root=output_root)
```

Therefore an explicit `History` currently controls one promoted PA's generated
data, but does not control or validate the copied inputs for the other promoted
PAs. This is now known implementation nonconformance with the active documents.

## 5. Relationship to Public View Links

This issue does not reverse the canonical-link decision.

For example, the following remains a correct canonical link for the default
Banzuke Changes public view:

```text
?page=banzuke_changes&division=makuuchi&context=false&banzuke_style=true&delta=false&equelo=false
```

Its meaning is:

```text
Show the Banzuke Changes default material view for the latest basho in the
History/data instance published by this built site.
```

If a later deployment publishes a later coherent History/data instance, the
same link may correctly display updated latest-basho changes. The defect exposed
by this audit is that one built site currently mixes different data instances,
not that its link omits an immutable history snapshot identifier.

For a Page such as Basho Results, an explicit Filter value such as
`basho=latest` may likewise be a valid dynamic reader selection. It need not be
rewritten to a concrete basho merely because the chosen data instance resolves
what "latest" currently displays.

---

## 6. Required Implementation Policy Decision

There are two acceptable initial ways to make explicit-history builds honest:

### Policy A: Prepare all included History-dependent PAs

For every included promoted PA whose public meaning depends on History, invoke
or adapt its producer so it derives site-facing inputs from the selected
`resolved_history` before those inputs are staged into `BuildOutput`.

This is the complete desired end state, but may require integrating several
producers at once.

### Policy B: Fail or omit unsupported PAs in explicit-history builds

Until each producer is integrated, an explicit-history build may include only
PAs that can be built or validated against the selected History. A promoted PA
whose input cannot be established as coherent must cause a blocking build error
or be excluded only under an explicit non-public/preview policy.

This policy prevents misleading mixed-history output while allowing integration
to proceed PA by PA.

### Recommendation

Use Policy B as the immediate safety rule and integrate Banzuke Changes as the
first concrete producer path. The existing restricted-history workflow has
already shown that Banzuke Changes is a valuable conformance test case, while
silently leaving all other copied PAs in a supposedly coherent historical build
would remain misleading.

The active documents now require selected-History coherence; they deliberately
do not yet claim that Policy B, rather than an immediately comprehensive Policy
A implementation, has been adopted in code.

## 7. Next Technical Investigation: Banzuke Changes

Before implementing the first producer integration, inspect the Banzuke Compare
producer boundary to determine:

- whether it already exposes a function that can consume a `History` object or
  selected-history serialization;
- whether its current `files/output/bcr` site-facing files contain sufficient
  metadata to validate the represented history/data instance;
- whether producing `site_config.json` and `banzuke_change_report.csv` into a
  supplied output root is already supported;
- whether `make_site2` should call a preparation API or consume a prepared
  producer output carrying selected-History identity.

The correction should preserve the architectural boundary:

```text
Producer
  owns computation of Banzuke Changes from the selected History.

make_site2
  plans, validates, stages and presents that deliberate site-facing output.
```

`make_site2` should not duplicate Banzuke Changes analytical computation merely
to conceal an integration gap.

---

## 8. Verification Requirements

Any implemented correction to explicit-history building shall be tested using a
restricted History such as the observed `1978_01 to 1980_11.zip` case.

Minimum verification:

```text
Basho Results latest view
  displays the final basho in selected History.

Banzuke Changes default view, once integrated
  displays changes into the final basho in selected History.

Any remaining included promoted PA
  is either derived from/validated against the selected History, or is clearly
  rejected/omitted under the selected explicit-history build policy.

No successful explicit-history public build
  silently contains known mixed-history promoted material.
```

---

## 9. Summary

The current implementation accepts an explicit selected `History`, but uses it
directly only for Basho Results. Banzuke Changes has been demonstrated to copy
incompatible current/full-history output, and the remaining copied promoted PAs
are either plainly based on wider fixed intervals or lack build-time evidence of
coherence.

The governing public/design rule is now incorporated: a selected History governs
the whole build's History-dependent promoted material. The active P0 is to
choose and implement safe incremental enforcement of that rule, with Banzuke
Changes as the first concrete producer-integration case.
