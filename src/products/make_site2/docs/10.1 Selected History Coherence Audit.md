# 10.1 Selected History Coherence Audit

## Status

Current audit of the relationship between an explicitly selected `History` input
and the data published by currently promoted `make_site2` Pages.

This document records the evidence and initial PA-by-PA assessment for the
active Selected-History coherence P0. The governing rule exposed by this audit
has been incorporated into:

```text
02 Specification.md
04.2 Publication Plan Model.md
07 Build, Output and Runtime Design.md
08 Producer Integration and Migration.md
```

The first concrete producer integration, **Banzuke Changes**, has now been
implemented in code and awaits local verification. Broader enforcement for the
remaining History-dependent promoted PAs remains outstanding.

---

## 1. Trigger for the Audit

A local build was run using a deliberately restricted history source:

```text
--history-zip '.\files\output\Historys\1978_01 to 1980_11.zip'
```

The resulting public site showed two different apparent data instances:

```text
Basho Results
  correctly reflected the latest basho in the selected History: 1980_11.

Banzuke Changes
  displayed current/full-history change material from 2026 rather than
  changes into the final basho of the selected History.
```

This exposed a build/data-coherence problem, not a public-link problem. The
canonical Banzuke Changes link correctly identifies the Page's latest-basho
view; the data copied into that built site was inconsistent with the selected
History used elsewhere in the same site.

---

## 2. Agreed Rule

The accepted build rule is:

```text
An explicit History input selects the History/data instance for the whole
published site build.

Every included promoted PA whose meaning depends on History must be derived
from, or validated against, that selected History.
```

For **Banzuke Changes**, the precise PA meaning is:

```text
Compare the final banzuke contained in the Selected History with the
immediately preceding banzuke contained in that Selected History.
```

Therefore, for the restricted History used in this audit:

```text
Selected History:  1978_01 to 1980_11
Current banzuke:   1980_11
Previous banzuke:  1980_09
```

The Page does not request the next basho after `1980_11`. If the live store does
not yet contain a newly issued external banzuke, that is a live-store/tracker
freshness matter rather than a reason for this Page to infer data outside the
History supplied to the site build.

Further consequences:

- a build from a History ending in `1980_11` shall not silently combine a
  `1980_11` Basho Results view with a `2026` Banzuke Changes view;
- a PA whose semantic meaning is `latest` means latest contained in the selected
  History/data instance used for that build;
- a public link does not freeze published data across later deployments, but a
  single completed build must be internally coherent;
- pre-existing copied producer output is acceptable only where it is known or
  validated to correspond to the selected build data instance, or where the PA
  is demonstrably independent of that History.

**Incorporation status:** This rule is part of the active specification and
design documents. It is no longer merely a proposed conclusion of this audit.

---

## 3. Original Build Mechanism and First Implemented Correction

`build_site(...)` resolves a `History` from either an explicit object, an
explicit `history_zip`, or the live store:

```python
resolved_history = (
    history
    if history is not None
    else load_history_from_zip(history_zip)
    if history_zip is not None
    else get_history()
)
```

Before the correction, Basho Results used that selected object directly:

```python
build_basho_results_data_output(
    history=resolved_history,
    output_root=output_root,
    payload_mode=basho_results_payload_mode,
)
```

but Banzuke Changes copied unrelated previously prepared output:

```python
copy_banzuke_changes_data_output(output_root=output_root)
```

The correction now made is:

```python
build_banzuke_changes_data_output(
    history=resolved_history,
    output_root=output_root,
)
```

The implementation preserves the producer boundary:

```text
src.analysis.banzuke_compare
  now exposes a make_site2 publication path accepting a selected History.

src.products.make_site2
  calls that path and stages its site-facing CSV/config output.
```

That producer path uses:

```text
current banzuke   = final banzuke contained in supplied History
previous context  = immediately preceding basho contained in supplied History
```

It does not read the live store or copy pre-existing `files/output/bcr` data.
The standalone BCR publisher's separate external-new-banzuke workflow has not
been silently redefined by this integration.


## 5. Relationship to Public View Links

This issue does not reverse the canonical-link decision.

For example, the following remains a correct canonical link for the default
Banzuke Changes public view:

```text
?page=banzuke_changes&division=makuuchi&context=false&banzuke_style=true&delta=false&equelo=false
```

Its meaning is:

```text
Show the Banzuke Changes default material view for the final two banzukes
contained in the History/data instance published by this built site.
```

If a later deployment publishes a later coherent History/data instance, the
same link may correctly display updated latest-banzuke changes. The defect
exposed by this audit was that one built site mixed different data instances,
not that its link omitted an immutable History snapshot identifier.

For a Page such as Basho Results, an explicit Filter value such as
`basho=latest` may likewise be a valid dynamic reader selection. It need not be
rewritten to a concrete basho merely because the chosen data instance resolves
what `latest` currently displays.

---

## 6. Remaining Implementation Policy Issue

There are two acceptable ways to make the complete explicit-History site honest:

### Policy A: Prepare all included History-dependent PAs

For every included promoted PA whose public meaning depends on History, invoke
or adapt its producer so it derives site-facing inputs from `resolved_history`
before those inputs are staged into `BuildOutput`.

### Policy B: Fail or omit unsupported PAs in explicit-History builds

Until each producer is integrated, an explicit-History build may include only
PAs that can be built or validated against the selected History. A promoted PA
whose input cannot be established as coherent must cause a blocking build error
or be excluded only under an explicit non-public/preview policy.

### Recommendation

Use Policy B as the immediate safety rule while integrating producer paths
incrementally. Banzuke Changes is the first integration and now awaits
verification; the other copied PAs remain subject to the broader P0.

---

## 7. Banzuke Changes Verification Requirements

After pulling the implementation and rebuilding from the restricted History,
check:

```text
Basho Results latest view
  displays 1980_11.

Banzuke Changes site_config.json
  current_date is 1980/11 (or the equivalent project date string).
  previous_date is 1980/09 (or the equivalent project date string).

Banzuke Changes visible default view
  displays the 1980_11 banzuke relative to 1980_09 context,
  not current/2026 material.
```

Any build failure during this test may reveal a further producer dependency,
such as optional Equelo snapshot data, that also needs coherent treatment; it
must not be hidden by reverting to copied current output.

---

## 8. Broader Verification Requirements

For the remaining explicit-History P0:

```text
Any remaining included promoted PA
  is either derived from/validated against the selected History, or is clearly
  rejected/omitted under the selected explicit-history build policy.

No successful explicit-history public build
  silently contains known mixed-history promoted material.
```

---

## 9. Summary

The selected-History rule is now explicit and the first concrete integration has
been implemented: `make_site2` asks the Banzuke Compare producer to construct
Banzuke Changes data from the supplied `resolved_history`, using the final two
contained banzukes as current and previous.

For the restricted `1978_01 to 1980_11` History, the required Banzuke Changes
result is therefore `1980_11` compared with `1980_09`. This now requires local
verification.

The wider P0 remains open because other included promoted PAs are still copied
from fixed/current/pre-existing output or lack selected-History validation.
