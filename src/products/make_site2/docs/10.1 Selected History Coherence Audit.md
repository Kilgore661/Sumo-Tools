# 10.1 Selected History Coherence Audit

## Status

Current audit of the relationship between an explicitly selected `History` input
and the data published by currently promoted `make_site2` Pages.

This document records the evidence and initial PA-by-PA assessment for the
active Selected-History coherence P0. The governing whole-build coherence rule
has been incorporated into:

```text
02 Specification.md
04.2 Publication Plan Model.md
07 Build, Output and Runtime Design.md
08 Producer Integration and Migration.md
```

A further investigation of Banzuke Changes has refined its PA-specific meaning:
it is a new-successor-banzuke report, not a general comparison of the final two
banzukes in an arbitrary selected History. The specification and producer-
integration documents must therefore distinguish its production availability
condition from ordinary History-derived PA coherence.

---

## 1. Trigger for the Audit

A local build was run using a deliberately restricted history source:

```text
--history-zip '.\files\output\Historys\1978_01 to 1980_11.zip'
```

The resulting public site showed two different apparent data contexts:

```text
Basho Results
  correctly reflected the latest basho in the selected History: 1980_11.

Banzuke Changes
  displayed a current/live new-banzuke report based on 2026 material.
```

This exposed a build/publication-coherence problem, not a public-link problem.
The canonical Banzuke Changes link identified its Page and Filter state
correctly; the problem was that the Page remained presented as ordinary
material within a historical selected-History build even though its input
condition was not established for that build.

---

## 2. Whole-Build Coherence Rule

The accepted general rule remains:

```text
An explicit History input selects the History/data instance for the whole
published site build.

Every included promoted PA whose meaning depends on History must be derived
from, validated against, or explicitly resolved as unavailable relative to that
selected History and its required compatible inputs.
```

Consequences:

- a build from a History ending in `1980_11` shall not silently present a
  `1980_11` Basho Results view alongside an unrelated live/current 2026 Page as
  though both belong to the same historical publication;
- a public link does not freeze published data across later deployments, but a
  single completed production build must be internally coherent;
- copied producer output is acceptable only when its relation to the build's
  intended public context is known and allowed by the Page contract;
- some Pages may be unavailable in a particular coherent build because their
  required public input condition is not met.

---

## 3. Refined Meaning of Banzuke Changes

### 3.1 Production Meaning

Banzuke Changes is a **new-banzuke change report**. It answers:

```text
A newly published banzuke is available before that basho has results of its
own. How does it differ from the preceding represented basho?
```

Its normal production inputs are therefore:

```text
predecessor context
  the latest relevant BashoState in History, containing the prior banzuke and
  prior-result context;

current subject
  a separately downloaded successor banzuke whose basho is not yet represented
  by results in History.
```

This is consistent with the existing producer arrangement: it reads History for
the predecessor and separately parses the new current banzuke.

### 3.2 What It Is Not

Banzuke Changes is not, under its production contract:

```text
a general adjacent-historical-basho comparison Page;
a view whose meaning is automatically “compare the final two banzukes in any
selected History”; or
a Page allowed silently to show unrelated live/new-banzuke data inside an
archive-history publication.
```

Readers who wish to inspect represented historical basho and their predecessor
context should use Basho Results.

### 3.3 Production Availability

In the production site, Banzuke Changes is available only where a compatible
newly published successor banzuke exists relative to the History used by that
site and that successor has not yet entered History with results of its own.

Where that condition is not satisfied:

```text
Banzuke Changes is unavailable;
its Navigation entry should be disabled or otherwise not invite selection as an
available report;
and a direct request should display an unavailable-state explanation directing
readers to Basho Results for represented historical comparison.
```

Appropriate reader-facing wording is conceptually:

```text
No newly published banzuke is currently available.
Use Basho Results to compare a represented basho with its predecessor.
```

## 4. Development Exception

The production availability rule would make Banzuke Changes difficult to regress
during most of the development cycle, because its natural live availability
window is the interval after a new banzuke is published and before that basho's
first results enter History.

The agreed temporary development exception is:

```text
In development builds, Banzuke Changes may remain selectable and render its
existing prepared/live report even when its production availability condition
has not been established for the build.
```

This is a testing affordance, not alternative public semantics. It permits
regression work on the Page outside its production availability window.

Until production availability enforcement is implemented, an enabled
Banzuke Changes Page in development output must carry a conspicuous visible
warning stating that availability has not been validated against the build's
History and that archive/historical builds may display unrelated live output.

Current CLI/build-mode fact:

```text
ordinary build without --prod
  uses development mode;

build with --prod
  identifies production mode, although Banzuke Changes availability enforcement
  has not yet been implemented.
```

Until enforcement exists, production output must not silently suppress the
warning while continuing to publish potentially inappropriate Banzuke Changes
material.

## 5. Current Build Mechanism

`build_site(...)` resolves a `History` from either an explicit object, an
explicit `history_zip`, or the live store:

```python
resolved_history = (
    history
    if history is not None
    else load_history_from_zip(history_zip)
    if history_zip is not None
    else get_history()
)
```

Basho Results is built using that resolved object:

```python
build_basho_results_data_output(
    history=resolved_history,
    output_root=output_root,
    payload_mode=basho_results_payload_mode,
)
```

Banzuke Changes currently stages an already prepared BCR output:

```python
copy_banzuke_changes_data_output(output_root=output_root)
```

For the ordinary live product this output may be the deliberately prepared
new-successor-banzuke report. For an explicit archive/history-zip build, copying
that live report without a warning or unavailability resolution is currently
nonconforming because it presents out-of-context material as though it belongs
to the historical site.

Other copied PA outputs remain subject to the broader Selected-History audit:

```python
copy_standings_by_wins_data_output(output_root=output_root)
copy_finish_by_chii_data_output(output_root=output_root)
copy_banzuke_division_by_era_data_output(output_root=output_root)
copy_makuuchi_rank_by_era_data_output(output_root=output_root)
copy_division_stability_data_output(output_root=output_root)
copy_first_chii_appearance_data_output(output_root=output_root)
copy_rank_at_retirement_data_output(output_root=output_root)
copy_career_length_data_output(output_root=output_root)
copy_typical_equelo_values_data_output(output_root=output_root)
copy_win_probability_by_standing_data_output(output_root=output_root)
```

## 7. Relationship to Public View Links

This issue does not reverse the canonical-link decision.

The following remains a correct canonical link for the default Banzuke Changes
Page/Filter view when the Page is available, or for a direct request which must
be resolved to its declared unavailable state:

```text
?page=banzuke_changes&division=makuuchi&context=false&banzuke_style=true&delta=false&equelo=false
```

The link identifies the Page and reader-selected Filter state. It does not prove
that the build has a compatible newly published successor banzuke. Page
availability is a publication-plan/build-context matter.

## 8. Required Implementation Work

### 8.1 Immediate Development Warning

The next limited implementation step is not to redefine or re-compute Banzuke
Changes from arbitrary selected History. It is to expose the current development
exception visibly.

In development output, after the existing subheading text:

```text
New-banzuke change report.
```

the Page shall visibly append a conspicuous warning materially equivalent to:

```text
DEVELOPMENT WARNING: availability is not yet validated against this build's
History. This Page is intended only for a newly published banzuke before its
first results enter History; archive or historical builds may show unrelated
live output.
```

### 8.2 Production Availability Enforcement

The eventual production implementation shall:

```text
resolve whether a compatible successor banzuke input exists relative to the
build's History;
render Banzuke Changes normally only when that condition holds;
disable or otherwise mark its Navigation entry unavailable when it does not;
and provide a clear direct-request unavailable-state explanation directing the
reader to Basho Results.
```

The existing `--prod` build mode is the natural location for enforcing this
production rule, whereas non-`--prod` builds may retain the warning-backed
development affordance.

### 8.3 Remaining Selected-History Enforcement

Banzuke Changes does not dispose of the broader P0. Other included promoted PAs
whose meaning is directly History-derived must still be prepared, validated,
omitted under an explicit non-public inspection policy or rejected where their
required selected-History coherence is unavailable.

## 9. Verification Requirements

### Immediate Warning Patch

```text
A normal development build keeps Banzuke Changes selectable for regression
inspection.

Its Heading subheading visibly carries the agreed warning after
“New-banzuke change report.”

An archive/history-zip development build also shows that warning rather than
silently appearing production-coherent.
```

### Eventual Production Behaviour

```text
When a compatible newly published successor banzuke exists:
  production Banzuke Changes is available and displays that report.

When no compatible successor exists:
  production Banzuke Changes is unavailable;
  its Navigation treatment does not invite an ordinary available selection;
  direct selection displays an explanatory unavailable state referring readers
  to Basho Results.
```

---

## 10. Summary

The initial selected-History observation remains a real coherence defect, but
Banzuke Changes is not correctly modelled as a generic “last two banzukes in
Selected History” PA. It is a new-successor-banzuke report whose production
availability depends on separately available new-banzuke input relative to the
site's History.

The production rule is to show it only when that condition holds and otherwise
disable it or explain its unavailability. During development, the Page may
remain enabled outside that window to permit regression testing, provided the
exception is made conspicuous in its visible subheading. The wider Selected-
History P0 remains for other History-dependent promoted material.
