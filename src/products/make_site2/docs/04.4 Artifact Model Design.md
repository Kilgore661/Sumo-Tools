# 04.4 Artifact Model Design

## Status

Initial design document for the `make_site2` Artifact Model.

This document describes the analytical objects displayed inside UI Model PA
slots. It defines the artifact-level contracts that sit below the UI Model and
above concrete rendering implementation.

This is a design document, not an implementation inventory. Naming a concept
does not imply that the concept must become a Python class.

Rendering mechanics belong mainly to:

```text
05 Rendering Design.md
```

The UI Model boundary is defined in:

```text
04.3 UI Model Design.md
```

---

# 1. Purpose

The Artifact Model describes the analytical object displayed inside a PA slot.

It answers questions such as:

```text
What kind of analytical object is being displayed?
What data does it consume?
What artifact-specific labels, columns, traces, sections, or links does it own?
What renderer kind does it require?
What notes or caveats pertain to artifact features?
What provenance belongs to the analytical object?
What behavior is internal to the artifact rather than owned by the surrounding
page?
```

The Artifact Model does not answer:

```text
What route is the page published at?
What navigation node selected the page?
What ContentPanel grammar is used?
What filters surround the PA slot?
What HTML shell is emitted?
Where files are written?
Where the site is deployed?
```

Those belong to other model layers.

---

# 2. Position in the Pipeline

The Artifact Model sits below the UI Model.

```text
SiteDefinition
  -> PublicationPlan
  -> UIModel
       -> ArtifactModel
  -> RenderedSite
  -> WrittenOutput
```

The UI Model owns the public interface structure.

The Artifact Model owns the analytical object inside the PA slot.

The renderer consumes both:

```text
UI Renderer:
  renders shell, Sidebar, ContentPanel, Heading, Filters, Branches, PA slots,
  and Notes

Artifact Renderer:
  renders table/chart/prose/custom internals inside an Artifact slot
```

---

# 3. Core Responsibility

The Artifact Model owns artifact-specific analytical structure.

It owns:

```text
artifact kind
artifact data references or data objects
artifact renderer kind
artifact labels
artifact-specific notes
artifact-specific provenance
table columns and column groups
chart traces and axes
sectioned-table sections
prose structure
custom artifact contract
artifact-local interaction semantics
```

It does not own:

```text
site identity
navigation
route derivation
page status
ContentPanel structure
FilterSection placement
BranchSelector structure
page Heading
global shell layout
deployment
```

A useful rule:

```text
If the concept is about the analytical object itself, it belongs in the Artifact
Model.

If the concept is about where that object appears in the page, it belongs in the
UI Model.

If the concept is about how the object becomes HTML/CSS/JS, it belongs in
Rendering.
```

---

# 4. PA and Artifact Boundary

The UI Model treats PA as a visible analytical slot inside page contents.

At UI Model level, PA owns:

```text
PA identity
PA placement
PA framing/title, if present
Note ownership
Artifact slot
```

At Artifact Model level, PA connects that visible slot to the concrete
analytical object.

Conceptually:

```text
PA
  PAId
  PATitle, if present
  Artifact
  Note*
```

The Artifact is the concrete analytical object:

```text
Artifact
  TitleBlock, optional
    title
    subtitle, optional
  Payload
    table
    indexed_table
    chart
    sectioned_table
    prose
    custom_artifact
  Note*, optional
```

The title block and notes belong to the Artifact, not to a particular payload
kind.

A table payload does not own the Artifact title.

A chart payload does not own the Artifact title.

An Artifact may have no title block.

The PA/Artifact boundary allows `make_site2` to keep shared page structure
separate from artifact internals.

---

# 5. Artifact Kinds

The initial artifact kinds are:

```text
table
indexed_table
chart
sectioned_table
prose
custom_artifact
```

These kinds are design categories.

They do not require one renderer implementation each, but they define the
semantic classes of analytical object that `make_site2` expects to publish.

A future artifact kind should be added only when an actual page cannot be
honestly represented by the existing kinds.

---

# 6. Producer Site-Facing Inputs

Artifacts are constructed from producer-owned site-facing inputs.

These inputs may be:

```text
Python objects
generated JSON-like data
CSV or table data
chart data/config objects
structured prose
project-local generated files
other explicit producer outputs
```

The important requirement is not the serialization format.

The important requirement is that the producer supplies intentional site-facing
information rather than requiring `make_site2` to reverse-engineer old generated
HTML.

(The current `make_site2` design does not need the former concept of a
"PA Manifest" as a first-class model entity. In the previous UI-model
experiment, PA manifests were the practical carrier of artefact truth: they
described the published analytical artefact, its renderer, its data, and enough
surrounding metadata for the prototype runtime to display it. In the current
design, that role is split more explicitly. The UI Model owns interface
structure; the Artifact Model owns the analytical object displayed inside a PA
slot; producer site-facing inputs supply whatever data, metadata, labels, notes,
provenance, and renderer hints are needed to construct those models. A JSON or
Python "manifest" may still be a convenient serialization or interchange format,
but it is not currently a separate semantic layer in the design.)

If later implementation pressure shows that manifests are again the cleanest
stable producer/builder boundary, they can be reintroduced deliberately as a
serialization of the Artifact Model or UI Model, rather than inherited by
accident from the prototype.

---

# 7. Artifact Renderer Kind

Each artifact requires a renderer kind.

The renderer kind identifies how the artifact internals are rendered.

Examples:

```text
basic_table
indexed_table
plotly_chart
sectioned_table
markdown_prose
banzuke_changes_table
```

Renderer kind is artifact-specific.

It does not define the page shell.

It does not define the route.

It does not define the ContentPanel.

A custom artifact renderer is acceptable when the artifact has genuine local
structure that cannot be represented honestly by a generic renderer.

---

# 8. Runtime Requirements

The Publication Plan records the complete runtime requirements of the planned
site.

The Artifact Model may imply runtime needs, but those needs are known to the
Publication Plan before rendering.

The renderer should not discover runtime requirements ad hoc.

In the initial design, it is acceptable for all pages to use the standard
`make_site2` runtime bundle.

If later the runtime is split into smaller bundles, the split remains a planning
concern.

---

# 9. TableArtifact

A TableArtifact is a semantic analytical table.

A table is not merely:

```text
a dataframe dump
an HTML table element
a CSV file
```

A TableArtifact may define:

```text
data source
columns
column groups
row identity
row ordering
default sort
sort kinds
visibility presets
links
formatting hints
notes
provenance
```

Table semantics include distinctions such as:

```text
identifier column
label column
metric column
status column
chii column
rating column
record column
delta column
link column
orientation column
```

Column display labels should be public-facing.

Implementation names such as `after_basho_chii` should not leak into visible
public table headings unless deliberately chosen.

Tables may have column-level or group-level notes.

Tables may have artifact-local controls such as sorting, but not every table
interaction is a UI Model Filter.

A table interaction becomes a Filter only when it is public state that belongs
to the page/contents/PA contract.

---

# 10. IndexedTableArtifact

An IndexedTableArtifact is a table artifact whose visible rows are selected from
an indexed data universe.

It is useful when the full table universe is too large or too naturally
partitioned to load as one flat table.

Examples may include:

```text
Basho Results Browser
per-basho result payloads
division/date-indexed tables
large historical result tables
```

An IndexedTableArtifact may define:

```text
index data
payload data references
key fields
default selected instance
row schema
column schema
artifact renderer kind
artifact notes/provenance
```

The UI Model may expose Filters that select which indexed data instance is
visible.

The Artifact Model owns how the selected key maps to table data.

---

# 11. ChartArtifact

A ChartArtifact is a semantic analytical chart.

A chart is not merely:

```text
a Plotly object
a generated HTML file
an image
```

A ChartArtifact may define:

```text
data source
series/traces
axis semantics
category ordering
default visible series
legend policy
hover labels
annotations
support/sample-size metadata
uncertainty representation
notes
provenance
renderer kind
```

Chart artifacts should be generic enough to support Plotly without becoming
Plotly-specific in the model.

Plotly is a likely renderer, not the semantic model.

Chart titles used as public framing should belong to the UI Model PA title or
page Heading, not to plotting-library title fields.

Chart-internal labels such as axes, legends, trace labels, and hover text remain
artifact-internal.

---

# 12. SectionedTableArtifact

A SectionedTableArtifact is a table-like artifact composed of named sections.

It is useful when a single analytical table is naturally grouped into multiple
subtables or explanatory sections.

A SectionedTableArtifact may define:

```text
section order
section labels
section-level data
columns shared across sections
columns local to sections
section notes
artifact notes
provenance
renderer kind
```

Example use cases may include:

```text
Typical Equelo Ratings
landmark tables
grouped summary tables
```

A section label is artifact-internal unless it is promoted to PA framing.

The surrounding page structure still belongs to the UI Model.

---

# 13. ProseArtifact

A ProseArtifact is a first-class artifact kind.

It represents explanatory or narrative material that belongs inside a PA slot.

A ProseArtifact may contain:

```text
structured prose
method explanation
glossary material
research narrative
caveats
embedded references to related pages
inline lists or tables where appropriate
```

A ProseArtifact is not a fallback for arbitrary HTML.

It should participate in the same ownership structure as other artifacts.

The page Heading and PA title remain outside the prose artifact unless the UI
Model says otherwise.

Prose may be represented by Markdown, structured text blocks, or another
project-local representation. The exact format is an implementation detail.

---

# 14. CustomArtifact

A CustomArtifact represents a genuine artifact-specific structure that cannot be
honestly represented by the standard artifact kinds.

Custom artifacts are allowed.

They are also suspect unless the need is real.

A CustomArtifact owns only artifact internals.

It does not own:

```text
page route
navigation
Sidebar
ContentPanel
Heading
FilterSection placement
BranchSelector
page-level status
```

Example:

```text
Banzuke Changes may require a custom artifact renderer because the table has a
banzuke-shaped display with genuine domain structure.
```

That custom renderer may own the banzuke-specific table internals.

It may not own the surrounding page.

---

# 15. Notes in the Artifact Model

Notes explain or qualify visible analytical content.

Notes may pertain to:

```text
the PA as a whole
a table column
a column group
a visibility preset
a chart trace
a chart source
a data source
a prose section
a visible artifact feature
a caveat
a provenance fact
```

Notes are not table-only.

Notes do not belong to Filters.

A Filter may affect whether a Note is relevant by changing what is visible. That
does not make the Note a Filter note.

The Artifact Model should support note targeting at the level needed by real
artifacts.

Do not invent a large note-target taxonomy until examples require it.

---

# 16. Provenance

Artifacts may carry provenance.

Provenance may include:

```text
source data
generation date
model family
model version
method notes
sample support
known limitations
audit stage, if public-facing
producer identity
```

Provenance should distinguish public explanatory metadata from internal
diagnostic history.

Internal filenames, diagnostic stage names, or experiment labels should not
become public provenance merely because they exist.

If provenance is important to interpretation, it should be represented in the
Artifact Model or Notes, not hidden in file paths.

---

# 17. Artifact-Local Interaction

Some interaction belongs inside the artifact.

Examples:

```text
table sorting
table row expansion
column popovers
chart hover
chart zoom
legend toggling
section collapse, if local to a sectioned table
```

These interactions do not automatically become UI Model Filters.

An interaction becomes a Filter when it is reader-visible state that restricts,
selects, projects, or otherwise narrows what part of the available analytical
view is shown and is part of the page/contents/PA contract.

Artifact-local interaction may remain internal to the artifact renderer.

---

# 18. Links and Domain Behavior

Artifacts may contain domain-specific links.

Examples:

```text
shikona link
rikishi profile link
SumoDB external link
legacy graph link
related-page link
```

The Artifact Model should represent link meaning where the meaning affects
rendering or public behavior.

For example, shikona links may need consistent click and alternate-click
behavior across table artifacts.

Link behavior should not be reimplemented differently by unrelated artifact
renderers.

---

# 19. Artifact Validation and Internal Consistency

The Artifact Model should be internally coherent.

Examples of expected consistency:

```text
table columns referenced by notes exist
default sort references a sortable column
chart default visible traces exist
section order references known sections
custom renderer kind exists
required data references are supplied
```

An internally incoherent artifact model is a programming error.

The core design does not require defensive recovery from impossible artifact
states.

---

# 20. Relationship to UI Model

The UI Model places the PA.

The Artifact Model defines what is inside it.

Example:

```text
UI Model:
  G1 page with Heading, FilterSection, PA slot, and Notes.

Artifact Model:
  the PA slot contains an IndexedTableArtifact for Basho Results.
```

The UI Model may know the artifact kind.

It should not know table rows, chart traces, or custom artifact internals.

---

# 21. Relationship to Publication Plan

The Publication Plan knows that a planned page requires certain artifact inputs
and runtime support.

The Artifact Model interprets the site-facing inputs into artifact structures.

Example:

```text
PublicationPlan:
  Basho Results requires the BRB artifact input and standard runtime bundle.

Artifact Model:
  BRB is an IndexedTableArtifact with index data, payload data, columns, links,
  notes, and provenance.
```

The Publication Plan always knows the runtime requirements.

The Artifact Model does not surprise the planner with late runtime dependencies.

---

# 22. Relationship to Rendering

Artifact renderers consume Artifact Model objects.

They render artifact internals inside UI Model slots.

The UI Renderer owns:

```text
page shell
ContentPanel
Heading
FilterSection
BranchSelector
PA placement
Note placement policy
```

Artifact renderers own:

```text
table internals
chart internals
sectioned-table internals
prose rendering
custom artifact internals
```

If an artifact renderer needs to change the surrounding page structure, the
model boundary has been crossed.

---

# 23. Relationship to make_site and ui_model Evidence

Existing `make_site` and `ui_model` material may inform the Artifact Model.

Useful evidence includes:

```text
known artifact kinds
known table structures
known chart structures
BRB indexed table behavior
Banzuke Changes custom table behavior
Career Length chart/table alternatives
Typical Equelo sectioned tables
known note/provenance needs
```

That evidence is not authoritative.

The Artifact Model for `make_site2` is defined by the new requirements,
specification, and design.

---

# 24. Deferred Questions

The following questions are deferred:

```text
Exact representation of artifact inputs.
Whether artifact inputs are Python objects, JSON-like data, generated files, or
mixed.
Exact table column metadata vocabulary.
Exact chart semantic metadata vocabulary.
Exact note-target representation.
Exact custom artifact renderer registration mechanism.
Exact prose representation.
Whether a durable serialization format is later needed for artifact contracts.
How much link behavior belongs in Artifact Model versus shared runtime.
```

These should be resolved when they become implementation pressure points.

---

# 25. Summary

The Artifact Model describes the analytical object displayed inside a UI Model
PA slot.

It says:

```text
what kind of artifact this is
what data it uses
what renderer kind it needs
what labels, columns, traces, sections, links, notes, and provenance it owns
what behavior is artifact-local
```

It does not say:

```text
where the page lives in navigation
what route the page has
what ContentPanel grammar is used
what HTML shell is emitted
where files are written
where the site is deployed
```

This separation lets `make_site2` support rich artifact-specific rendering
without returning to page-specific shell rendering.
