## 8. Summary

The Notes/PAPanel, sortable-column, notes-panel and canonical-link corrections
are complete and verified. The settled Basho Results (7.1) model is now folded
into the main spine as `04.5 Basho Results Model.md`, with the current record,
Context, Skill, Analysis, Result and Changes shape rendered by the transitional
runtime.

Basho Results no longer carries its former local kyujo-rating continuity
workaround. The upstream zenkyujo lifecycle bug was fixed in the Oracle input
domain, and BRB now uses the shared `src.analysis.equelo.api.EqueloLookup`
before/after API for Equelo display.

The `get_bios` package may be the right source for biographical lifecycle
semantics such as career length and whether a rikishi should have an Equelo
rating at a given basho, but its current integrity/status needs investigation.
The audit command `src.infra.get_bios.integrity` exists to compare parsed bio
career dates against History banzuke appearances and should inform whether the
bio data can replace banzuke-appearance proxies for lifecycle-sensitive logic.
If public shikona resolution starts consuming `get_bios`, the package also
becomes part of the publication cache lifecycle: the raw SumoDB rikishi-page
downloads and parsed `rikishi_bios.json` cache need an explicit freshness rule
alongside the existing captured basho HTML and current-standings data.

Public shikona disambiguation is implemented but not settled. The current
`get_bios` rule keeps the latest holder of a non-unique History shikona on the
bare name and gives earlier holders their full romanised shikona. The Hakuho
case shows that this is not sufficient: `RikId(1123)` remains public `Hakuho`,
while the earlier `RikId(8206)` also has full romanised shikona `Hakuho`.
Test the kanji-shikona theory before choosing a suffix policy: the first
romanised word as kanji should be unique within a basho, full shikona as kanji
may be unique across the catalogue, and second-word kanji may naturally
disambiguate cross-basho duplicates. This may require extending `get_bios`,
because the current parsed cache stores romanised `Shikona` only. Other
non-`rikid` candidates include `Shusshin` and former shikona history.

The unfinished `makefile` audit/build-control work is the current home for this
bootstrap problem. Either complete it or replace it with another explicit
fresh-install and cache-regeneration contract so maintainers know which
generated outputs are publication prerequisites and how to refresh them.

The tracker/downloader has an open stale daily-results validation issue: an
existing daily-results file may be reused without semantic validation, so a
pre-results page with blank outcome cells can persist and cause downstream
History/BRB output to treat a completed basho as incomplete.

There is also an open duplicate-chii investigation from `2026/05`:
`RikId(13003)` and `RikId(13004)` both appear in History as `Ms60eTD`
(`Ms60TD` in parser recovery output). This may be JSA/SumoDB source-data
weirdness rather than a pure parser defect. Determine whether earlier SumoDB
banzuke pages contained comparable cases that the parser handled successfully,
whether the 2026/05 HTML changed enough to defeat that handling, whether this
is a rare JSA ranking exception, or whether this is the first genuinely
duplicate represented chii. The temporary BCR tolerance preserves publication
while leaving `Chii` ordering/model semantics unchanged.

The active publication-coherence issue is now more accurately defined. Banzuke
Changes is a Page for a newly published successor banzuke before results enter
History; it is not an arbitrary historical comparison Page. Production must
only expose it when its successor-input condition is met, while development may
temporarily keep it accessible for regression testing provided a conspicuous
warning makes that exception visible.

Other copied History-derived PAs remain subject to the broader Selected-History
coherence audit. A separate Plotly empty-trace defect remains open for triage.
A future explicit PA model for table chrome/body separation remains deferred
unless real pressure appears. A universal recursive table presentation model is
also deferred; shared table styling and alignment policy should be pursued first
without requiring all table-like PAs to use the 7.1 table shape.

Filter option grammar is also deferred. The site should be reviewed for
consistent use of checkboxes versus finite-choice controls, especially where a
compact binary checkbox label such as `Current rikishi` replaces a fuller
question such as `Show current rikishi?`.

Records pages have a provisional vocabulary direction: use `Current` and
`Former` rikishi checkboxes for population selection across all five Records
artifacts, with page-specific binary controls such as `Whole career`,
`Fusensho` and `Fusenpai`. The record-position meaning of `#` under population
selection remains a separate open design question.
