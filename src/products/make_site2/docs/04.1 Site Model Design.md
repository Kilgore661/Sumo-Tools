# 04.1 Site Model Design

## Status

Initial design document for the `make_site2` Site Model.

This document describes the declared public-site model. It defines the concepts
that express public intent before publication planning, UI modeling, rendering,
or output writing occur.

This is a design document, not an implementation inventory. Naming a concept
does not imply that the concept must become a Python class.

---

# 1. Purpose

The Site Model describes what the public site claims to contain.

It is the model of declared public intent.

It answers questions such as:

```text
What is this site?
What public subjects does it expose?
What pages are known to the site?
Where do pages belong in the navigation tree?
Which pages are public, candidate, research, diagnostic, legacy, superseded, or
excluded?
What global site-level assets or defaults exist?
```

The Site Model does not answer:

```text
What exact files will be written?
What concrete route table has been derived?
What data files have been resolved?
What UI grammar does a page use?
What HTML/CSS/JS will be emitted?
How will an artifact render internally?
Where will the generated site be deployed?
```

Those questions belong to later model layers.

---

# 2. Site Model Position in the Pipeline

The Site Model is the first model layer in the `make_site2` core pipeline.

```text
SiteDefinition
  -> PublicationPlan
  -> UIModel
  -> RenderedSite
  -> WrittenOutput
```

The Site Model is consumed by the Publication Plan stage.

It is not consumed directly by the renderer.

The Site Model declares public structure. The Publication Plan resolves that
structure for a particular build.

---

# 3. Core Responsibility

The Site Model owns declared public structure.

It owns:

```text
site identity
navigation tree
page registry
page status
global site assets
site-level defaults
home-page identity
quick-entry declarations, if used
```

It does not own:

```text
build timestamp
cache token
output directory
remote deployment target
resolved route table
runtime filter state
concrete copied files
loaded data payloads
loaded artifact inputs
ContentPanel structure
artifact internals
```

A useful rule:

```text
If the concept describes what the public site is, it belongs in the Site Model.
If it describes what this build does with the site, it belongs in the
Publication Plan or build configuration.
```

---

# 4. SiteDefinition

`SiteDefinition` is the root of the Site Model.

Conceptually, it contains:

```text
SiteId
Title
NavigationTree
PageRegistry
GlobalAssets
BuildDefaults
HomePageId
QuickLinks, if used
```

The `SiteDefinition` is authoritative for public-site intent.

If there is a conflict between the SiteDefinition and incidental producer output
layout, the SiteDefinition wins.

Example:

```text
A producer may write files under an implementation-specific output directory.
That directory does not define the public navigation or public route.
The SiteDefinition defines the public structure.
```

---

# 5. Site Identity

The Site Model owns public site identity.

Site identity includes:

```text
stable site id
public title
caption/source text used by the public shell
home-page identity
```

Site identity is distinct from:

```text
page title
navigation label
artifact title
deployment root
package name
```

Example distinction:

```text
Package:
  make_site2

Public site:
  Gaspode-san's Sumo Lab

Deployment root:
  sumo-tools
```

These names may be related, but they do not have the same owner.

---

# 6. NavigationTree

Navigation is the declared subject structure of the public site.

Navigation is a rooted labelled tree.

A navigation node conceptually has:

```text
NodeId
Label
Slug
Children
optional page reference
optional status/readiness/depth metadata
```

A navigation node need not be a page.

Some nodes are subject/grouping nodes. Some nodes are page nodes. Some may be
development aide-memoire or stress-test nodes.

The navigation tree should be organized primarily by subject, not by user type.

Reader depth should normally be handled through page framing, filters, notes,
progressive disclosure, and research/status markers rather than by creating
separate top-level beginner/expert navigation.

---

# 7. Navigation Nodes and Page References

A navigation node may reference a page in the PageRegistry.

A node with a page reference is a navigable page node.

A node without a page reference is a grouping, structural, placeholder,
aide-memoire, or stress-test node.

The Site Model permits unclickable navigation nodes.

Unclickable nodes do not automatically imply planned pages. They may exist to
record possible future structure or to test navigation behavior such as nested
collapsible lists.

The Publication Plan decides what is included in a particular build, but it
should not reinterpret every unclickable node as a missing page.

---

# 8. Canonical Navigation Placement

A public page should have a canonical navigation placement.

For a promoted page, the normal expectation is:

```text
one page
one canonical route
one canonical navigation placement
```

Quick links or home-page entry points may point to the same page, but they do
not create additional canonical placement.

This keeps public structure understandable while still allowing casual-reader
shortcuts.

---

# 9. PageRegistry

The PageRegistry is the collection of page definitions known to the site.

It maps stable page identity to page declarations.

A page may exist in the PageRegistry even if it is not currently promoted.

The PageRegistry is distinct from the navigation tree:

```text
Navigation:
  public subject placement and hierarchy

PageRegistry:
  known page definitions
```

This separation allows:

```text
grouping nodes with no page
pages that are not currently linked
quick links to known pages
development-only pages with explicit status
```

A navigation page reference denotes a page known to the PageRegistry.

---

# 10. PageDefinition

A PageDefinition is the Site Model's declaration of a public or candidate
publication unit.

Conceptually, a PageDefinition contains:

```text
PageId
Title
Summary or framing text
Status
ContentSource
PageAssets, if declared at this level
```

A PageDefinition is not:

```text
an HTML file
a route
a ContentPanel
a UI grammar instance
an artifact
an artifact input payload
```

The PageDefinition identifies the page and points toward its content source.

The UI Model stage later resolves the page into concrete interface structure.

---

# 11. Page Identity and Labels

The Site Model distinguishes several names that should not be collapsed:

```text
PageId
  stable internal/public page identity

NavigationNodeId
  stable navigation-node identity

NavLabel
  short label used in the navigation tree

PageTitle
  public page title/headline

Slug
  route component or route-name component

Summary
  short page framing text
```

These values may be similar, but they are not the same concept.

Example:

```text
PageId:
  basho_results_browser

NavLabel:
  Basho Results

PageTitle:
  Basho Results Browser

Slug:
  basho-results
```

The model should preserve these distinctions so that public wording is not forced
to match implementation identity.

---

# 12. PageStatus

Page status is public-intent metadata.

Initial status vocabulary:

```text
promoted
candidate
research
diagnostic
legacy
superseded
excluded
```

The status records how the project currently regards the page.

At Site Model level, status means:

```text
This is the declared public-intent status of the page.
```

At Publication Plan level, status may affect:

```text
whether the page is included in a build
how the page is marked
whether the page must conform to promoted-page rules
whether the page is visible only in development views
```

Those build consequences belong to the Publication Plan design.

---

# 13. Promoted Pages

A promoted page is a page intended to be part of the normal public site
contract.

A promoted page is expected to have:

```text
stable PageId
canonical navigation placement
canonical public route
public title/framing
site-facing content source
eventual UI Model representation
```

A promoted page is not merely an interesting output.

A promoted page is not a copied prototype artifact unless explicitly still in a
transitional state.

Promoted pages are the pages that should converge on the normal `make_site2`
publication path.

---

# 14. Candidate, Research, Diagnostic, Legacy, Superseded, and Excluded Pages

Non-promoted statuses are used to avoid accidental publication.

A candidate page may be interesting but not yet fully promoted.

A research page may expose methodology, model assumptions, calibration, or
unsettled interpretation.

A diagnostic page may be useful to maintainers or technical readers but is not a
normal public deliverable.

A legacy page may preserve old output or old product ideas but should not define
new public contracts.

A superseded page records something that has been replaced.

An excluded page is known but not part of the public site.

The exact public treatment of each status is decided by the Publication Plan and
rendering design.

The Site Model's responsibility is to record the declared status.

---

# 15. Global Assets

The Site Model may declare global site assets.

Global assets are assets needed by the site as a whole rather than by one page.

Examples might include:

```text
site-wide CSS
site-wide JavaScript
navigation runtime
shared font or icon assets, if used
```

The Site Model may identify these assets, but it does not copy them or decide
their final build-time destination.

Copying and output placement belong to the Publication Plan and OutputWriter.

---

# 16. Page Assets

A PageDefinition may declare page-level assets if those assets are part of the
page's declared public content.

Examples:

```text
page-specific data/artifact input reference
page-specific static image
page-specific custom artifact runtime, if truly local
```

However, page-specific assets should not become a way to smuggle complete
page-specific shells into the Site Model.

If a page asset defines the page structure, that is a sign that the page has not
yet been properly represented in the UI Model.

---

# 17. BuildDefaults versus BuildConfig

The Site Model may contain site-level build defaults.

These are semantic defaults of the public site.

Examples:

```text
default home page
default status inclusion policy
default public theme/runtime family
default quick-entry group
```

Operational build configuration is different.

Operational build configuration includes:

```text
output root
build timestamp
cache token
development versus production mode
local deployment target
remote deployment target
```

Operational configuration belongs to BuildConfig or BuildContext, not the Site
Model.

---

# 18. Home Page

The public site should have a declared home page.

The home page should be a normal PageDefinition unless later design gives a
specific reason to generate it automatically.

The SiteDefinition may name the home page by PageId.

This preserves two facts:

```text
the home page is a real public page
the site definition chooses which page is home
```

---

# 19. Quick Links

The Site Model may support quick links.

Quick links are not the canonical navigation tree.

They are casual-reader entry points into the canonical structure.

Examples:

```text
latest standings
banzuke changes
basho results
rikishi lookup
rank outcomes
ratings/model explanation
```

Quick links should reference known pages or public routes.

They should not become a second public information architecture.

Quick links may be deferred from the first implementation.

---

# 20. Site Model Invariants

The Site Model should be internally coherent.

Important invariants include:

```text
SiteId is stable.
Navigation node ids are stable within the site.
Page ids are stable within the site.
A navigation page reference denotes a known page.
A declared home page denotes a known page.
A quick link, if present, denotes a known page or public route.
A promoted page has a canonical navigation placement.
Page status is explicit.
```

The Site Model does not need a defensive recovery path for violations of these
invariants.

An internally incoherent SiteDefinition is a programming error.

---

# 21. What the Site Model Does Not Own

The Site Model does not own:

```text
concrete output file paths
deployment paths
build timestamps
cache-busting tokens
loaded producer data
parsed artifact inputs
ContentPanel structures
FilterSections
G1/G2 grammar selection
artifact rendering
table rows
chart traces
HTML templates
CSS class implementation
JavaScript behavior
```

Those belong to later stages.

This boundary matters because the Site Model should remain a declaration of
public intent, not an accidental build script.

---

# 22. Transformation to PublicationPlan

The next stage consumes the Site Model and produces a Publication Plan.

Conceptually:

```python
def make_publication_plan(
    site_definition: SiteDefinition,
    build_config: BuildConfig,
) -> PublicationPlan:
    ...
```

This transformation resolves:

```text
included pages
canonical routes
dependency references
status-based inclusion
build-mode consequences
```

It does not render the UI.

It does not decide artifact internals.

It prepares the declared site for UI-model resolution and rendering.

---

# 23. Relationship to make_site and ui_model Evidence

Existing `make_site` and `ui_model` material may inform the Site Model.

Useful evidence includes:

```text
current navigation shape
known page ids
likely page statuses
stress-test navigation nodes
current public candidates
legacy/prototype inclusions
```

That evidence is not authoritative.

The Site Model for `make_site2` is defined by the new requirements,
specification, and design.

---

# 24. Deferred Questions

The following questions are deferred:

```text
Exact status vocabulary after first implementation.
Whether quick links are included in the first vertical slice.
Whether non-promoted pages appear in development builds.
Whether inactive navigation nodes appear in public builds.
Whether home page is hand-authored or generated from navigation/quick links.
Exact representation of global and page assets.
Exact route-slug derivation policy.
```

These should be resolved when they become implementation pressure points.

---

# 25. Summary

The Site Model is the declared public-site model.

It says:

```text
what the site is
what pages are known
how public subjects are organized
which pages have which public-intent status
what site-level assets and defaults exist
```

It does not say:

```text
how pages are rendered
what concrete files are written
how artifacts work internally
how deployment happens
```

The Site Model should be rich enough to make public intent explicit, but it
should remain upstream of publication planning, UI modeling, rendering, and
output writing.
