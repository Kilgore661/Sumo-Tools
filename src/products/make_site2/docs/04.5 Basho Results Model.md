# 04.5 Basho Results Model

## Status

Normative design document for the Basho Results (7.1) Published Artifact in
`src/products/make_site2`.

This document folds the settled 7.1 redesign into the main documentation spine.
The earlier `Basho Results (7.1) Outcome.md` is now supporting historical
evidence rather than the active authority.

This document refines:


It does not decide that all table PAs must use the recursive Basho Results table

## 1. Public Question

Page **7.1 Basho Results** remains **Basho Results**.

It is the public place to inspect results for a basho represented in the site's
History:

- completed historical bashos;
- the latest/current basho once results exist; and
- in-progress bashos where results are known only up to a represented day.

The page should not be renamed `Latest Results`: the selected-basho historical
reading is part of its public meaning.

Page **2.1 Banzuke Changes** remains separate. It answers the
new-banzuke-before-results question:

```text
A new banzuke has been published before that basho has results of its own.
How does it differ from the preceding represented basho?
```

Basho Results answers a different represented-basho question:

```text
A basho is represented in History. What were the results for that basho, and how
should selected before/current/after analytical context be inspected?
```

## 2. Published Artifact Shape

Basho Results is an indexed table PA whose selected table instance is chosen by
public Filter state, principally selected basho and division.

Unlike ordinary flat table PAs, Basho Results uses a recursive hierarchical table
specification because its visible public meaning is temporal and grouped:

```text
reference
before
selected
comparison
```

The `before` and `selected` groups are parallel basho-record groups. `before`
represents the predecessor basho record and is visible only when previous-basho
context is selected. `selected` represents the selected basho record and is
always part of the selected Basho Results table. The `selected` group renders as
`Current` for an in-progress represented basho and `After Basho` for a completed
represented basho.

The recursive structure is a Basho Results presentation-table model, not a new
site-wide table requirement. The model is justified here because repeated flat
headings such as `BP`, `Result`, `Equelo`, or `Analysis` are ambiguous unless
their before/selected/comparison context is visible.

Conceptually:

```text
BashoResultsPA
  selected_basho
  selected_division
  lifecycle_state
  header
  recursive_table_spec
  row_values
  visible_projection
  local_sort_state
```

The surrounding page grammar remains unchanged:

```text
ContentPanel -> Heading . Contents
Contents -> FilterSection? . PAPanel
PAPanel -> PA . Notes
```

The Basho Results renderer owns only the PA-internal table structure.

## 3. Recursive Table Specification

A Basho Results table specification is an ordered recursive keyed structure:

```text
TableSpec ::= S+
S ::= <key> : (<terminal column> | TableSpec)
```

The maximal Basho Results frame is:

```text
BashoResultsFrame ::=
[
  reference: ReferenceSpec,
  before: RecordSpec,
  selected: RecordSpec,
  comparison: ComparisonSpec
]
```

The maximal known structure is:

```text
reference
  row_number
  shikona

before
  context
    skill
      bp
      equelo
    analysis
      banzuke_error
        direction
        magnitude
      rbbp
  result
    wins
    losses
    absences
    prizes

selected
  context
    skill
      bp
      equelo
    analysis
      banzuke_error
        direction
        magnitude
      rbbp
  result
    wins
    losses
    absences
    prizes
  next_bp

comparison
  division_change
  delta_equelo
```

The current implementation covers this transitional slice of the model:
reference columns, before/selected BP, decomposed result columns, Equelo context,
monolithic Analysis projection containing BZ Error / DeltaBZ and RBBP, `nuChii`
where available, Division Change as a comparison value, and `delta_equelo`.
Producer output is still transitional in places, especially compact result
strings and client-side derivation of Analysis values.

## 4. Records, Context, Skill, Analysis and Result

A Basho Results **record** is the before-basho or selected-basho row object for a
rikishi. In the presentation model:

```text
before :: record
selected :: record
```

A record has two main parts:

```text
record
  context
  result
```

`context` contains non-result information about the rikishi at that represented
basho point:

```text
context
  skill
    bp
    equelo
  analysis
    banzuke_error
      direction
      magnitude
    rbbp
```

`skill.bp` is the official BP/Chii slot. `skill.equelo` is the rating value for
the represented point. `analysis` contains values derived from comparing the BP
ordering and the Equelo ordering. Analysis is intentionally monolithic for the
current UI: the public `Analysis` option controls the whole analysis subtree. A
future design may split it only if real pressure appears.

`result` contains the decomposed score information for that record:

```text
result
  wins
  losses
  absences
  prizes
```

Division Change is not a result field in this model. It compares the selected
record's BP context with successor BP context where known, so it belongs to the
top-level `comparison` group.

## 5. Terminal Paths and Values

Terminal paths are the stable column identities in the Basho Results recursive
table. They play the role that flat column ids play in ordinary table PAs.

Examples:

```text
reference.row_number
reference.shikona
before.context.skill.bp
before.context.skill.equelo
before.context.analysis.banzuke_error.direction
before.context.analysis.banzuke_error.magnitude
before.context.analysis.rbbp
before.result.wins
before.result.losses
before.result.absences
before.result.prizes
selected.context.skill.bp
selected.context.skill.equelo
selected.context.analysis.banzuke_error.direction
selected.context.analysis.banzuke_error.magnitude
selected.context.analysis.rbbp
selected.result.wins
selected.result.losses
selected.result.absences
selected.result.prizes
selected.next_bp
comparison.division_change
comparison.delta_equelo
```

Terminal paths resolve to concrete display values or null/empty values. Public
options project or hide parts of the resolved table; options do not decide
whether values conceptually exist.

A terminal path may have a separate sort-value path where the displayed value is
not the correct sortable value. BP display values shall sort by emitted ordinal
values, not by runtime parsing of display strings.

## 6. Public Projection Options

The current Basho Results projection is deliberately simple and ad hoc. It is
not a general theory of hierarchical table options.

```text
Previous Basho
  shows the `before` record.

Equelo Ratings
  shows `*.context.skill.equelo` and `comparison.delta_equelo`.
  It does not show Analysis merely because Analysis depends on ratings.

Analysis
  shows `*.context.analysis.*` as one monolithic subtree: BZ Error direction,
  BZ Error magnitude and RBBP.

nuChii
  shows `selected.next_bp`.
```

The minimal selected record projection is:

```text
selected.context.skill.bp
selected.result.wins
selected.result.losses
selected.result.absences
selected.result.prizes
comparison.division_change
```

When a projected group has only one visible child, the current renderer may still
show the intermediate group headings. That is acceptable for now and does not
trigger a general hierarchical table projection/collapse theory.

## 7. Result Decomposition

Basho Results does not treat a compact result string as the final public model.
A result is logically decomposed into:

```text
wins
losses
absences
prizes
```

`prizes` remains a compact displayed value. Other result fields are logically
separate even if a later view chooses to display them compactly.

The current renderer still contains transitional parsing where producer output
has not yet emitted the final decomposed shape. That parsing is a migration seam,
not the final model.

## 8. Rating-Order Analysis Model

Basho Results may compare official BP order with Equelo order for the same
selected table population.

For a given record:

```text
banzuke_position
  position when rows are ordered by official BP/Chii;

rating_position
  position when rows are ordered by Equelo rating;

signed_bz_delta
  banzuke_position - rating_position;

rbbp
  the official BP slot at rating_position in the BP-ordered slot list.
```

`signed_bz_delta` is an implementation convenience, not the public model. The
public BZ Error / DeltaBZ value is decomposed into:

```text
direction
  up      rating_position is higher than banzuke_position;
  down    rating_position is lower than banzuke_position;
  none    positions are equal or the comparison cannot be made;

magnitude
  absolute distance between banzuke_position and rating_position.
```

An upward direction means the rating order places the rikishi higher than the
official banzuke order. A downward direction means the rating order places the
rikishi lower than the official banzuke order.

RBBP is the rating-based BP slot, not a prediction of actual promotion or
placement by the banzuke committee. It ignores promotion rules, rank-holding
conventions, vacancies and other banzuke-making constraints. It answers only:

```text
If the selected population occupied the same BP slots in Equelo order, which BP
slot would this rikishi occupy?
```

The output paths are:

```text
before.context.analysis.banzuke_error.direction
before.context.analysis.banzuke_error.magnitude
before.context.analysis.rbbp
selected.context.analysis.banzuke_error.direction
selected.context.analysis.banzuke_error.magnitude
selected.context.analysis.rbbp
```

These paths belong to `context.analysis` because they are derived analysis about
the represented record's context, not raw skill indicators and not results.

## 9. Temporal Resolution

For the `before` record:

```text
before.context.skill.bp
  predecessor-basho BP

before.result.*
  predecessor-basho result values

before.context.skill.equelo
  pre-selected-basho Equelo rating

before.context.analysis
  predecessor-basho banzuke slots plus pre-selected-basho rating order
```

For an in-progress selected basho:

```text
selected.context.skill.bp
  selected-basho BP

selected.result.*
  selected-basho results through the represented day

selected.context.skill.equelo
  day-end Equelo rating after the represented day

selected.context.analysis
  selected-basho banzuke slots plus day-end rating order
```

For a completed selected basho:

```text
selected.context.skill.bp
  selected-basho BP

selected.result.*
  final selected-basho result values

selected.context.skill.equelo
  post-basho/final-day Equelo rating

selected.context.analysis
  selected-basho banzuke slots plus post-basho rating order
```

`selected.next_bp` is successor BP context and is shown by the current transitional
`nuChii` option. `comparison.division_change` compares selected BP context with
successor BP context where known.

Operational data availability may lag the ideal date/time-derived state. That is
an operations/build-data concern, not a change to the pure table model.

## 10. Movement and Comparison Terms

Three arrow-like concepts are distinct and shall not be collapsed:

```text
Division Change
  Whether selected BP context changed significantly relative to successor BP
  context. This is a Basho Results comparison value.

Movement
  Whether a rikishi actually moved up/down in the official banzuke from one
  basho to the next. This is the 2.1 Banzuke Changes movement feature.

BZ Error / DeltaBZ
  Whether rating order places the rikishi above/below their official BP order,
  plus the absolute size of that discrepancy. This is Basho Results analysis.
```

Basho Results currently renders Division Change under `comparison`. Banzuke
Changes renders Movement. Basho Results renders BZ Error / DeltaBZ and RBBP under
`context.analysis` when the Analysis option is selected.

## 11. Sorting

Basho Results follows the ordinary table sorting contract, adapted to recursive
terminal paths.

```text
Ordinary flat table:
  sortable column identity = flat column id

Basho Results recursive table:
  sortable column identity = recursive terminal path
```

A sortable Basho Results column is a visible leaf heading: a terminal heading
that sits above exactly one data column.

Rules:

- every visible leaf heading is sortable by default;
- `reference.row_number` is a reference column and is not sortable;
- group headings are not sortable because they do not identify one data column;
- clicking a sortable leaf heading sorts rows by that leaf column's sort value;
- clicking the active sorted leaf heading reverses the sort direction;
- the active sorted leaf heading visibly indicates direction and exposes
  equivalent accessible state;
- row numbers are renumbered after filtering and sorting.

The default Basho Results sort is `selected.context.skill.bp` ascending by the
emitted BP ordinal value.
