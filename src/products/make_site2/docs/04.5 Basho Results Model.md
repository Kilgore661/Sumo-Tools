# 04.5 Basho Results Model

## Status

`src/products/make_site2`.

This document folds the settled 7.1 redesign into the main documentation spine.
The earlier `Basho Results (7.1) Outcome.md` is now supporting historical

This document refines:

## 1. Public Question

Page **7.1 Basho Results** remains **Basho Results**.

It is the public place to inspect results for a basho represented in the site's
History:

- completed historical bashos;
- the latest/current basho once results exist; and
- in-progress bashos where results are known only up to a represented day.

The page should not be renamed `Latest Results`: the selected-basho historical
reading is part of its public meaning.

Page **2.1 Banzuke Changes** remains separate. It answers the
new-banzuke-before-results question:

```text
A new banzuke has been published before that basho has results of its own.
How does it differ from the preceding represented basho?
```

Basho Results answers a different represented-basho question:

```text
A basho is represented in History. What were the results for that basho, and how
should selected before/current/after analytical context be inspected?
```

## 2. Published Artifact Shape

Basho Results is an indexed table PA whose selected table instance is chosen by
public Filter state, principally selected basho and division.

Unlike ordinary flat table PAs, Basho Results uses a recursive hierarchical table
specification because its visible public meaning is temporal and grouped:

```text
reference
before
state
comparison
```

The recursive structure is a Basho Results presentation-table model, not a new
site-wide table requirement. The model is justified here because repeated flat
headings such as `Chii`, `Result`, or `Equelo` are ambiguous unless their
before/current/after context is visible.

Conceptually:

```text
BashoResultsPA
  selected_basho
  selected_division
  lifecycle_state
  header
  recursive_table_spec
  row_values
  visible_projection
  local_sort_state
```

The surrounding page grammar remains unchanged:

```text
ContentPanel -> Heading . Contents
Contents -> FilterSection? . PAPanel
PAPanel -> PA . Notes
```

The Basho Results renderer owns only the PA-internal table structure.

## 3. Recursive Table Specification

A Basho Results table specification is an ordered recursive keyed structure:

```text
TableSpec ::= S+
S ::= <key> : (<terminal column> | TableSpec)
```

The maximal Basho Results frame is:

```text
BashoResultsFrame ::=
[
  reference: ReferenceSpec,
  before: RBASpec,
  state: RBASpec,
  comparison: ComparisonSpec
]
```

The `state` group heading is rendered as:

```text
Current
  for an in-progress represented basho

After Basho
  for a completed represented basho
```

The maximal known structure is:

```text
reference
  row_number
  shikona

before
  rba
    bp
    result
      wins
      losses
      absences
      prizes
      division_change
    equelo
    rbbc
      banzuke_error
        direction
        magnitude
      rbbp

state
  rba
    bp
    result
      wins
      losses
      absences
      prizes
      division_change
    equelo
    rbbc
      banzuke_error
        direction
        magnitude
      rbbp

comparison
  delta_equelo
```

The current implementation covers the settled transitional slice of that model:
reference columns, before/state BP, decomposed result columns, Equelo context,
`nuChii` where available, and `delta_equelo`. `rbbc`, BZ Error / DeltaBZ and
RBBP are now specified/design-defined concepts but remain implementation work
items until producer output, rendering and verification are complete.

## 4. Terminal Paths and Values

Terminal paths are the stable column identities in the Basho Results recursive
table. They play the role that flat column ids play in ordinary table PAs.

Examples:

```text
reference.row_number
reference.shikona
before.rba.bp
before.rba.result.wins
before.rba.result.losses
before.rba.result.absences
before.rba.result.prizes
before.rba.result.division_change
before.rba.equelo
before.rba.rbbc.banzuke_error.direction
before.rba.rbbc.banzuke_error.magnitude
before.rba.rbbc.rbbp
state.rba.bp
state.rba.result.wins
state.rba.result.losses
state.rba.result.absences
state.rba.result.prizes
state.rba.result.division_change
state.rba.equelo
state.rba.rbbc.banzuke_error.direction
state.rba.rbbc.banzuke_error.magnitude
state.rba.rbbc.rbbp
state.rba.next_bp
comparison.delta_equelo
```

Terminal paths resolve to concrete display values or null/empty values. Public
options project or hide parts of the resolved table; options do not decide
whether values conceptually exist.

A terminal path may have a separate sort-value path where the displayed value is
not the correct sortable value. Chii/BP display values shall sort by emitted
ordinal values, not by runtime parsing of display strings.

## 5. Result Decomposition

Basho Results does not treat a compact result string as the final public model.
A result is logically decomposed into:

```text
wins
losses
absences
prizes
division_change
```

`prizes` remains a compact displayed value. Other result fields are logically
separate even if a later view chooses to display them compactly.

The current renderer still contains transitional parsing where producer output
has not yet emitted the final decomposed shape. That parsing is a migration seam,
not the final model.

## 6. Rating-Order Comparison Model

Basho Results may compare official BP order with Equelo order for the same
selected table population.

For a given row:

```text
banzuke_position
  position when rows are ordered by official BP/Chii;

rating_position
  position when rows are ordered by Equelo rating;

signed_bz_delta
  banzuke_position - rating_position;

rbbp
  the official BP slot at rating_position in the BP-ordered slot list.
```

`signed_bz_delta` is an implementation convenience, not the public model. The
public BZ Error / DeltaBZ value is decomposed into:

```text
direction
  up      rating_position is higher than banzuke_position;
  down    rating_position is lower than banzuke_position;
  none    positions are equal or the comparison cannot be made;

magnitude
  absolute distance between banzuke_position and rating_position.
```

An upward direction means the rating order places the rikishi higher than the
official banzuke order. A downward direction means the rating order places the
rikishi lower than the official banzuke order.

RBBP is the rating-based BP slot, not a prediction of actual promotion or
placement by the banzuke committee. It ignores promotion rules, rank-holding
conventions, vacancies and other banzuke-making constraints. It answers only:

```text
If the selected population occupied the same BP slots in Equelo order, which BP
slot would this rikishi occupy?
```

The conceptual output paths are:

```text
before.rba.rbbc.banzuke_error.direction
before.rba.rbbc.banzuke_error.magnitude
before.rba.rbbc.rbbp
state.rba.rbbc.banzuke_error.direction
state.rba.rbbc.banzuke_error.magnitude
state.rba.rbbc.rbbp
```

These paths belong to `rbbc` because they compare a represented BP-slot ordering
with a rating ordering for the same represented point.

## 7. Temporal Resolution

For the `before` group:

```text
before.rba.bp
  predecessor-basho BP

before.rba.result.*
  predecessor-basho result values

before.rba.result.division_change
  predecessor performance's significant promotion/demotion into the selected
  basho's broad division or rank level

before.rba.equelo
  pre-selected-basho Equelo state

before.rba.rbbc
  selected-basho banzuke slots plus pre-selected-basho rating order
```

For an in-progress basho:

```text
state.rba.bp
  selected-basho BP

state.rba.result.*
  selected-basho results through the represented day

state.rba.result.division_change
  null

state.rba.equelo
  day-end Equelo state after the represented day

state.rba.rbbc
  selected-basho banzuke slots plus day-end rating order
```

For a completed basho:

```text
state.rba.bp
  selected-basho BP

state.rba.result.*
  final selected-basho result values

state.rba.result.division_change
  significant promotion/demotion into the successor basho's broad division or
  rank level when the successor banzuke is known; otherwise null

state.rba.equelo
  post-basho/final-day Equelo state

state.rba.rbbc
  selected-basho banzuke slots plus post-basho rating order
```

Operational data availability may lag the ideal date/time-derived state. That is
an operations/build-data concern, not a change to the pure table model.

## 8. Movement Terms

Three arrow-like concepts are distinct and shall not be collapsed:

```text
Division Change
  Whether a result caused a significant promotion/demotion into a different
  broad division or rank level.

Movement
  Whether a rikishi actually moved up/down in the official banzuke from one
  basho to the next. This is the 2.1 Banzuke Changes movement feature.

BZ Error / DeltaBZ
  Whether rating order places the rikishi above/below their official BP order,
  plus the absolute size of that discrepancy.
```

Basho Results currently renders Division Change. Banzuke Changes renders Movement.
BZ Error / DeltaBZ remains a Basho Results implementation task for the `rbbc`
group.

## 9. Sorting

Basho Results follows the ordinary table sorting contract, adapted to recursive
terminal paths.

```text
Ordinary flat table:
  sortable column identity = flat column id

Basho Results recursive table:
  sortable column identity = recursive terminal path
```

A sortable Basho Results column is a visible leaf heading: a terminal heading
that sits above exactly one data column.

Rules:

- every visible leaf heading is sortable by default;
- `reference.row_number` is a reference column and is not sortable;
- group headings are not sortable because they do not identify one data column;
- clicking a sortable leaf heading sorts rows by that leaf column's sort value;
- clicking the active sorted leaf heading reverses the sort direction;
- the active sorted leaf heading visibly indicates direction and exposes
  equivalent accessible state;
- row numbers are renumbered after filtering and sorting.
