Look at the code and docs in make_site. Now look at the migration plan in make_site2. Let's get started.

Important context from the previous discussion:

The existing make_site docs are still the current make_site model, but the make_site2 migration plan intentionally departs from them in several places. Do not assume the make_site docs are the final make_site2 target.

The current make_site docs use:
  ContentPanel = Heading + Options? + Contents
  Contents = PA | PASet
  PASet = PASelector + PA+
  PA = PATitle? + Artifact + Notes?

In the make_site2 plan we changed this.

Key decisions for make_site2:

1. Start with a new package:
   src/products/make_site2

2. First milestone:
   an iframe-free BRB-only build.
   Nav item 7.1 Basho Results / Basho Results Browser / BRB should render directly inside the ContentPanel.
   No iframe.
   No copied standalone HTML.
   No TableAppView / StandaloneHtmlView path for promoted pages.

3. The old word “Option” is no longer the preferred make_site2 model term.
   Use “Filter” instead.

4. Informal data model:
   There is one giant table with all the data.
   We filter/project what we want from it.
   The result may be rendered as a table or as a chart.
   Tables and charts are not semantically different kinds of PA; they are different renderings of table-shaped views.
   Keep calling the public unit a PA, but conceptually a non-prose PA is a table-shaped view plus public meaning.

5. Filter model:
   FilterSection -> Filter*
   Filter -> SimpleFilter | FilterGroup
   FilterGroup -> Tag . Filter+

   Filters do not have Notes.
   A filter can have a short label/help/popover, but not persistent Notes.

6. Current working grammars:

   G1:
   ContentPanel -> Heading . Contents
   Contents -> FilterSection . PA+ . Note*
   PA -> Title . Artifact

   G2:
   ContentPanel -> Heading . Contents
   Contents -> PA+ . Note*
   PA -> Title . Artifact . FilterSection

   G1 is the normal case.
   G2 is for PA-specific filters.

7. Current working partition:
   Most extant pages are G1.
   Career Length / 7.3.1 is G2.
   finish_by_chii should be considered G1 once migrated, not ignored; it is a multi-chart page with shared filters and no notes.

8. Career Length / 7.3.1 should not be treated as five views.
   It is better modeled as two PAs:
     Charts:
       chart = distribution | PMF | CDF | survival
     Longest:
       active = all rikishi | active only

   So Career Length has PA-specific filters.
   The first filter applies to the chart PA.
   The second applies to the Longest table PA.

9. Notes:
   Notes only pertain to table PAs.
   Charts do not have notes.
   Filters do not have notes.
   Notes may be carried at the contents level in the grammar, but behind the scenes they should render only when the relevant table PA and relevant table column/column group/table feature is visible.
   This is a deliberate simplification from the make_site docs, which still allow notes to pertain to chart traces/sources.

10. The next task is probably:
   read the make_site code and current make_site docs;
   read the make_site2 migration plan;
   then work through the case studies and classify each current clickable nav item under G1 or G2:
     - BRB / 7.1
     - ordinary chart pages
     - ordinary table pages
     - Career Length / 7.3.1
     - finish_by_chii
   The purpose is to verify that G1/G2 cover the current project before implementing too much.

11. Watch for stale terminology:
   Existing docs and code still say Options, PASet, MultiViewPA, PASelector, selected-PA options, and PA Notes.
   In make_site2, those terms may be implementation history rather than target model.
